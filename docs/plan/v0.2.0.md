# What v0.2.0 is for

**Close the gaps [the v0.1.0 notes](../releases/v0.1.0.md) disclose — under
*What it does not read*, and now under *What it does not finish* as well.**

The first section lists six measured cases where a credential reaches the model
through a surface this scanner is wired to. The second was added by errata on
2026-09-03 and holds one more, of a different kind: not a buffer the scanner
declines to read, but one it is still reading when the harness kills it. Both
are published, so they are the commitment a reader can hold this project to
without a checkout — which is what makes this a scope rather than a preference.
Whether the scope held is read off a diff between two release notes, not off
anyone's account of the release.

## The rows the tag waits for

Labelled `v0.2.0` in `docs/queue/`.

| Row | The disclosed case |
|---|---|
| [Q95](../queue/Q95.md) | a recursive read is refused, so `grep -r` does not run |
| [Q87](../queue/Q87.md) | readers outside the three that have been driven |
| [Q108](../queue/Q108.md) | a secret synthesized at runtime, with nothing to open |
| Q111 — closed | a block carries no notice about a buffer nothing read |
| Q118 — **done** | a binary-looking `@` target crossed whole and unscanned. The prompt surface matches the raw bytes now; `Read` and `Bash` still skip them, on a measured cost rather than a policy |
| [Q120](../queue/Q120.md) | a scan that runs past the 60-second timeout, disclosed on 2026-09-03 as *What it does not finish* |

**Q111 is closed**, so its row is in the history rather than the store: every
verdict over a call carrying a buffer nothing read now names that buffer, and
the notes can say which channel each event was measured to deliver that on
instead of restating the gap.

**Closing a row here means deciding it, which for two of them is not a code
change.** Q95's three answers include the status quo, and Q108's case is
structural — bytes that exist only in a tool process cannot be opened at
`PreToolUse`. A row closes when the notes can state the outcome and the reason
rather than restating the gap, and *the gap is unchanged, here is why* is a
legitimate outcome for either. What is not legitimate is carrying the same
sentence into a second release with no argument attached to it.

Two of the three still open from *What it does not read* carry `open-question`
or wait on a row that does. Q95's input
has since arrived: the timeout measurement it was waiting on is
[taken](../design/README.md#the-third-shape-is-a-timeout-and-it-is-the-one-this-repo-configures),
and it points at refusing rather than walking — a hook past its timeout is
killed and the call proceeds, so an unbounded walk that overruns allows instead
of stalling. Q95 still owes the walk benchmark, which no longer decides the
question by itself.

## The timeout, and why one row of three is in the table

That measurement also opened [Q120](../queue/Q120.md): the same expiry allows any
buffer too large to finish in the budget, `Read` and `Bash` operands alike, with
no directory involved. **The scope call is taken — fix it in v0.2.0, and correct
v0.1.0 by errata rather than by a patch tag.** The errata landed in #95, which
added *What it does not finish* to the v0.1.0 notes, so this is no longer a
seventh case outside the disclosed set. It is disclosed, which is what puts it in
the table above on this file's own terms.

Three rows carry the `v0.2.0` label and only Q120 is listed, because the table
means *the tag waits for this* and the other two are inputs to Q120 rather than
gates of their own:

- **[Q122](../queue/Q122.md)** is the measurement that sizes the budget — ~390
  MiB of keyword-bearing text in one call, on an M5 Max. Its headline number is
  published in the v0.1.0 errata already, and what it still owes is the residual
  its own last section lists: an end-to-end drive against a real session, and a
  reading on a slower machine. That is the benchmark Q120 says its budget must be
  picked against, so it closes as part of Q120 rather than beside it.
- **[Q123](../queue/Q123.md)** is an optimisation and not a gate. Anchoring the
  match loop at the prefilter's hit positions moves the crossing by about an order
  of magnitude, which changes how often anyone meets the budget and not whether
  the budget must exist — Q123 says so itself. Making the tag wait on it would
  hold v0.2.0 for a differential proof and a four-rule benchmark in order to make
  a fixed defect less likely to be met.

Both stay labelled so that cutting the tag drops the label from them, and so a
groom reading `render --label v0.2.0` sees the whole cluster rather than the one
row that gates it.

## What is out, and why it is named rather than dropped

- **The sixth read-gap, [Q102](../queue/Q102.md)** — a UTF-8 byte-order mark
  ahead of a NUL. Deferred on its own argument: the notice covers the whole
  residual class where a third decode arm would cover one member of it. The gap
  stays disclosed in v0.2.0's notes, with the trigger that would revive it.
- **The two install channels, [Q13](../queue/Q13.md) and
  [Q14](../queue/Q14.md).** Named in the same section, and a different kind of
  gap — a machine that cannot verify, rather than a buffer nothing read. They
  rank near the bottom of the store and nothing here moves them up.

## How this file retires

When `v0.2.0` is tagged. A plan doc naming a release that already exists is the
staleness this arrangement is meant to avoid, so cutting the tag deletes this
file and drops the label from any row still carrying it —
[`release-process.md`](../development/release-process.md) carries that step,
under *Publishing the draft*.

**Nothing checks it.** That is a step somebody performs by reading it back,
which is the construction #85 and #87 both paid for. The gate is filed as
[Q119](../queue/Q119.md).

Until then the check is cheap and needs no gate: this file names a version, and
comparing that version against the next tag to cut is what says whether it is
current.
