**spill-guard keeps secrets and PII from reaching the API through a Claude Code session.** It scans at the boundary between your filesystem and the model's context — the one a git secret scanner never sees, because a file read into a session is never committed.

> [!WARNING]
> This is a `0.x` release and the surface carries no compatibility promise. Subcommand names, rule IDs, the reason strings, and the shape of a verdict can change in the next minor.

> [!NOTE]
> **`aws-access-key-id` matches four prefixes now, not five.** The `A3T` arm is cut, because it traces to nothing AWS publishes. If you were relying on it, **Deprecations** has the sourcing and what the cut is and is not evidence of.

## What v0.4.0 is for

Three things, and none of them is a new feature. **Close the edges v0.3.0 disclosed, put a control on the release path, and stop the scanner blocking reads of this repository's own tests.**

The v0.3.0 notes ended with a list, under *What it does not read*, of the edges a resolver acquires by resolving more. That list is published, so it is the commitment a reader can hold this project to without a checkout, and working it down is the first theme: two of the five edges it added are closed here.

The second is the release path. It carries ten named steps and seven of them assert something no pull request can reach — signing, attestation, upload — and v0.1.0 cost four tag cycles finding that out. What landed is a negative control: the verification a release depends on now has to prove it can *reject*, and it runs on every pull request against the last published release rather than first executing on a permanent version number.

The third is friction this project met on itself. The hook refused a `grep` over this repository's own test files, and thirteen of the twenty-two files that tripped it are supposed to — the corpus doing its job. That makes it a precision question rather than a convenience, and the answer is a gate that requires every tripping file to be a decision somebody made.

## Highlights

- **`aws-access-key-id` cuts the `A3T` prefix arm.** AWS's IAM identifiers reference, *Understanding unique ID prefixes*, names twelve prefixes; `A3T` is not among them, and the ruleset carried it because it was inherited rather than written. `ABIA` and `ACCA` are on that list and stay, now with the citation beside them. Four prefixes ship: `AKIA`, `ASIA`, `ABIA`, `ACCA`. **The cut is not sourced to a zero**: `A3T` reports 0 raw matches over 5.05 GiB of third-party Go source, and so does `AKIA` on the surviving column, which is exactly the reading `rules/README.md` forbids drawing an arm's death from. The zero bounds what the cut costs on that population and says nothing about whether AWS issues the prefix. The residual is the table's own caveat: *"Prefixes may vary based on when they were created."*
- **`private-key-block` steps over a whitespace-only separator line.** The rule crossed from the header to the base64 body across `[\r\n]+`, so a separator line carrying a space or a tab was not crossed and the key went unreported. The producer of that shape is `git diff`: unified format prefixes every context line with a space, so a blank line inside a quoted file arrives carrying exactly one — driven on git 2.55.0 rather than argued from the format spec. An encrypted PKCS#1 key is what pays for it, because `openssl rsa -aes128 -p` and `ssh-keygen -m PEM -N` both write a bare empty line between `DEK-Info:` and the body. **Both steps widened, not the header's alone**: in an encrypted key the whitespace-only line falls after `DEK-Info:`, and a header-only fix reports three of the five new cases and misses that one and the planted patch. The corpus case is `git diff -U14` output with its command and git version recorded in the preamble, not a hand-written patch, because a patch somebody typed would be a guess about what the format does.
- **A `for` loop's variable resolves to its literal list.** `for f in a b; do cat "$f"; done` scanned neither file on v0.3.0 and gets a verdict on both now. This was the fourth item on v0.3.0's own disclosure list, and it closes.
- **A `case` arm is read as conditional.** `case x in y) P=/case;; esac; cat $P/f` resolved `/case/f` on v0.3.0 — a path bash may never have assigned — and is recorded rather than mis-resolved now. This was the third item on that list, and it closes too. Nineteen `case` arms in the measured week assign a variable, nine of them expanded later.
- **The install scripts pin the tag when they verify with `gh`.** `--signer-workflow` matches the certificate subject as a *prefix*, so the bare `<owner>/<repo>/.github/workflows/release.yml` both scripts passed accepted that workflow at **any ref**, while the `cosign` branch beside it pinned the tag. Since the scripts verify with whichever tool is present, a machine with only `gh` took the weaker path. Measured against the published v0.3.0 attestation: bare exits 0, `@refs/tags/v0.3.0` exits 0, `@refs/heads/main` exits 1. Both verifiers now assert the same string.

## Upgrading

Both halves move. The binary is what changed; the plugin manifest version is what makes `claude plugin update` deliver it.

```
curl -fsSLO https://github.com/karlkfi/claude-spill-guard/releases/download/v0.4.0/install.sh
sh install.sh
claude plugin update spill-guard
```

Windows, in PowerShell:

```
curl.exe -fsSLO https://github.com/karlkfi/claude-spill-guard/releases/download/v0.4.0/install.ps1
powershell -ExecutionPolicy Bypass -File install.ps1
```

Two steps rather than one on purpose. The one-liner that pipes a remote script into a shell works, and for a tool whose whole pitch is that nothing leaves your machine, opening with "pipe this into your shell" undercuts the claim before you reach the second paragraph. Download it, read it, run it.

Hooks are read when a session starts, so start a new one. Then run `spill-guard selftest` and read what it says it could not establish.

**No action is required and no configuration changes.** There is no new subcommand, no new environment read, no change to the coverage log's format or location, and no reason string was rewritten. If you upgraded to v0.3.0, the behavioural change you were warned about there — a coverage failure defers instead of blocking — is unchanged here.

**What you may notice.** Two shapes that produced a coverage record now get a verdict, so if you read `spill-guard coverage` regularly its `for`-loop and `case`-arm lines should stop growing. Nothing that blocked before stops blocking, with one exception in the other direction: a `private-key-block` inside a patch or an encrypted key's `DEK-Info:` block now matches where it did not, so a `Read` of a diff carrying a private key blocks where it previously went through.

## Deprecations

- **The `A3T` arm of `aws-access-key-id` is removed**, with its keyword, its test-table row and its vector. This is a narrowing: a key beginning `A3T` is no longer matched by this rule. The sourcing argument is in **Highlights** and in `rules/README.md`; what settles it is that AWS does not publish the prefix, not that a corpus failed to contain one. It was not settled by agreement with another scanner's ruleset either — `docs/design/brief.md` names gitleaks as a possible origin of these rules, so agreement there would be one list arriving twice.
- **Nothing else is deprecated**, and no subcommand, rule ID, environment read, or output format was removed.

## What it does not read

Each item here is a case where a credential can cross. They are listed because a scanner's gaps are the only part of it a user cannot discover for themselves. v0.3.0 disclosed six inherited cases and added five more; this is every one of them.

| Disclosed in v0.3.0 | v0.4.0 |
|---|---|
| A UTF-8 byte-order mark ahead of a NUL | **Stands.** Undeclared to the decoder, so the buffer falls through and the NUL is read raw. The call proceeds and the person is told in a notice. |
| A binary buffer on `Read` and on a `Bash` operand | **Stands.** The raw match pass is the prompt's alone, on the cost argument: 13 of the 21 binary `Bash` operands in the design corpus are the Claude Code binary, 306 MiB, 36.5 seconds of match loop. |
| A recursive read | **Stands.** A walk reads a different file set from the one the command would send — over one checkout `rg --files` reports 211 where a walk finds 11,815. The call proceeds with nothing scanned and a record. Name the files. |
| A secret synthesized at runtime, other than a bare `env` | **Stands.** Structural: nothing to open at `PreToolUse`, and `PostToolUse` cannot withhold a result. |
| An MCP server's file reader | **Stands, still undriven.** The one member of the reader class nothing here has measured. |
| A command with no reader row | **Stands.** A command absent from the table is scanned as a string and no further. |
| A queued substitution body starts with an empty variable map | **Stands.** `SP=/x; echo $(cat $SP/f)` records where `SP=/x; cat $SP/f` resolves. The honest route is a fix upstream in `claude-workspace-guard` first, ported by inspection, and a tag cannot wait on another repository's merge. |
| A quoted assignment is read as one where bash runs a command | **Stands**, blocked on the same upstream. |
| A `case` arm is read as unconditional | **Closed.** A `case` arm is conditional now, so a variable assigned only inside one is recorded rather than resolved to a path bash may never have used. |
| A `for` loop's variable is poisoned | **Closed.** Bound to its literal list, which is the port upstream already had. |
| The glob table is one machine's shell options | **Stands.** 22 of 22 snapshots here leave `dotglob` unset, so a `.bashrc` that sets it makes every pattern in that machine's tool shell reach hidden files this expansion drops. Whether a hook can find its session's snapshot has to be driven before there is anything to build. |
| A credential-file read through an interpreter, or through `env -0` | **Stands**, and is the stated under-fire rather than a hole to widen into: firing on the careful form would be the defect. |
| `!` bash mode is not a tool call | **Stands.** `PreToolUse` never sees it — over 1,661 transcripts, 62 such entries, 0 carrying a `toolUseID`. Whether `UserPromptSubmit` fires for it is unmeasured and needs a pty. |

There is still no Homebrew tap and no Scoop bucket. Both are designed and neither is built, so a machine with neither `cosign` nor `gh` has no route that verifies for it — the install scripts refuse on such a machine rather than falling back to the checksum, because `checksums.txt` comes from the same place the archive did and answers corruption, not substitution.

## The surface this freezes

Small on purpose, and `0.x` means none of it is promised. **Nothing here is new since v0.3.0** — this release adds no subcommand, no flag, no environment read and no output format.

- **Subcommands:** `hook`, `selftest`, `version`, `coverage`. None takes a flag.
- **Rule IDs, on by default:** `aws-access-key-id`, `github-token`, `github-fine-grained-pat`, `slack-token`, `slack-webhook-url`, `stripe-live-secret-key`, `openai-api-key`, `google-api-key`, `private-key-block`, `jwt`. Two of these changed what they match; none changed its ID.
- **Rule IDs, off by default:** `payment-card`, `us-ssn`, `cn-resident-id`, `ipv4-public`.
- **A finding reports the rule ID, the path, and the byte offset. Never the value, and not a redacted fragment either**, because the refusal text reaches the API as well.
- **Environment:** `SPILL_GUARD_BIN` for the launcher; the binary reads `HOME`, `TMPDIR`, `XDG_STATE_HOME`, `CDPATH`, `GIT_DIR`, `GIT_WORK_TREE` and `GIT_CEILING_DIRECTORIES`. `SPILL_GUARD_OVERRIDE=` is not in this list, because it is a command-position prefix and is never read from the environment.
- **Reason strings**, which the model reads and a script might match on: **unchanged this release.**

## Validation

<details><summary>1,379 test cases across 10 packages, 22 gates each paired with a job that breaks it, and 13 selftest arms of which 5 must allow and 1 must defer</summary>

- `go test ./...` passes 1,379 cases across 10 packages, 277 top-level tests. v0.3.0 shipped 1,267 across 9.
- **22 gates run on every pull request, three more than v0.3.0.** `release-scope` retires a release-scope record when its tag is cut. `release-notes` re-reads a published release body against its notes file, and binds on `main` rather than on a pull request, because while the edit is open the divergence *is* the proposal. `self-scan` requires every tracked file that trips the scanner to be an explicit decision — two corpus regions plus a named list — and its stale-entry check fails on an allowlist entry that no longer matches, so an exemption cannot outlive the thing it excused. `tests.yml` carries 45 jobs: each gate, a mutation control that breaks the property and requires the gate to go red, and one control over `make check` itself.
- **A fourteenth workflow job runs the harness, not the tree.** `prompt-oracle` re-drives `internal/hook/testdata/prompt-oracle.json` — Claude Code's own answer to the `@`-token grammar — against a pinned `claude` binary on every pull request. It needs no credential, because the harness resolves `@` tokens and writes the transcript before it makes an API call. **24 of 24 cases agree at 2.1.261 against a census recorded at 2.1.238**, on darwin/arm64 and linux-x64, so the grammar has not drifted across those releases. Before this, a Go test compared the resolver to the recording on every run and nothing re-took the recording.
- The precision corpus: 13 clean files producing 0 findings, 15 planted files producing exactly one finding each — one new, the `git diff -U14` patch carrying an encrypted PKCS#1 key.
- **The release path's verification has to prove it can reject.** `scripts/check-signature-identity.py` verifies `checksums.txt` and then requires three identities the release was not signed under — a branch, another workflow, a fork — to be rejected **on the identity**. That last clause is the point: an empty `--certificate-identity` also exits non-zero, on `--certificate-identity or --certificate-identity-regexp is required`, so a control reading only the exit status is satisfied by a cosign that never looked at the bundle. `scripts/check-attestation-identity.py` does the same for provenance, reading the certificate subject out of `--format=json`, because `gh attestation verify` prints nothing at all once its output is redirected — exit 0, zero bytes.
- **Those checks run on a pull request, against the last published release.** A branch has no signature of its own to check, so `published-release-verify` asserts about a previous release instead, which is the whole of what a pull request can assert about signing. No published release is a failure and not a skip, because a skipped job reports no check at all and that reads exactly like one that passed.
- Empty supply chain, unchanged: `go.mod` carries no `require` block at all, and the build graph is this module plus the standard library, reaching no `net`, `net/http`, or `os/exec`. Three gates enforce it on the import graph.
- `govulncheck` reports no known vulnerability the build graph calls.
- All five shipped targets cross-compile from one runner: `darwin/arm64`, `darwin/amd64`, `linux/amd64`, `linux/arm64`, `windows/amd64`.
- **What no pull request reaches, and what changed about that.** cosign signing, the provenance attestation and the asset upload still live behind the tag. What is new is that the *verifier* those steps depend on is exercised before the tag rather than first executed on a permanent version number. The signing and upload steps themselves are still first run by this tag.
- **What no gate reaches at all, said here rather than implied:** every transcript measurement in these notes is one machine's, taken by walking `~/.claude/projects/`, and CI cannot re-run any of it.

## Security

No advisory accompanies this release, and nothing here patches a reported vulnerability. What follows is a weakness in this project's own release verification, found and fixed in the same release, disclosed because a user who verified a v0.3.0 download with `gh` got less than the documentation promised.

**Both install scripts passed `--signer-workflow` without a ref.** That flag matches the certificate subject as a prefix, so the bare `<owner>/<repo>/.github/workflows/release.yml` accepted an attestation minted by that workflow at **any ref** — a branch, or a tag other than the one being installed. The `cosign` branch beside it pinned the tag correctly through `--certificate-identity`, and the scripts verify with whichever tool is present, so which check you got depended on which tool your machine happened to have. The release job's own comment said the identity was pinned to this workflow at this tag; that was true of the cosign call under it and not of these two.

Measured against the published v0.3.0 attestation: the bare form exits 0, `@refs/tags/v0.3.0` exits 0, and `@refs/heads/main` exits 1 — so appending the ref is what pins it. Both scripts now do, and both verifiers assert the same string.

**What this was and was not.** Exploiting it would have required an attacker who could already mint an attestation from this repository's release workflow at another ref, and then substitute an archive on this repository's releases. It is a weaker check than documented rather than an open door, and no evidence suggests it was used. It is disclosed at this length because the whole claim of the verification step is that a signature minted somewhere else is rejected, and for `gh` users that claim was broader than what ran.

The rest of the posture is unchanged: no network capability in the build graph, no third-party runtime dependency, no in-band bypass tag, and control characters escaped in every emitted string, since paths and rule descriptions both reach a terminal.

The threat model is the accident — `cat .env`, a `grep -r password`, a stack trace carrying a bearer token. It is not a defense against a user who means it.

## Verifying this release

Every archive is listed in `checksums.txt`, which is signed keylessly into the Sigstore bundle `checksums.txt.sigstore.json`, and each archive carries a SLSA build provenance attestation. `install.sh` and `install.ps1` are listed in `checksums.txt` too, so the script you fetch in order to read it can also be checked:

```
curl -fsSLO https://github.com/karlkfi/claude-spill-guard/releases/download/v0.4.0/checksums.txt
sha256sum --ignore-missing -c checksums.txt
```

`--ignore-missing` is the load-bearing flag: without it `sha256sum -c` fails on every asset you did not download, which reads as a verification failure.

To check authenticity rather than integrity, with either tool — `cosign` needs the bundle downloaded alongside `checksums.txt`, `gh` fetches what it needs itself:

```
curl -fsSLO https://github.com/karlkfi/claude-spill-guard/releases/download/v0.4.0/checksums.txt.sigstore.json
cosign verify-blob --bundle checksums.txt.sigstore.json --new-bundle-format --certificate-identity 'https://github.com/karlkfi/claude-spill-guard/.github/workflows/release.yml@refs/tags/v0.4.0' --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' checksums.txt
gh attestation verify spill-guard_0.4.0_linux_amd64.tar.gz --repo karlkfi/claude-spill-guard --signer-workflow 'karlkfi/claude-spill-guard/.github/workflows/release.yml@refs/tags/v0.4.0'
```

**The `gh` command carries the ref for the reason `install.sh` now does.** Without the `@refs/tags/...` suffix, `--signer-workflow` prefix-matches and accepts that workflow at any ref. **Security** has the measurement.

The provenance also travels as an asset, `spill-guard_0.4.0.intoto.jsonl`, for a consumer with no network path to the attestations API.
