**spill-guard keeps secrets and PII from reaching the API through a Claude Code session.** It scans at the boundary between your filesystem and the model's context — the one a git secret scanner never sees, because a file read into a session is never committed.

> [!WARNING]
> This is a `0.x` release and the surface carries no compatibility promise. Subcommand names, rule IDs, the reason strings, and the shape of a verdict can change in the next minor.

> [!CAUTION]
> **A call v0.2.0 blocked because it could not read it now goes through.** An operand the scanner cannot resolve before the command runs, a file behind an encoding this build does not decode, a scan past its 45-second budget: none of these blocks any more. The hook writes no verdict, your own permission rules run exactly as they would without it, and the gap is written to a log that `spill-guard coverage` reads back. A finding still blocks. So does a read of a credential file and a bare `env`. If you were counting on the old block to stop a `cat $FILE` you had not looked at, that stop is gone, and **Upgrading** says where to look instead.

> [!NOTE]
> The escape hatch is a command-position prefix and has never been an environment variable: `SPILL_GUARD_OVERRIDE=<reason> <command>` on a `Bash` call, read from the inline assignment and never from the environment, and it turns a block into a confirmation rather than an allow. The v0.1.0 and v0.2.0 notes called it an environment variable in their own banners. They were wrong on that word, the code was not, and this note is where it is corrected.

## What v0.3.0 is for

Two things. **Friction that was measured, and coverage that was measured.** Over the week to 2026-09-05, across 100 sessions on one machine, 509 of 540 blocks — 94.3% — were the scanner refusing a call it could not read rather than a call carrying a secret, and after such a block the session got a clean call through within four attempts 99.2% of the time, reading the same tree another way. The block was not withholding the bytes. It charged a turn, and then a person's attention, for a refusal the next call walked around. All 31 content findings in the same window fired inside this repository's own worktrees, on its own corpus fixtures.

So the block on a coverage failure is gone, and what replaces it is a record. A record of a gap is worth something only if the gaps then close, which is the second half: four of the shapes the old block fired on most are now resolved and scanned rather than recorded. Of the 393 refusals measured over 14,868 `Bash` calls in the transcripts where the hook was live, 361 landed on four operand-resolution arms — a variable expanded at run time (135), a directory (96), a relative operand after a `cd` (79), a glob (51). Three of those four arms resolve now. The directory arm stays out on its own argument, below.

The list the v0.2.0 notes committed to is answered case by case at the end, under **What it does not read**.

## Highlights

- **A coverage failure defers and is recorded, instead of blocking.** The hook writes nothing at all — not an allow, because an allow is an opinion that would suppress your own configured rules, and this has none to spend on a call it could not read. The gap goes to two sinks: a line on stderr, which Claude Code stores in the transcript beside the call and shows to nobody, and a capped JSONL log under `$XDG_STATE_HOME/spill-guard/`, or `~/.local/state/spill-guard/` when that is unset. `spill-guard coverage` reads the log back grouped by reason, commonest first, so the shape that costs the most is the first line. What still blocks: a rule match, a bare `env`, and a read of a credential file. What still exits 2: a payload the binary cannot decode at all, which is a broken install and not a scanner failing to read something. 0 of the 540 verdicts in the measured week were that.
- **A read of a credential file is refused on its path alone.** `.env`, `~/.aws/credentials`, `.netrc` and `_netrc`, `.git-credentials`, `~/.docker/config.json`, and a kubeconfig. The shipped set is fourteen high-precision shapes and none of them matches an AWS *secret* access key, a netrc password, a base64 registry auth or a kubeconfig's `client-key-data`, which is what these files hold — driven, `cat .aws/credentials` over such a file exited 0 silent on v0.2.0. Reads only, and only through the readers this knows — the per-command table that decides which token of a `Bash` command is a file: `python3 -c "print(open('.env').read())"` walks straight past it, and the reason says so rather than reading as path protection. The careful form is not refused and is still scanned: `cat .env | cut -d= -f1` has a stage after it. Over 24,381 `Bash` calls and 521 `Read` calls in the seven days to 2026-09-04 the class refused **0** real calls, and 11 of 12 planted ones — the twelfth is `~/.aws/config`, deliberately out. `.claude/settings.json` was the first-named member and the measurement removed it: 29 reads in that week, not one a credential, 26 of them a session reading back a line it had just written.
- **The `Bash` surface resolves four shapes it used to record or refuse.** Two of the four — the `cd` tracker and the variable map — are ports of `claude-workspace-guard`'s resolution, kept structurally identical rather than rewritten; the input redirect and the glob expansion are this repository's own, since upstream never needed the operator and resolves a glob only inside a `for` list. The variable map and the glob expansion were driven against bash 5.3.15 and the output checked in, rather than reasoned about from the manual.
  - **An input redirect's file is scanned.** `cat < deploy.env` exited 0 silent on v0.2.0 where `cat deploy.env` blocked, and `cat < .env` walked past the path refusal the same way — one operator defeating both of this tool's answers. Over 28,187 `Bash` calls in the week to 2026-09-04, 360 segments carry an input redirect, 219 of them on a reader the table knows and 141 on a command with no row, 77 of those `python3`. Driven over every one of the 1,431 calls in that week carrying a bare `<`: 43 moved from allow to deferred, and nothing moved to a block.
  - **A literal `cd` target is followed.** `cd sub && cat x` reads `x` under `sub` and gets a verdict, per segment in order, so `cd a && cat x && cd b && cat y` reads each under its own directory. Followed: a literal target, and the quoted `"$(git rev-parse --show-toplevel)"` and `"$(pwd)"`. Not followed, as upstream: bare `cd`, `cd -`, `popd`, a `$`-bearing target, and a move inside a subshell or a pipeline stage. Of 137 coverage records on this arm over this machine's transcripts, 6 named a target nothing can follow.
  - **A variable the same command assigned a plain literal is substituted.** `SP=/x; tail -30 "$SP/unit.log"` opens `/x/unit.log`. That was the commonest shape on the busiest arm: of the 137 commands recovered behind the variable arm's 135 refusals, 86 assigned a literal earlier in the same string, most of them a session writing its scratchpad path down once and reading a log back from it. Anything that is not a provable literal poisons the name and leaves the operand where it was, recorded. An and-or list is read the way bash runs it: an assignment reached through `&&` counts while everything before it is certain to have exited 0, which is 220 of the week's 655 conditional assignments sitting directly after `cd "$(git rev-parse --show-toplevel)" &&`, and one reached through `||` does not.
  - **A glob is expanded to the files bash would send.** `grep -n pat internal/hook/*.go` opens every file it names, under bash's default options, which 22 of 22 shell snapshots on this machine restore: a leading `.` is matched only by a literal `.`, and the literal word is included whenever a file by that name exists, because bash passes an unmatched pattern through and `app/[id]/page.tsx` is a filename. Anything earlier in the string that could change those options — `shopt`, `set -f`, a `GLOBIGNORE` assignment, `eval`, `source` — puts the pattern back on the record, and a brace expansion is recorded rather than passed through as a file that does not exist. 135 operands in 95 measured calls get a verdict where they had a record.
- **Rules run at their keyword positions.** Eight of the ten enabled rules open on `\b`, an empty-width op that leaves `regexp` no literal prefix to skip towards, so v0.2.0 ran the NFA over every byte to arrive back at positions the prefilter already had. Seven of the eight now run one anchored attempt per hit. Over this repository's own text, which names every keyword the set gates on, the shipped ruleset went from 7.12 MB/s to 32.09 MB/s. A differential over 280,406 buffer-and-rule pairs compared 824 findings between the two paths with 0 disagreements. The 500 MiB fixture that hit the 45-second budget on v0.2.0 now denies on its rule at 14.9 to 17.7 seconds.
- **`private-key-block` reads an indented PEM block.** The rule required the base64 body to begin a line, so a key pasted into a Kubernetes secret's block scalar or an indented Markdown fence matched nothing. Over 239,670 files of third-party Go source, 5.05 GiB, the widening newly matches 3 blocks in 1 file, all three indented `client-key: |` scalars, and no new false positive. The clean corpus stays at 0.

## Upgrading

Both halves move. The binary is what changed; the plugin manifest version is what makes `claude plugin update` deliver it.

```
curl -fsSLO https://github.com/karlkfi/claude-spill-guard/releases/download/v0.3.0/install.sh
sh install.sh
claude plugin update spill-guard
```

Windows, in PowerShell:

```
curl.exe -fsSLO https://github.com/karlkfi/claude-spill-guard/releases/download/v0.3.0/install.ps1
powershell -ExecutionPolicy Bypass -File install.ps1
```

Two steps rather than one on purpose. The one-liner that pipes a remote script into a shell works, and for a tool whose whole pitch is that nothing leaves your machine, opening with "pipe this into your shell" undercuts the claim before you reach the second paragraph. Download it, read it, run it.

Hooks are read when a session starts, so start a new one. Then run `spill-guard selftest` and read what it says it could not establish: it has 13 arms now, and one of them reports `deferred` rather than `ok` on a block, because that is the arm whose whole value is that a deferral is visible.

**What you will stop seeing.** The refusal that opened *Nothing scanned this call for secrets* and ended in a block. On v0.2.0 that was 94.3% of what this tool said to anyone. Its subject — an operand carrying a `$`, a glob, a directory, a relative path after a `cd`, a file behind a byte-order mark this build does not decode — now proceeds with no verdict from this hook, and the reason goes to the log.

**Where it went.** Run `spill-guard coverage`. The first line is the log's path, the next is a count and a date range, and then one line per reason, commonest first, with its share. Each is a call that proceeded with nothing scanned. They are not findings: a rule that matched would have stopped the call and is not written there. The log is state and not configuration — delete it and nothing changes — and it rotates at 4 MiB into one older generation, so it is bounded at 8 MiB and needs no pruning.

**If you ran `go test` on a v0.2.0 checkout**, your log already holds entries that are not yours: the suite wrote its fixture reasons into the real state directory, and on one machine 126 of the first 180 records were temp-dir paths from test runs. The suite is isolated now. Delete the log once and it starts clean.

**If you wrote a `.claude/spill-guard.json`**, it never did anything and still does not. The shipped loader never read it — the code path that would have honoured it had no caller outside two test files — and it is retired rather than finished, because a file under the project root that turns a rule off is one the model can write. **Deprecations** has the rest.

**One reason string a script might have matched on has moved.** The directory refusal's second clause read *this reads files rather than walking them*, which with `grep -r` in the command read as a claim about `grep`. It now names its subject: *this scanner reads files rather than walking a tree*. Nothing here promises reason-string stability, and this is the release where two of them changed.

## Deprecations

- **The project ruleset at `.claude/spill-guard.json` is retired.** It was designed, described in five places, and never read by the shipped loader, so nothing changes at runtime and nothing warns — there is no file to warn about. A precision complaint is answered by changing the shipped set in a pull request somebody reviews, and restoring a second source now takes a reviewed diff rather than a token somebody passes. Every page that described it is gone.
- **Nothing else is deprecated**, and no subcommand, rule ID, or environment read was removed.

## What it does not read

Each item here is a case where a credential can cross, and all but two of them are measured — those two say so. They are listed because a scanner's gaps are the only part of it a user cannot discover for themselves. The v0.2.0 notes disclosed six; here is each, and what follows them is what this release added to the list.

| v0.2.0 disclosed | v0.3.0 |
|---|---|
| A UTF-8 byte-order mark ahead of a NUL | **Stands.** Undeclared to the decoder, so the buffer falls through and the NUL is read raw. The call proceeds and the person is told in a notice. Nothing new here, since v0.2.0 already allowed it; the deferral change touched the *declared* arm, which was blocking and now records. |
| A binary buffer on `Read` and on a `Bash` operand | **Stands.** The raw match pass is the prompt's alone, on the same cost argument: 13 of the 21 binary `Bash` operands in the design corpus are the Claude Code binary, 306 MiB, 36.5 seconds of match loop. |
| A recursive read | **Stands, and now defers rather than refusing.** `grep -rn pat docs/` names a directory, and a walk reads a different file set from the one the command would send — over one checkout `rg --files` reports 211 where a walk finds 11,815. On v0.2.0 that was a block; now the call proceeds with nothing scanned and a record. `grep -rn pat docs/*` expands to the entries and meets the same answer for the directories among them. Name the files. |
| A secret synthesized at runtime, other than a bare `env` | **Stands.** Structural: nothing to open at `PreToolUse`, and `PostToolUse` cannot withhold a result. |
| An MCP server's file reader | **Stands, still undriven.** The one member of the reader class nothing here has measured. |
| A command with no reader row | **Stands.** A command absent from the table is scanned as a string and no further — 141 of the 360 input redirects measured this release sit on one, 77 of them `python3`, and the same cap holds the credential-path refusal to the readers it knows. |

What this release adds to the list, because a resolver that resolves more has more edges:

- **A queued substitution body starts with an empty variable map and inherits a lost directory.** `SP=/x; echo $(cat $SP/f)` records where `SP=/x; cat $SP/f` resolves, and a `cd sub && echo \`cat x\`` defers rather than reading `x` under `sub`. 11 of the 137 `cd` records carried a substitution after the move.
- **A quoted assignment is read as one where bash runs a command.** `'SP=/x'; cat $SP/f` is, to bash, a command it cannot find followed by a read of the environment's `$SP/f`; the lexer strips the quotes and this resolves `/x/f`. Bounded: the unresolved form already proceeds unscanned with a record, so the divergence trades a record for a scan of the wrong path, and the same bytes cross either way. The same lexer makes `cat "*.env"` expand where bash would open one file named `*.env`; every file bash would send is in that set, and files it would not are too.
- **A `case` arm is read as unconditional**, so `case x in y) P=/case;; esac; cat $P/f` resolves `/case/f` where bash may never have assigned it. 19 `case` arms in the measured week assign a variable, 9 of them expanded later.
- **A `for` loop's variable is poisoned**, so `for f in a b; do cat "$f"; done` records both. Upstream resolves it; the port does not yet.
- **The glob table is one machine's shell options.** 22 of 22 snapshots here leave `dotglob` unset, so a `.bashrc` that sets it makes every pattern in that machine's tool shell reach hidden files this expansion drops.
- **A credential-file read through an interpreter, or through `env -0`.** Both are the stated under-fire: the path refusal stops where the reader table stops, and the `env` refusal is the bare form only, because firing on the careful form would be the defect.
- **`!` bash mode is not a tool call.** Typing `!cat ~/.aws/credentials` runs the command locally and puts the output in front of the model, and `PreToolUse` never sees it: over 1,661 transcripts, 62 such entries, 0 carrying a `toolUseID` and 0 preceded by an assistant `tool_use`, against 143,678 model-issued `Bash` calls found by the same walk. Whether `UserPromptSubmit` fires for it is unmeasured and needs a pty the harness has refused three times.

There is still no Homebrew tap and no Scoop bucket. Both are designed and neither is built, so a machine with neither `cosign` nor `gh` has no route that verifies for it — the install scripts refuse on such a machine rather than falling back to the checksum, because `checksums.txt` comes from the same place the archive did and answers corruption, not substitution.

## The surface this freezes

Small on purpose, and `0.x` means none of it is promised. What is new since v0.2.0 is marked.

- **Subcommands:** `hook`, `selftest`, `version`, and **new** `coverage`. None takes a flag, and `coverage` ignores whatever follows it — `spill-guard coverage --help` prints the summary.
- **`coverage` exit codes**, new: 0 with the summary, and 0 with a two-line message when there is no log yet, which is the good case. 1 when the state directory cannot be resolved or the log cannot be read.
- **The coverage record**, new: one JSON object per line, fields `time`, `event`, `tool`, `reason`, at `$XDG_STATE_HOME/spill-guard/coverage.jsonl` or `~/.local/state/spill-guard/coverage.jsonl`, mode `0600`, rotated once at 4 MiB to `coverage.jsonl.1`. The reason names the path of what went unread and none of its bytes.
- **`selftest`'s per-arm result column gains `deferred`**, beside `blocked` and `allowed`, on the one arm whose want is a deferral.
- **Environment:** `SPILL_GUARD_BIN` tells the launcher where the binary is. The binary itself reads `HOME`, `TMPDIR`, `XDG_STATE_HOME`, and — new, for following a `cd` — `CDPATH`, `GIT_DIR`, `GIT_WORK_TREE` and `GIT_CEILING_DIRECTORIES`. Each is tested for being set or compared against as a path; none is stored, logged or emitted, and `PRIVACY.md` is now generated from the source and gated, so that list cannot drift from the binary silently. `SPILL_GUARD_OVERRIDE=` is not in this list, because it is not read from the environment.
- **Rule IDs, on by default, unchanged:** `aws-access-key-id`, `github-token`, `github-fine-grained-pat`, `slack-token`, `slack-webhook-url`, `stripe-live-secret-key`, `openai-api-key`, `google-api-key`, `private-key-block`, `jwt`.
- **Rule IDs, off by default, unchanged:** `payment-card`, `us-ssn`, `cn-resident-id`, `ipv4-public`.
- **A finding reports the rule ID, the path, and the byte offset. Never the value, and not a redacted fragment either**, because the refusal text reaches the API as well.
- **Reason strings**, which the model reads and a script might match on: one new body, for the credential-path refusal; the coverage-failure body rewritten, since it said a scanner that cannot run blocks and that is no longer true; the budget body rewritten the same way; and the directory refusal's subject named. None of them names the override, and the tests that hold that line still hold it.

## Security

No advisory accompanies this release. What it carries is the posture, unchanged: no network capability in the build graph, no third-party runtime dependency, no in-band bypass tag, and control characters escaped in every emitted string, since paths and rule descriptions both reach a terminal.

Two changes in this release harden trust handling without patching a reported vulnerability. The credential-path refusal closes a class the ruleset never could, and the retired project ruleset removes the one code path that would have honoured a model-writable file. The deferral change moves the other way and is disclosed as such in the banner: a call the scanner cannot read is now your permission rules' decision and not this hook's.

The threat model is the accident — `cat .env`, a `grep -r password`, a stack trace carrying a bearer token. It is not a defense against a user who means it.

## Verifying this release

Every archive is listed in `checksums.txt`, which is signed keylessly into the Sigstore bundle `checksums.txt.sigstore.json`, and each archive carries a SLSA build provenance attestation. `install.sh` and `install.ps1` are listed in `checksums.txt` too, so the script you fetch in order to read it can also be checked:

```
curl -fsSLO https://github.com/karlkfi/claude-spill-guard/releases/download/v0.3.0/checksums.txt
sha256sum --ignore-missing -c checksums.txt
```

`--ignore-missing` is the load-bearing flag: without it `sha256sum -c` fails on every asset you did not download, which reads as a verification failure.

To check authenticity rather than integrity, with either tool — `cosign` needs the bundle downloaded alongside `checksums.txt`, `gh` fetches what it needs itself:

```
curl -fsSLO https://github.com/karlkfi/claude-spill-guard/releases/download/v0.3.0/checksums.txt.sigstore.json
cosign verify-blob --bundle checksums.txt.sigstore.json --new-bundle-format --certificate-identity 'https://github.com/karlkfi/claude-spill-guard/.github/workflows/release.yml@refs/tags/v0.3.0' --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' checksums.txt
gh attestation verify spill-guard_0.3.0_linux_amd64.tar.gz --repo karlkfi/claude-spill-guard
```

The provenance also travels as an asset, `spill-guard_0.3.0.intoto.jsonl`, for a consumer with no network path to the attestations API.
