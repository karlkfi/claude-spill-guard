> **Upgrade if you are on v0.4.0.** A quoted word made only of shell operator characters — `cat ';' f` — cut the command in two before the scanner read it, so every operand after that word went unscanned. No verdict, no coverage record, exit 0. The file it read had an ordinary name.

One fix, in the shell segmentation, and it closes two things.

**A file the command reads, that nothing scanned.** A word spelled entirely from the characters `shlex` groups as punctuation — `;()<>|&` and a newline — has the *text* of an operator and is not one when quotes made it a word. Reading it as a separator ended the segment there: `cat` kept no operands, and `f` was read as a command name with no reader row, so neither file was opened. **No file named `;` has to exist** for this to bite. The split happens at tokenization and `cat` continues past the operand it could not open, so the credential file is ordinarily named and what is unusual is one quoted operator-only word anywhere in the command.

**The escape hatch was armable from a position that is not command position.** `cat f ';' SPILL_GUARD_OVERRIDE=x` downgraded a block to a confirmation, because the quoted `;` opened a fresh segment and a *trailing* override fell into env-prefix position. The design rules the hatch to command position by name, so this is the narrower half in effect and the sharper half in kind.

Measured on built binaries either side, in a directory holding only `f` with a planted AWS key:

| command | v0.4.0 | v0.4.1 |
|---|---|---|
| `cat ';' f`, no file named `;` | no verdict object, exit 0 | **deny**, naming `aws-access-key-id` |
| `cat f ';' SPILL_GUARD_OVERRIDE=x` | ask | **deny** |
| `cat f` — control | deny | deny |
| `cat 'x;y' f` — control | deny | deny |
| `cat f SPILL_GUARD_OVERRIDE=x` — control | deny | deny |
| `SPILL_GUARD_OVERRIDE=x cat f` — control | ask | ask |

The controls are the point rather than decoration: two of them move in opposite directions across the hatch fix, and `'x;y'` says the mechanism is the split rather than the quoting.

**Two sites, and the obvious one alone does not fix the headline case.** A single-character run is byte-identical whether it is decomposed or skipped, so a quoted `;` reaches the segmenter's own vocabulary tests intact; patching only the operator-run splitter fixes `cat ';;' f` and leaves `cat ';' f` splitting in two. Ported from `claude-bouncer` #138, which converts three sites in `workspace-guard`; there are two here, because this reads the hatch off a segment rather than re-scanning raw tokens.

## The precision risk, and who measured it

This change makes the segmenter treat *more* tokens as words, so what it risks is something that should segment no longer doing so — and the author of a change is the worst person to choose its controls. An independent session measured it over **155,000 unique `Bash` command strings** from real transcripts, diffing the file set the hook resolves between binaries built either side: **154,969 file sets identical, 27 gain files, 4 lose, 0 both.** All four losses are non-file tokens — `--`, `-e`, `$b`, `\n`, and a `git show <rev>:<path>` pseudo-path — so no real path stops being scanned. Every gain is a real path: `grep -c ';' CLAUDE.md` now scans `CLAUDE.md`, and `find … -exec … \;` keeps its `-exec` clause.

**No gate re-runs that measurement**, and it is the only evidence for the precision direction of this change. Said here rather than implied.
