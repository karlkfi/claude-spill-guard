# A tee to an absolute file after env copies the dump past the refusal

`env > vars.txt` is refused, because a redirect to a file is not read as a filter.
`env | tee /abs/path/vars.txt | cut -d= -f1` is not refused, and it writes the same dump to the same kind of file.
Read through `envDumped` on the branch that closed Q258, at `3a93067`, with the path absolute under a session scratchpad: no refusal.
The relative spelling, `env | tee vars.txt | cut -d= -f1`, is refused on that branch, and a test pins it.

The split comes from `copiedAround` in `internal/hook/grep.go`, which `lastInPipeline` now calls.
For a grep, a copy to a regular file is allowed when nothing later in the string can read it, because a later call that reads the file is scanned then.
That argument does not carry over to `env`.
The values in the dump match no rule, so a later `cat vars.txt` scans the file, finds nothing, and sends it.
By the same reading, not driven, a guarded path copied out under an unguarded name leaves the class behind: `cat .env | tee /abs/copy.txt | cut -d= -f1`.
A relative name is refused only because `envDumped` runs ahead of the directory tracker and passes the directory as unknown, which is an accident of order, not a decision.

A regex over the text of 309,504 real `Bash` calls, swept on 2026-11-27, found no bare `env`-family dump piped straight into a `tee`, so refusing this would cost nothing measured.
An awk or sed stage writing the dump to stderr is a separate residual, and a stated under-fire rather than part of this row: Q257 closed it for the grep filter with a pass-through list that only the grep caller reads, because the same list would refuse `env | grep … | sed 's/=.*/=<set>/' | sort`, which is the careful form.

**Done** when a copy of an `env` dump or a guarded read to any regular file, absolute or relative, is refused, and the grep filter's file allowance is unchanged.
