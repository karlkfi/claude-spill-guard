# ~390 MiB of keyword-bearing text reaches the timeout fail-open

[Q120](Q120.md) leaves one thing open by name: how big "big enough" is. It is
about **390 MiB**, and the number belongs to the call rather than to any file in
it.

Driven 2026-09-03 against a binary built from this tree, timing the hook process
-- the quantity [Q96's kill was measured against](../design/README.md#the-third-shape-is-a-timeout-and-it-is-the-one-this-repo-configures),
60.38s wall at `timeout: 60`. `Read` surface, warm page cache, Apple M5 Max,
Go 1.26.5. Every fixture carries the planted key from
[`testdata/corpus/planted/aws-access-key-id.env`](../../testdata/corpus/planted/aws-access-key-id.env)
at its midpoint, so a run that finishes has to emit a real deny rather than an
empty allow.

| Size | Wall | What the hook did |
|---|---|---|
| 128 MiB | 19.567s | blocks, names `aws-access-key-id` |
| 350 MiB | 53.154s | blocks |
| 380 MiB | 58.297s | blocks |
| 400 MiB | 60.749s | **killed at 60s, call proceeds** |
| 440 MiB | 66.853s | **killed at 60s, call proceeds** |

The 380 MiB row is the control, and without it the rest is worth nothing: a
drive that overran and a drive that never started are the same observation from
outside. That one finishes 1.7 seconds inside the budget and denies. Rate is
flat at 6.52-6.58 MiB/s across the bracket and 6.7 MiB/s at 16 MiB, so the
crossing interpolates to 393.9 MiB rather than being sampled at it.

#92's session re-derived it independently on its own fixture and got 6.8 MiB/s
and a crossing near 410 MiB, so read the number as 390-410 rather than as three
significant figures. That reading times `internal/scan` where these time the
whole hook process, which makes these the conservative pair -- though by very
little here, since the read and the startup together are 0.043s of the 58.297s.

The arithmetic this replaces -- 60 seconds over the 17.4 MiB/s aggregate #92's
session measured across 1,414.7 MiB of real binaries, giving 460 MiB to 1 GiB --
was high by 1.2x to 2.6x. Not because the 17.4 was wrong; that figure is not
re-taken here. An aggregate over real files averages in the files where almost
no rule ran.

## Size is not the axis. The number of rules clearing the prefilter is

Measured at 64 MiB, same surface, min of three:

| Buffer | Rate | 60s buys |
|---|---|---|
| binary -- a NUL in the sniff window | 9746 MiB/s | nothing stops it; 380 MiB is 0.039s |
| text, no rule clears the prefilter | 1055 MiB/s | ~62 GiB |
| text, one rule clears | ~50 MiB/s | ~3 GiB |
| text, all ten clear | 6.5 MiB/s | ~390 MiB |

So the file that reaches the fail-open is not the one that looks dangerous. A
buffer of NUL bytes is free, because the sniff skips it. What is expensive is
ordinary text that happens to carry the ten literals, **one occurrence each** --
that is what the 390 MiB fixture holds. A log with one `eyJ`, one `AKIA` and one
`sk-` somewhere in it costs the same as a file made of secrets.

## Eight of the ten rules pay a full pass, and two are free

Per rule at 64 MiB, with `regexp.Regexp.LiteralPrefix` beside the time:

| Rule | Prefix the engine can skip to | Full pass |
|---|---|---|
| `slack-webhook-url` | `https://hooks.slack.com/services/T` | 0.001s |
| `private-key-block` | `-----BEGIN ` | 0.001s |
| the other eight | none | 1.18-1.29s each |

The two cheap ones are the only shipped patterns that do not open on `\b`. Go's
`regexp` computes a literal prefix by walking the program from the start, an
empty-width op stops that walk, and without a prefix there is nothing to memchr
towards -- so the whole buffer goes through the NFA. Falsified rather than read
off the source: the same three patterns with the leading `\b` removed acquire
prefixes `gh`, `AIza` and `eyJ` and run **1175x to 1186x** faster on the same
buffer. Measured on Go 1.26.5; it is one implementation's optimizer and not
something RE2 promises.

Deleting the `\b` is not the repair; it would match inside `xghp_...`. The lever
it points at is a match loop driven by the prefilter's own hit positions instead
of by the whole buffer, and that is a different item with its own cost -- a
buffer dense in one literal is slower that way, not faster. Filed here because
it is the largest single term in the number above, not because this row proposes
it.

## The budget is per call, and `scanCall` loops over every buffer

One `Bash` call, `cat` over identical 128 MiB files:

| Files | Total | Wall |
|---|---|---|
| 1 | 128 MiB | 19.513s |
| 2 | 256 MiB | 38.886s |
| 4 | 512 MiB | 78.130s |

Nothing here is near 390 MiB on its own. That matters for the shape of the
cheaper half of Q120: **a per-file size cap does not bound a call.** The budget
has to be over the bytes the call adds up to.

The cost is also decoupled from what the command would read. `head`, `tail`,
`wc` and `grep` are all in [`internal/readers`](../../internal/readers/spec.go),
and over the same 128 MiB file they cost what `cat` costs: `tail -5` 19.321s,
`head -1` 19.826s, `wc -l` 20.005s, `cat` 19.800s. Reading five lines and
matching the whole file are the same call.

## v0.1.0 is the same number, and #92 no longer changes who it applies to

`internal/scan`, `internal/hook` and `rules/spill-guard.json` are byte-identical
between `v0.1.0` and `main`. Confirmed by measurement rather than by the diff:
the same 380 MiB fixture through binaries built from `v0.1.0`, `main` and #92 at
`df0b3d3` gives 57.721s, 58.805s and 58.324s.

#92 does not move the number, and as of `e53f99d` it no longer moves the
population either. Its branch moved twice while this was being measured, so both
readings are named by head. One 380 MiB fixture with a NUL at byte 3 and the
same planted key, prompt surface:

| Build | Wall | Verdict |
|---|---|---|
| `main` | 0.039s | allowed, with the notice |
| #92 at `df0b3d3` | 58.190s | **blocks**, names the rule |
| #92 at `e53f99d` | 0.039s | allowed, with the notice |
| #92 at `e53f99d`, a 16 MiB fixture | 2.482s | **blocks**, names the rule |

At `df0b3d3` the raw pass was unbounded, which put binary `@` targets on this
same crossing -- coverage below it, and above it strictly worse than the skip it
replaced, since `main` answers in 39 ms with a notice a person can act on where
a killed hook writes nothing at all. `e53f99d` caps the raw pass at 32 MiB,
sized against the rate above; #92's session then drove that limit at 4.300s for
a keyword-rich 32 MiB buffer, a fourteenfold margin inside the timeout.

The fourth row is the control, and it is the one the cap needs: under the limit
the coverage is still there, so the allow above it is a bound rather than the
entry point being switched off. `Read` and `Bash` keep the skip on every head,
and the cap does not reach the text path -- the 380 MiB text fixture is 57.488s
at `e53f99d`. The branch has since moved to `3487a0f`, whose diff is comments
and prose only, so every reading here still describes it.

## The gap is not in v0.1.0's disclosed list

[`docs/releases/v0.1.0.md`](../releases/v0.1.0.md) enumerates six cases under
*What it does not read*, opening with "Every item here is measured, and each one
is a case where a credential can cross." This is a seventh, and it is not the
same shape as the six: every allow in that list carries a notice naming the
buffer. This one carries nothing, because the process is killed before it can
write. Whether the notes owe a bullet, and whether that is worth a patch tag or
waits for v0.2.0, is a release call this row does not take.

## What this does not cover

- **Nothing drove a real Claude Code session at the crossing.** The wall time is
  the hook process's; that Claude Code kills it at 60 seconds and lets the call
  through is Q96's measurement, not a second observation of the two together.
  [Q94](Q94.md) established a credential-free `claude -p` route that fires
  `UserPromptSubmit`, so the end-to-end drive is buildable and was not built.
- **One machine, and the number scales with single-core speed.** 390 MiB is an
  M5 Max. A budget picked against this alone is picked against the fastest
  machine anyone will run it on, which is the wrong end. Retiring that is the
  benchmark Q120 already says its budget has to be picked against, and the
  design's four benchmarking rules -- real heterogeneous files, no repeated
  chunk, match counts reconciled first, fixed cost measured separately -- are
  what it owes. The fixtures here are synthetic and non-repeating, which meets
  the second rule and not the first.
- **Warm page cache.** At 380 MiB the read plus sniff is 0.039s, so a cold read
  cannot move the crossing by much -- but that bound is reasoned from the warm
  figure and device throughput, not measured cold.
- **Reachability is bounded, not established.** The two populations reachable
  from here are small: nothing outside `.git` in this worktree exceeds 5 MiB, and
  the largest `.jsonl` under `~/.claude/projects` on this machine is 35.4 MiB.
  Neither comes near 390 MiB. Whether a 400 MiB log or dataset is ordinary in
  the trees this runs against is not something either census answers.
- **Content within "text" was varied over three shapes, not sampled.** Rare
  alphabet, full alphabet, and dense near-matching candidates. Real prose,
  minified JavaScript, CSV and JSON were not measured, and match density does
  move the rate -- a buffer with a JWT-shaped token every 512 bytes ran at 35.5
  MiB/s where the same single rule over a sparse buffer ran at 52.6.
