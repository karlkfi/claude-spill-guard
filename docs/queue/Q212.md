# A cd in a piped brace group or a function body is followed past it

`{ cd w; cat x; } | cat; cat x` and `f() { cd w; }; cat x` both read `./x` in
bash and both are scanned against `./w/x`. With the key in `./x` and clean text
in `./w/x`, both exit 0 with no verdict and nothing on stderr. Driven
2026-10-25 on binaries built from `origin/main@9f0fbdc` and from the Q201
branch, with bash 5.3.15 under `env -i bash --norc --noprofile -c` reading the
key in both:

| command | key in | bash reads the key | `main` | Q201 branch |
|---|---|---|---|---|
| `{ cd w; cat x; } \| cat; cat x` | `x` | yes | allow | allow |
| `f() { cd w; }; cat x` | `x` | yes | allow | allow |

The segmenter reads a `(` as a subshell and nothing else. bash also runs a
`{ … }` group, a loop, an `if` or a `case` in a child shell when it is piped
or backgrounded as a whole, so the `cd` inside never reaches the segment
after the pipeline. A function definition runs none of its body, so a `cd`
there moves nothing until the function is called. Both are followed today
as though they ran in the current shell, so the operand after them is
resolved against a directory bash never entered.

Upstream scopes both in `split_groups` in
`plugins/workspace-guard/scripts/bash-workspace-guard.py`: a compound piped or
backgrounded as a whole gets a scope numbered like a `(` (its Q272), and a
function body gets an `(n, name)` scope (its Q265). The Q201 port took the `(`
half of the same function (its Q173) and none of these, so this is a port
and not a design. The `lastpipe` arm beside them needs nothing: it marks a
last pipeline stage as possibly the current shell, and this port already loses
the directory at every pipeline-stage `cd`.

A function that is *called* after its definition is the other half of Q265,
and upstream answers it by losing the directory at the call
(`calls_cd_function`). Port both or neither: a body scope with no call rule
turns `f() { cd w; }; f; cat x` from a scan of the wrong file into a scan of a
different wrong file.
