# A reason that names a command is double-escaped by the verdict layer

`internal/hook/bash.go` formats an operand refusal with `fmt.Errorf("in the %q
here, %w", command, err)`, and the verdict layer then applies its own `%q` to
the whole reason. The quotes the inner one added are escaped by the outer one, so
what reaches a reader is:

    ... could not be completed: "in the \"grep\" here, a file operand names a
    directory, and this reads files rather than walking them, so what that
    operand would send was not read -- name the files instead". A scanner ...

Driven on a binary built from this branch, piping a `PreToolUse` payload for
`grep -rn pat sub` with a real working directory into `spill-guard hook` and
reading `permissionDecisionReason` out of the decision object. Pasted from that
output rather than typed -- the first draft of this row hand-wrote the
backslashes and doubled them, which in a row about escaping is the whole
failure it describes.

## Why it is a row rather than a fix in the PR that surfaced it

The nesting is not new. `in the %q here` is at `internal/hook/bash.go:125` on
`origin/main`, and the verdict layer's `%q` is on `main` too, so every refusal
naming a command has read this way since the Bash surface landed.

What changed is the traffic. The directory refusal is the case a user actually
meets — 7.1% of the calls that carry a reader operand, a floor rather than a
rate — so a wart that used to sit on rare refusals is now on the most-met one.
Q95 settled that the refusal stays, so this is not waiting on it and the traffic
is not going away.

## What makes it awkward to fix

Both `%q` verbs are load-bearing and neither is obviously the one to drop.

- The inner one escapes a **caller-derived** string. `command` is a key of the
  reader table, a closed set this repo authored, so it is safe to name — but
  `bash.go` quotes it rather than trusting that, and the argument for quoting is
  the same one `CLAUDE.md` makes under *escape control characters in every
  emitted string*.
- The outer one escapes the assembled reason for the same rule, and it is what
  keeps a C0 or bidi override out of a terminal.

So the fix is not "delete one" — it is deciding where the escaping boundary is,
which is a verdict-layer question touching every reason rather than this one.

Worth checking against [Q89](Q89.md) when either is picked up: that row is about
which reasons interpolate caller-controlled text, and this is the rendering half
of the same inventory.
