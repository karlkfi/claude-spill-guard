# The reader spec that turns a Bash segment into file operands

[`internal/bash`](../../internal/bash/) splits a command string into the simple
commands it runs and hands back each one's tokens and redirect targets. It says
nothing about which of those tokens is a path. `cat a b` has two file operands;
`grep pat f` has one, and the token before it is a pattern; `tar -C dir -xf
archive` has an operand behind a flag that takes a value. Deciding that is a
per-command table, and nothing in the repository has one.

## The seam this sits in, which reads as covered

[Q50](Q50.md) says of the `Bash` event that what gets scanned is "the command
string plus the resolved file operands of the common readers", and attributes
that resolution to the segmentation port — which delivered segmentation and not
the table. So the work is named in one row as belonging to another, and the
other's title, body and design-doc line all say *segment parsing*. Read either
row alone and the gap is invisible; that is the shape a completed row leaves
behind when its title was wider than its body, and it is the same shape Q50's
own "Why this row exists at all" section describes happening to Q8.

## What it has to do

**Port the table, do not invent it.** `claude-workspace-guard` carries it as
`SPEC` with `_split_args` and `files_in_command` beside it, in
`plugins/workspace-guard/scripts/bash-workspace-guard.py`. The same argument
that made the segmentation layer a port applies one layer up and applies harder:
a spec entry that names the wrong argument position produces a scanner that
reads the wrong file, reports clean, and looks like it ran. Take the upstream
entries and say at each site where this repo's question differs from theirs.

**The question does differ, and in one direction.** workspace-guard asks *which
files does this command touch*, including writes; this asks *what content is
about to leave the machine*, which is reads. A `cp inside outside` is an
offender there and is not a spill here. So the port is the table and the
positions, and the read/write split is this repo's own — which is exactly the
kind of divergence that has to be written down at the entry rather than left for
someone to infer from behaviour.

**Fail closed on what it cannot resolve.** A `$VAR` operand, a relative path
after an untrackable `cd`, a glob: none of these can be read, and a scanner that
skips them reports a safety it is not providing. Blocking with a reason is the
repo's rule and the sibling guards' `expand`/`untracked` categories are the
shape of the answer.

**The recursion is this row's, and so is its depth cap.** A `$(…)` body holds
commands, and `CommandSubstitutions` returns the outermost ones for a caller to
re-scan. Nothing drives that loop yet. Upstream caps it at 25
(`MAX_SUBST_DEPTH`), which is a backstop against unbounded work on a
pathological input rather than a limit anyone reaches, and it belongs with the
driver rather than with the scanner — which is why the port left it out.

**A heredoc body is content, not an operand.** `StripHeredocBodies` already
hands the bodies back (`Heredocs.Expanded`, `Heredocs.Unterminated`), and a
`cat <<EOF` carrying a key is the shape a model writes without meaning to. It is
the one input to this row that needs no path resolution at all, and the one most
likely to be forgotten because it is not a file.

## Why it is not part of the segmentation row

The two fail differently. Segmentation fails silently in both directions and is
defended by agreeing with an upstream, byte for byte, over a fuzz corpus. A
reader spec fails by naming the wrong argument, which no differential against
workspace-guard can catch, because its answer to `cp` is deliberately not this
repo's. It needs cases of its own.
