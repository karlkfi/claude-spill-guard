# A UTF-8 byte-order mark is a declaration `decode` does not read

`internal/scan`'s decode stage has three arms: the UTF-32 marks, the UTF-16
marks, and a default that reads raw bytes. `EF BB BF` — the UTF-8 signature,
from the same Unicode registry as `FF FE` — matches none of them, so a buffer
carrying it falls to the default, its NUL is read raw, and it returns
`SkippedBinary`, which `internal/hook` allows in silence.

So a file that declares an encoding and holds a credential can cross with
nothing in the transcript. It is the shape Q91 closed for UTF-16 —
that row is completed and gone, and its reasoning is in
[`docs/design/README.md`](../design/README.md) —
and it is still open for the mark Windows tooling writes most: PowerShell 7's
`Out-File -Encoding utf8BOM`, Notepad, and Visual Studio.

## Measured, four times, by four sessions

Found while reviewing Q91. Driven end to end on a built binary, `PreToolUse` on
`Read`, with the key taken from `testdata/corpus/planted/` so it survives
validation:

| Buffer | Verdict |
|---|---|
| `EF BB BF` + `# notes\n\0` + an AWS-shaped key | **allowed**, empty stdout |
| the same without the NUL — *the control* | denies, names `aws-access-key-id` |
| no mark + `\0` + the same key | allowed — the documented binary skip |

Two readings make this a measurement rather than an absence:

- **The control's offset moves by exactly three.** It denies at byte 29 with the
  mark and 26 without it. The mark stays in the buffer and is scanned as
  ordinary content, which is what having no arm looks like from outside
  `internal/scan` — stronger evidence than a `git grep` for `EF BB BF` finding
  nothing, which is how it was first noticed.
- **A UTF-8-marked buffer lands where an unmarked one does.** The third row is
  the one that fixes the reading: the mark buys the buffer nothing at all, so
  `decode` never reads it rather than reading it and deciding against it.

**Every arm exits 0, both denials included.** The discriminator is the `deny`
object on stdout, never the exit code. A re-run that tests `rc -eq 2` reads all
of them as allows and concludes the controls are dead — the same confusion this
repo's launcher bug turned on.

## Growing a third arm is not obviously the fix, and the count is the weakest reason

Three arguments, weakest last, because the order matters here — the third is a
*cost* measurement and cannot bound the benefit.

**1. Nothing forces the issue the way it was forced for UTF-16.** What decided
Q91 was that `FF FE 00 00` is the UTF-32LE mark *and* a UTF-16LE mark followed
by `U+0000`, so one buffer got opposite verdicts on where its NUL sat. That is
structural and frequency-independent, and `EF BB BF` has no counterpart to it.
Of the five marks in play, `FF FE` and `FF FE 00 00` are the **only** prefix
pair; `EF BB BF` is a prefix of nothing and nothing is a prefix of it. So there
is no second reading, no verdict turning on NUL position, and none of the
argument that carried Q91 transfers.

**2. [`Q84`](Q84.md)'s notice already covers the whole residual class.** Telling
the user a buffer went unread serves this member *and* the undeclared half —
UTF-16 with no mark — which no arm can ever reach, because nothing in such a
buffer declares anything. An arm buys one member of a class a notice serves
entirely.

**3. On this machine the arm would fire twice and be wrong twice — and that is
a cost reading, not a bound on the benefit.** Swept `~/go/pkg/mod` and
`~/workspace/claude-spill-guard`:

| `EF BB BF` files | 63 |
|---|---|
| carrying a NUL in the first 8 KiB | **2** |

Both are `tetratelabs/wazero@v1.12.0`'s
`internal/integration_test/spectest/{v1,v2}/testdata/binary.22.wasm` — 11 bytes,
the mark glued to the wasm magic `\0asm`, spec-test fixtures whose whole point
is that a parser must reject them. Genuinely binary.

**Do not read that as "an arm would be all false positives".** It says what the
arm costs on a corpus that cannot produce the true positives — a Windows-authored
file carrying a mark, a NUL and a credential is exactly as unobservable here as
the UTF-16 population Q91 could not count. Claiming the benefit is zero on
evidence that can only see the cost is the reasoning Q91's own review had to
strip out once already.

What the 63 do show is composition, and it is worth more than the ratio: 61 are
ordinary text — 15 `.html`, 14 `.yaml`, 6 `.md`, 5 `.json`, 3 `.env`, and a
`.wxs` WiX installer manifest that is Windows-authored text with no NUL. The
NUL-carrying pair are a different kind of file entirely.

**An argument, held rather than measured**, and it should be read as one: a
declared UTF-8 buffer with an embedded NUL is odd in a way a declared UTF-16 one
is not. PowerShell 5.1 emits BOM'd UTF-16 as its ordinary output, so a
credential landing in that class needs no coincidence; nothing routinely emits
BOM'd UTF-8 containing NULs. That asymmetry is a better reason to scope this row
to the silence than the 2-of-63 is, and it is still an argument.

## What it costs to leave

Q91's review found the same claim asserted in three places and each has been
corrected to state the gap rather than define it away — `CLAUDE.md`'s axis
paragraph, `docs/design/README.md` step 2, and Q84's population count. The
temptation worth naming: restating the law as *"the axis is whichever
declaration this build routes on"* makes it true by construction, unfalsifiable
by a fourth encoding, and is how this one survived Q74 and Q91 both.
