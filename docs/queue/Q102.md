# A UTF-8 byte-order mark is a declaration `decode` does not read

`internal/scan`'s decode stage has three arms: the UTF-32 marks, the UTF-16
marks, and a default that reads raw bytes. `EF BB BF` — the UTF-8 signature,
from the same Unicode registry as `FF FE` — matches none of them, so a buffer
carrying it falls to the default, its NUL is read raw, and it returns
`SkippedBinary`, which `internal/hook` allows in silence.

So a file that declares an encoding and holds a credential can cross with
nothing in the transcript. It is the shape Q91 closed for UTF-16 —
that row is completed and gone, and its reasoning is in
[`docs/design/README.md`](../design/README.md) —
and it is still open for the mark Windows tooling writes most: PowerShell 7's
`Out-File -Encoding utf8BOM`, Notepad, and Visual Studio.

## Measured, four times, by four sessions

Found while reviewing Q91. Driven end to end on a built binary, `PreToolUse` on
`Read`, with the key taken from `testdata/corpus/planted/` so it survives
validation:

| Buffer | Verdict |
|---|---|
| `EF BB BF` + `# notes\n\0` + an AWS-shaped key | **allowed**, empty stdout |
| the same without the NUL — *the control* | denies, names `aws-access-key-id` |
| no mark + `\0` + the same key | allowed — the documented binary skip |

Two readings make this a measurement rather than an absence:

- **The control's offset moves by exactly three.** It denies at byte 29 with the
  mark and 26 without it. The mark stays in the buffer and is scanned as
  ordinary content, which is what having no arm looks like from outside
  `internal/scan` — stronger evidence than a `git grep` for `EF BB BF` finding
  nothing, which is how it was first noticed.
- **A UTF-8-marked buffer lands where an unmarked one does.** The third row is
  the one that fixes the reading: the mark buys the buffer nothing at all, so
  `decode` never reads it rather than reading it and deciding against it.

**Every arm exits 0, both denials included.** The discriminator is the `deny`
object on stdout, never the exit code. A re-run that tests `rc -eq 2` reads all
of them as allows and concludes the controls are dead — the same confusion this
repo's launcher bug turned on.

## Growing a third arm is not obviously the fix, and the population says so

Swept `~/go/pkg/mod` and `~/workspace/claude-spill-guard`, 245,397 files:

| | |
|---|---|
| files carrying `EF BB BF` | 63 |
| of those, carrying a NUL in the first 8 KiB | **2** |

Both are `tetratelabs/wazero@v1.12.0`'s
`internal/integration_test/spectest/{v1,v2}/testdata/binary.22.wasm` — organic,
nobody's fixture, and genuinely binary. So an arm that blocked on a UTF-8 mark
plus a NUL would, across the whole measured population, block only true
binaries. That is a false-positive rate of two out of two.

Contrast the UTF-16 side of the same sweep, which is why Q91's change was cheap:
43 marked files, 21 of them organic in the module cache, and **none** decoding to
binary.

**So this row is about the silence, not about the arm.** Do not read it as
specifying a decode change. The remedy space includes [`Q84`](Q84.md)'s notice —
telling the user the buffer went unread — which serves this member without any
ruling about encodings, and which is the cheaper answer if the arm would only
ever fire on `.wasm` files. A decode arm needs a population that a notice does
not.

## What it costs to leave

Q91's review found the same claim asserted in three places and each has been
corrected to state the gap rather than define it away — `CLAUDE.md`'s axis
paragraph, `docs/design/README.md` step 2, and Q84's population count. The
temptation worth naming: restating the law as *"the axis is whichever
declaration this build routes on"* makes it true by construction, unfalsifiable
by a fourth encoding, and is how this one survived Q74 and Q91 both.
