# `recordMarks` runs a regex over every token of every segment

`substStates` walks the marked string and calls `recordMarks` on each token of
each segment, which runs `substMarkRE.FindAllStringSubmatch` unconditionally.
Most segments carry no marker at all -- a string with one substitution and two
hundred other segments runs the regex two hundred times to find nothing.

A `strings.ContainsRune(tok, substMark)` test is enough to skip the regex,
since the sentinel is a single byte and the pattern cannot match without it.

This predates Q165. That change added a `v.clone()` beside the same loop,
which is what drew attention to it; the regex is the older and larger cost.

## What is not known

Whether the win is real, and this is the whole of the item. Measured
2026-09-09 on a 201-segment string carrying one substitution and five live
variables, in a package benchmark:

| arm | ns/op |
|---|---|
| guarded, five runs | 555,717 / 651,849 / 723,955 / 1,140,060 / 885,550 |
| unguarded, five runs | 4,960,920 / 5,180,621 / 5,500,902 / 4,843,479 / 8,253,843 |

That reads as a 5x win and **should not be believed**. An earlier single run
of the same unguarded code, taken before the guarded arm existed, returned
945,179 ns/op -- inside the guarded range. The box was running the repo's gate
and several other sessions throughout, so the two arms were measured under
different load and the comparison is confounded rather than close.

The clone is separately measured and is not the cost: `vars.clone()` is
706 ns empty and 1,449-2,331 ns holding five names, so 201 of them is under
half a millisecond.

Re-take both arms interleaved on an idle machine before writing any code. If
the effect survives, the guard is two lines; if it does not, close this and
say so, because the confounded table above is the kind of number that gets
cited later.
