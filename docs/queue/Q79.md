# The reader lookup and the mover check use different Base functions

`internal/readers` finds a command's row with `path.Base(tokens[0])`.
`internal/hook/bash.go` decides whether a segment moved the working directory
with `filepath.Base(tokens[0])`. On darwin and linux these are the same
function. On Windows they are not: `path.Base` splits on `/` only, and
`filepath.Base` splits on `\` as well.

Nothing chose that. The two were written a layer apart and the difference is
incidental, which is why this is a row rather than a comment — a comment saying
the two are deliberately different would invent a decision nobody made, and a
later reader would build on it as settled.

## Which side is exposed

The mover check is the safe one. `filepath.Base` strips more, so more tokens
read as `cd`/`pushd`/`popd`, and more relative operands are refused as
unresolvable. Erring toward blocking is the direction this project takes
everywhere.

The reader lookup is the exposed one. A backslash-style `argv[0]` — `x\cat` —
does not strip under `path.Base`, so `Files` reports the command as one with no
row, the segment contributes no operands, and the call is allowed with the file
unscanned. That is the fail-open direction.

It is **not** the refusal-leak class. Whatever the reason interpolates is
confined to the union of the spec keys and the alias keys, because `Files`
returns known only when the lookup succeeds — the directories cannot survive to
a reason because they cannot survive the lookup.

## What settles it

One logged Windows Bash payload, read for what `tool_input.command`'s `argv[0]`
actually looks like. Claude Code runs Bash under a POSIX-ish shell on Windows,
so the token may never carry a backslash at all — and neither the session that
found this nor the one that filed it can drive a Windows host to check.

**Event:** a Windows Bash payload is logged. If `argv[0]` is POSIX-shaped this
closes as not-a-defect, and the comment can then say something true rather than
something invented. If it carries backslashes the gap is real and the fix is
one function name.

Do not let it block a release. `cross-compile` builds windows/amd64, so the
binary ships there whatever this turns out to be, and the failure it describes
is a file going unscanned rather than one leaking.
