# Hook entry and the launcher that denies when the binary is gone

Blocked by [Q1](Q1.md), [Q3](Q3.md). The exit-code contract decides what
blocking looks like.

`hooks.json` cannot invoke `spill-guard` directly. An absent binary exits 127
with empty stdout, and Claude Code reads empty stdout as no objection — the
hook is then installed, silent, and enforcing nothing. That is the
predecessor's Node-18 failure with a different number on it, and
exit-status-guard shipped the same class at exit 126 in its 1.0.0, where the
launcher went out at mode 644 and the guard never fired once.

So the launcher resolves the binary and **writes a deny to stdout** when it
cannot find one, naming the install command for the platform it is on. The
resolution order is in `docs/design/distribution.md`: `SPILL_GUARD_BIN`, then
`PATH`, then the install-script location, then deny.

## Two packaging rules that are shipped bugs elsewhere

Anything `hooks.json` invokes ships executable, with the mode set in the git
index via `git update-index --chmod=+x` rather than `chmod` alone. And CI
drives the hook **through the launcher** on all three operating systems — a
suite that invokes the binary directly never executes the launcher at all, and
a launcher that stops working produces exactly the empty stdout a clean call
produces.

## The open question this item carries

Version skew between the launcher and the binary. A tap that upgrades
`spill-guard` while the plugin stays pinned gives a binary and a ruleset from
different releases. Checking every invocation costs latency on a path nobody
chose to be on; checking only in `selftest` catches it only when someone runs
`selftest`. Decide it here.
