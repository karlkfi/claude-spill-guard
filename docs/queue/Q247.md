# A key in a Grep glob or path crosses unread

`grepToolTargets` scans `pattern` on the argument that it is "text the call carries, and a
key typed into one is a key in the transcript". That argument reaches every string field of
the call, and `grepToolInput` decodes only `pattern`, `path` and `output_mode`. The comment
on that struct exempts the other fields because they cannot turn a mode that prints no lines
into one that does, which is a different question.

## Driven 2026-11-04

A built binary at Q245's head, a payload with the key in the named field, no real `claude`:

| Field holding the key | `path`, `output_mode` | Result |
|---|---|---|
| `glob` | a directory, `count` | exit 0, no verdict, no record |
| `glob` | a plain file, `content` | exit 0, no verdict, no record |

`path` is not read as text on any arm either. A key in a Bash operand is caught because the
operand sits in the command string; the same key in this field is opened as a path and never
matched. Traffic was not swept for such a call.

## What is owed

Scan the string fields of a Grep call as text, or say why not in the comment on the struct.
`glob` and `type` hold no path, so they need no resolving. Whether a `Read` call's
`file_path` belongs in the same change is part of the question, since it has the same shape.
