# The clean corpus is 13 files, and two claims rest on more than it holds

`testdata/corpus/clean/` is 13 files and 12,841 bytes, written for the purpose.
It is adversarial — the inherited `pii-postal-code` reports 31 matches on it
and `pii-phone-cn` reports 8 — and it is small. Two things currently lean on
it harder than that supports. Figures re-taken 2026-08-27; the 10 files and
8,731 bytes this row was filed against were a reading of an earlier tree.

**The pinned false-positive count.** Zero over 12.5 KiB is a much weaker claim
than zero over the 257 files and 27.6% file-level rate the design argues from.
The rules the corpus cannot see are the ones with no case in it. Three were on
that list when this row was filed and two have come off it: a sample JWT and a
published example key are both in the clean half now, and both rules grew a
second check to stay quiet on them. A base64 blob that happens to open `eyJ` is
still uncovered, as was a quoted PEM header until the rule grew a body-line
requirement. Every one of those was found by scanning this repository rather
than by anyone reading the corpus, which is the argument for doing that
deliberately. Run the ruleset over a real infrastructure repository, read every
hit, and either extend the corpus with what it found or cut the rule that found
it.

**What the clean half is adversarial *against*.** The 31 and 8 readings pin it
against the inherited numeric family, which is the noise this project exists
to answer. It is not adversarial against half of the shipped credential rules:
five of the ten — `github-fine-grained-pat`, `slack-token`,
`stripe-live-secret-key`, `openai-api-key`, `private-key-block` — get zero
*raw regex* matches on the
clean half, before any validator runs. For those five the pinned zero is a zero
over material that never approaches them, which is a weaker statement than it
looks. Five rules do get raw matches and are held by their validators —
`aws-access-key-id` 3, `slack-webhook-url` 2, `github-token` 1,
`google-api-key` 1, `jwt` 1, re-counted 2026-08-27 — and that is the part
currently carrying the claim. `jwt` joined that half when the sample token went
into the clean corpus.

**`validate.DefaultLabelWindow`'s own doc comment.** It records 64 bytes from
37,822 numeric runs over 914 files, then says the corpus was the wrong shape —
no Kubernetes manifests, no Ansible, no logs, no `.env` files — and asks to be
re-taken against `testdata/corpus` once that exists. It exists, and it cannot
answer the question: the measurement needs numeric runs sitting near PII
labels, and a corpus of clean infrastructure files holds none by construction.
So the comment's instruction is not executable as written.

The re-measurement it wants needs a third thing, which is neither half of the
current corpus: real text carrying real labels beside real numbers. Synthesised
PII would answer a question about the synthesiser. Decide whether that corpus
can be assembled at all, and if it cannot, say so in the comment rather than
leaving a re-measurement standing that nobody can take.

Grow the clean half first; the window measurement is downstream of having
material to take it on.
