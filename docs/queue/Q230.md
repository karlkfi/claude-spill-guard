# An input descriptor that `exec` opens is read by a later command

`exec 3<f` opens `f` on descriptor 3 for the rest of the shell, and `exec
<f` replaces stdin. A later `cat <&3`, or a bare `cat`, then prints the
file. Neither segment carries a path the hook opens, because `exec` with no
command word only redirects, and `<&3` names a descriptor rather than a file.
Driven 2026-11-01 under `env -i PATH=/usr/bin:/bin`, with the planted AWS key
in `k.env`. bash is 5.3.15, zsh is 5.9 under `-f`, and the hook is a built
binary of the Q219 branch over `826fed2`.

| command | bash | zsh | hook, both shells |
|---|---|---|---|
| `exec 3<k.env; cat <&3` | prints | prints | allow, silent |
| `exec <k.env; cat` | prints | prints | allow, silent |
| `exec 3<k.env; echo $(<&3)` | nothing | prints | allow, silent |

The likely fix reads an `exec` segment's `<` targets wherever the segment has
no command word. That is the same reading Q219 gave a bare redirect under
zsh. It over-reads an `exec 3<f` that nothing reads afterwards, which costs
nothing on the shape unless real calls carry it. Nobody has counted.

Found by the reviewer of the Q219 change, and kept out of it because `exec`
is a builtin that keeps the descriptor open, which is a different mechanism.
