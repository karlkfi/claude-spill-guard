# The attached provenance bundle has no consumer

Q58 attaches the build provenance to the release as
`spill-guard_<version>.intoto.jsonl`, and the release job verifies every archive
against that attached copy as well as through the attestations API. Its stated
reason is a consumer with no network path to that API: it has the bundle, and
nothing that reads it.

That consumer is still hypothetical here, because the install scripts do not
read it. [`install/install.sh`](../../install/install.sh) picks a verifier and
takes one of two paths — `cosign verify-blob` over `checksums.txt`, or `gh
attestation verify "$work/$archive"` with no `--bundle`, which queries the API.
`install/install.ps1` is written the same way. So the asset closes the OpenSSF
Scorecard gap and the packaging gap, and the verification gap it was argued
from is closed on the publishing side only.

Adding `--bundle` to the `gh` path is one flag and is not obviously right. The
bundle would have to be fetched as a second download before the archive is
trusted, which is a step the script does not have today; and `gh attestation
verify --bundle` still fetches the Sigstore trust root, so it removes the
attestations API from the path and not the network. Measured 2026-09-01 against
`cli/cli`: `gh attestation verify <asset> --bundle <downloaded bundle> --repo
cli/cli` exits 0, exits 1 on a different artifact, and exits 1 on a wrong
`--signer-workflow`, so the mechanism works and refuses. What it buys a user
here is narrower than it looks, and worth deciding rather than adding.

The other half is that `gh attestation verify` prints nothing on success once
its output is redirected — exit 0 on an empty log. Every assertion the release
job makes about provenance therefore rests on the exit status and the archive
count beside it. `--format=json` would give it a value to assert instead.
