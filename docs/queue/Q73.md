# Reading `.claude/spill-guard.json` is a decision, not a loader call

`internal/rules` merges a project ruleset over the shipped one and `Load`
already takes both sets of bytes, so wiring it is one argument in
`internal/hook`. What that argument would admit is a two-step bypass: write the
file with `{"id": "…", "enabled": false}`, then read the secret. Neither step
is caught. `Write` and `Edit` are not in the scanned set, and a
`cat > .claude/spill-guard.json` heredoc that *is* scanned carries no secret,
so a scanner looking for credentials passes it either way.

This row used to name two escape hatches. The other one — `SPILL_GUARD_OVERRIDE=`
in command position — had no such question and has shipped, reading an inline
assignment prefix off a `Bash` command and downgrading a block to a
confirmation. What is left is this half.

## Why "the model can write it" does not settle it on its own

The model can author the environment prefix too, and the design does not defend
against a user who means it. What separates the two is scope and legibility:
the prefix excuses one call and sits in the command the human is being asked to
approve, while a config entry disables a rule for every later call in every
later session and the write that made it is one line of scrollback.

So the question is not *can this be authored by the model* but *what makes a
disablement in this file trustworthy enough to honour*. The three guards that
suggest themselves each fail on their own terms, and the design section below
carries the working:

- **Scan `Write` and `Edit`.** Does not close it — the disablement carries no
  secret to find.
- **Stricter and never weaker.** Not decidable from the schema. Every field an
  override can set has a weakening direction, including a regex that matches
  nothing and keywords the prefilter will never find. The one mechanically
  clean version is *may add a rule, may not touch a shipped one*, which removes
  the reason the file exists.
- **A signature from outside the workspace.** Needs a key, a verifier and
  somebody to hold both, against a stated property of an empty supply chain.

A fourth is unexplored and is the one worth taking first: whether the answer is
that there is no project ruleset at all, and precision complaints are answered
by a rule change in the shipped set rather than by a local override. That
retires the file instead of guarding it, and it costs whatever local tuning is
worth — which nobody here has measured.

**Ask:** whether spill-guard ships a per-project override at all. What turns
on the maintainer is product scope, not a guard: the fourth option below —
retire `.claude/spill-guard.json` and answer precision complaints by changing
the shipped ruleset — removes the feature rather than securing it, and that is
a decision about what the tool is. The three guards are already refuted below,
so there is nothing left for grooming to settle.

## Where the reasoning already is

`docs/design/README.md`, under **Output discipline**, carries the analysis and
the measurement behind the half that shipped. `rules/README.md` says the file
is read by nobody, so a user reading the ruleset docs is not told it works.
Whatever this row decides has to move both.
