# The two escape hatches the design names are wired to nothing

`spill-guard hook` scans and blocks, and there is no way past it. The design
names two ways out and the hook entry implements neither, so a user whose file
trips a rule has the tool and no answer.

- **Per-rule disablement in `.claude/spill-guard.json`.** `internal/rules`
  already merges a project ruleset over the shipped one and `LoadFiles` already
  reads two paths. `internal/hook` calls `Load` with the compiled-in bytes and
  a nil override, so the project file is read by nobody.
- **`SPILL_GUARD_OVERRIDE=` in command position**, matching
  `WORKSPACE_GUARD_OVERRIDE` and `PROD_GUARD_OVERRIDE`. Reading it means
  finding the assignment prefix on the Bash command, which is
  `bash.StripEnvPrefix` over a segment — the same layer [Q62](Q62.md) works in,
  and not implemented by it, because Q62 resolves operands rather than reading
  the prefix.

## The half that is a question rather than a wiring job

The design says both hatches are "places the model cannot write to from inside
a scanned buffer", and for the environment prefix that holds: it is in command
position, which is not content. For the config file it holds only in the sense
written down. `.claude/spill-guard.json` is an ordinary file in the project,
and the model writes ordinary files — so wiring it as specified gives the model
a two-step bypass: write a rule with `"enabled": false`, then read the secret.
Nothing in the current tree makes that reachable, because the file is read by
nobody, and wiring it is what would.

So this is not "call `LoadFiles` instead of `Load`". Decide what makes the
config trustworthy before it is read — that the hook only honours it when
`Write` and `Edit` are themselves scanned, or that a project entry may make a
rule stricter and never weaker, or that a disablement has to be signed by
something outside the workspace. Any of those is a decision. Wiring it without
one ships the bypass.

The environment prefix has no such question and can land first.
