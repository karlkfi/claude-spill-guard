# Retire the project ruleset the docs describe and nothing reads

**Answered 2026-08-28 in #57: there is no project ruleset.** A precision
complaint is answered by changing the shipped set, which is a PR somebody
reviews, rather than by a local override the model can author through an
unscanned `Write`. That removes the two-step bypass instead of guarding it, and
it keeps the empty supply chain — no key, no verifier, nobody holding both.
What is left is a removal, and every site below still describes the feature as
present or coming.

## Why the label came back after the answer

#57 wrote the answer in and dropped `open-question` in the same edit, which is
what the store asks of whoever answers. #69's groom re-added it and wrote a
`**Settles:**` route at the top of the row, with a heading, five paragraphs

The search was sound and the row defeated it. #69 was hunting rows that end in
a choice and carry no label; an answered row that keeps its original `**Ask:**`
block looks exactly like an unanswered one, because the label is the only thing
the answer moved and the label is what the search keyed on being absent.

has no rule for the inverse. So this rewrite deletes the original question
instead of archiving it in place — `git log -p --follow docs/queue/Q73.md` is
the archive, and a route marker left in a row is a trap for the next groom
rather than a record.

## The argument, kept because the design still has to be rewritten from it

Saying the model can author the file is true and settles nothing: it authors
the `SPILL_GUARD_OVERRIDE=` prefix too, and the design does not defend against
a user who means it. What separates them is scope and legibility. The prefix
excuses one call and sits in the command a human is being asked to approve; a
config entry disables a rule for every later call in every later session, and
the write that made it is one line of scrollback.

The three guards that suggest themselves each fail on their own terms, and
`docs/design/README.md` under **Output discipline** carries the working: scanning
`Write` and `Edit` does not close it, because the disablement carries no secret
to find; *stricter and never weaker* is not decidable from the schema, since
every field an override can set has a weakening direction; and a signature from
outside the workspace needs a key, a verifier and somebody to hold both, against
a stated property of an empty supply chain.

Retiring the file is the fourth answer, and it removes the bypass rather than
guarding it. What it costs is local tuning, which nobody has measured and which
the shipped set now has to absorb.

## The removal reaches the loader, which the earlier answer said it would not

"`internal/hook` keeps calling `Load` with a nil override" is true of the call
site and leaves the merge standing. `rules.Load(embedded.Shipped, nil)` in
`scanCall` is the only caller in anything that ships, and `rules.LoadFiles` —
the one function that opens either path — has no caller outside
`internal/rules/load_test.go` and `internal/scan/corpus_test.go`.

Delete it. `LoadFiles`, `Load`'s `project []byte` parameter and its
`if project != nil` branch, `apply`, `overlay`, and the `projectSet` constant
exist for the retired feature and nothing else. Leaving them means honouring a
project disablement stays one token away, permanently, in a tree whose docs
will say the feature is gone; deleting them means restoring it takes a diff
somebody reviews, which is the whole argument the decision rests on. The repo
already holds this call under **Never put a raw secret in a struct that
outlives the match**: the predecessor's `secretValue` was a dedup key that was
never printed, and its existence was still a standing hazard.

`entry`'s pointer fields stay. `compile` reads their nil-ness to refuse a rule
that "does not say whether it is enabled", and that check is the shipped set's
own strictness rather than the override's — so the deletion does not weaken it.
