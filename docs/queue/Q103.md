# The Windows LF control reproduces a byte-drift symptom

`launcher-mutation-control`'s *LF endings with a block present* step flattens
`hooks/run-spill-guard.cmd` to LF, splices a parenthesized block into the batch
half, and requires `check-launcher.py` to report **both** the deny that never
arrives and cmd.exe's `cannot find the batch label`. Two greps, deliberately —
the step's own comment says requiring only the line-endings finding would test
the assertion rather than the behaviour.

**The behaviour it reproduces is byte-drift, and drift is a property of the
file rather than of LF.** cmd.exe's file position slips one byte per line it
reads out of a parenthesized block when the endings are LF, so with the
four-line block the step carried, whether the `goto` after it landed mid-label
depended on the layout of everything around it.

Measured 2026-08-31 on `windows-latest`, twice, while landing Q10
(the plugin manifests and hooks.json):

- Ten `REM` lines added to the batch half: the failure stopped reproducing. The
  gate still reddened on the line endings, the second grep found nothing, and
  the step failed saying *the gate failed, but not on the deny that never
  arrives*.
- The comment moved out of the batch half, leaving it at 74 lines and 75 CRLF —
  identical to `main` — and it **still** did not reproduce. So line-count
  parity is not sufficient; what was left was 273 bytes shaved off the four
  deny strings, all of them below the block.

**What is red is a guard on a guard, not the guard.** `launcher
(windows-latest)` passed throughout both measurements: the launcher's
production behaviour on Windows -- it denies, in the right shape, through
cmd.exe -- is asserted and holding. What stopped working is the control that
proves the line-endings gate can still fail.

**The expensive part is the direction it fails in.** A control that quietly
stops reproducing reports the *gate* as broken, not itself, and the reader's
first move is to look at `check-launcher.py` — which is correct. Nothing says
"the mutation landed and did not bite", which is the class
[`CLAUDE.md`](../../CLAUDE.md) already names.

## What was done about it, and what is left

Padding the block to forty lines puts the drift well past any single line, so
the reproduction stops depending on the surrounding bytes. That shipped with
Q10 and is the reason this row is `M` rather than a bug report: it makes the
symptom reliable and does not make it *checkable*.

What is left is the general question. This repository has twenty-odd mutation
controls and every one of them asserts a symptom by grepping for a message. A
control whose mutation can silently fail to bite needs the same thing a probe
needs — evidence it could have come back the other way — and there is no
cheap general form. Candidates, none costed:

- Assert the *pre-mutation* run is green and the post-mutation run is red, per
  control, so a control that has stopped biting differs from one that never did.
- Have the step assert what the mutation was supposed to cause and not only
  what the gate said about it — here, that the launcher's own exit and stdout
  changed.
- Accept a symptom grep where the mutation is deterministic (a deleted line, a
  renamed key) and require the stronger form only where it is not.

Related: [Q59](Q59.md) is the same shape one layer out — signing, attestation
and upload have no mutation control at all.
