# The Windows LF control reproduced a byte-drift symptom

**Answered 2026-08-31: it reconstructed the measured arm instead of
transplanting it, and it now drives a hashed fixture.** The row stands for the
class rather than the instance; the instance is fixed.

`launcher-mutation-control`'s *LF endings with a block present* step flattened
`hooks/run-spill-guard.cmd` to LF, spliced a parenthesized block into the batch
half, and required `check-launcher.py` to report both the deny that never
arrives and cmd.exe's `cannot find the batch label`.

[`CLAUDE.md`](../../CLAUDE.md) said the control "transplants the failing arm
byte for byte, 7,214 bytes verified identical". It did not. It **rebuilt** that
arm from whichever launcher was in the tree, so it landed on the measured
artifact only while the launcher was `main`'s:

| launcher the step patched | result |
|---|---|
| `origin/main` | 7,214 bytes, sha256 `d28a64b3…` — the measured arm exactly |
| the Q10 branch, four deny strings shortened | 7,824 bytes, 610 off |
| the same, block padded to forty lines | 8,304 bytes, further off |

So the byte-position mechanism stopped landing mid-label, cmd.exe went on
denying correctly, `line_endings` reddened alone, and the step failed reporting
*the gate failed for the wrong reason* — three heads running. Padding the block
made it worse, because more lines moved the file **away** from 7,214 rather
than nearer.

**Fixed by checking the artifact in.**
`testdata/launcher/lf-uniform-failing.cmd`, hash-asserted by the step before it
is driven. The control now depends on the launcher's bytes not at all, which is
the property no amount of tuning could give it, and `CLAUDE.md`'s claim becomes
true rather than needing a caveat.

**The undocumented thing, which is what this row is really for:** a mutation is
only valid against the artifact it was measured on. Nobody wrote that down, and
nothing in the step said the reconstruction was a reconstruction.

## The class, which is still open

This repository has twenty-odd mutation controls and every one asserts a
symptom by grepping for a message. A control whose mutation can silently fail
to bite reports the **gate** as broken rather than itself, so the reader's
first move is to audit a gate that is working — the expensive direction, and it
cost three CI round trips here before anyone compared bytes.

Candidates, none costed:

- Assert the pre-mutation run is green and the post-mutation run is red, per
  control, so a control that has stopped biting differs from one that never did.
- Have a step assert what the mutation was supposed to *cause* and not only
  what the gate said about it.
- Prefer a checked-in artifact over a reconstruction wherever the mutation is
  sensitive to anything but its own edit, and hash it.

`status-drift-mutation-control` met the same class from the other side in the
same batch and its precondition **held**: unwiring the `hook` arm no longer
made the binary stop reaching `internal/scan`, because `internal/selftest`
reaches it too, and the step said so instead of passing. That is the shape the
others want.

Related: [Q59](Q59.md) is one layer out — signing, attestation and upload have
no mutation control at all.
