# A substitution body after a followed `cd` is still recorded

The tracker in `bashTargets` follows a literal `cd` through the segments in
order, so `cd sub && cat x` resolves `x` under `sub`. A command-substitution
body does not get that: `bashTargets` queues every body it finds for a pass of
its own, and the queue carries no position relative to the move, so a body
found in a string that moved at all inherits an unknown directory
(`internal/hook/bash.go:72:or from none if the parent moved at all`). Its
relative operand is then a coverage record, as every relative operand after a
`cd` was before the tracker.

That is the right answer for a backtick body, which is only ever reached
through the queue, and a fail-closed one — the alternative resolved it against
the payload's cwd and allowed, driven. It is the wrong cost for a `$(…)` body:
`Segments` flattens that one into the in-order pass, where the tracker resolves
its operand correctly, and then the queue re-resolves the same operand against
the lost directory and the whole call defers on it. So `cd sub && echo $(cat x)`
records today exactly as it did before the tracker, while `cd sub && cat x`
beside it gets a verdict.

**Measured 2026-09-06** over this machine's transcripts: 137 coverage records
on the relative-after-`cd` arm carry a cd-family command, and **11** of them
carry a `$(…)` or backtick after it. The tracker converts the other 126; these
11 stay where they were.

## What closes it

Telling the two bodies apart. `bash.CommandSubstitutions` returns bodies as
strings, in text order, with nothing saying which opened with `$(` and which
with a backtick, and nothing saying where in the string either sat. Either
reading would do: a kind lets the queue skip a `$(…)` body's operands, since
the flattened pass already had them and the queue exists for the nested
backticks and heredocs inside it; an offset lets the queue start the body from
the directory tracked at that point in the string, which is the answer for a
backtick too.

Both are changes to the shape of `internal/bash`, which `CLAUDE.md` holds
structurally identical to its `claude-workspace-guard` upstream. Upstream has
the same gap: its `shell_bodies` list carries the group cwd, but its
command-substitution recursion runs once over the whole string after the group
loop and starts from `cwd`, not from the directory tracked at the substitution.
So the honest route is the same as Q92's — a fix upstream first, ported by
inspection — and the row should not close by diverging the port for 11 records.

Matching `"$(" + body + ")"` against the raw text to guess the kind is the
shortcut to refuse: it is a second parser over text the lexer already read, and
it disagrees with the lexer the first time a body appears in both forms.

## The same position problem holds the variable map

The resolver in `internal/hook/vars.go` gives each queued body an empty map
rather than the parent's: a body has no position, so a value the string
assigns *after* the body would be substituted into text bash expanded with the
environment's value. Upstream seeds its recursion with `stable_vars`, the
names holding one literal at every point in the string -- and a name assigned
once and never poisoned is stable there whether the body sits before or after
the assignment. For workspace-guard a stale value only ever adds a prompt; for
a scanner it picks which file gets read, so the seed is not ported. The
consequence is the one above with a variable in place of a `cd`:
`SP=/x; echo $(cat $SP/f)` records where `SP=/x; cat $SP/f` resolves. An
offset per body closes both halves at once, which is the argument for that
reading over the kind.
