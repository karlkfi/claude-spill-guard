# A case right after an opening brace is not read as one

`P=.; { case a in b) P=w;; esac; }; cat $P/x` reads `./x` in bash, because
no pattern matched and the assignment in the arm never ran. The hook reads
`w/x`. With the key in `./x` and clean text in `./w/x` it exits 0 with no
verdict and nothing on stderr. Driven 2026-11-01 on bash 5.3.15 under `env -i
bash --norc --noprofile -c`, and through `hook.Run` on the Q212 branch by a
throwaway test. The same command without the braces gets the right answer.

The mechanism is read from the code and not driven apart. `Segment.CaseArm`
(Q151) is set by `trackCase`, which opens a clause only in command position,
and command position after a reserved word is `cmdPosKeywords` in
`internal/bash/lex.go`. That set has no `{`, `!` or closer, so after `{` the
`case` is an operand and the arm reads as code that ran. Upstream's
`LEADING_WORDS` has all of them, and the Q212 port added a `leadingWords`
table beside the narrower one for its compound tracking rather than widening
`cmdPosKeywords`, because `scanDollarParen` keys on that set to decide which
`)` closes a substitution.

So the fix is one of two, and the second is the one to measure first: widen
`cmdPosKeywords` to upstream's set and drive `scanDollarParen` over the
shapes it changes (`$( { case x in a) ;; esac; } )`), or have `trackCase`
take the compound tracker's position. Check `! case`, `then case` after a
closer, and `time case` while there.
