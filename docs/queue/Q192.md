# On Windows the shell ladder never answers bash, so every glob defers

On Windows, the `Bash` tool runs Git Bash. The hook's shell ladder still
answers *not bash* there for every file, because `executableBy` in
`internal/hook/shell_other.go` reads the execute bits and Go never sets them
on a Windows regular file. So `toolShell()` returns the empty string,
`toolShellIsBash()` is false, and every glob operand on Windows is a coverage
failure, even on a machine where the shell is certainly bash.

## The question this row asked, answered

This row asked whether a `Bash` tool call on Windows can reach the PowerShell
provider. **It cannot.** The answer is a reading of the 2.1.290 CLI
(`~/.local/share/claude/versions/2.1.290`), taken 2026-11-01 on macOS. It
reads the shipped code's Windows branches and runs nothing on Windows. That
is the second-best source this row named, so the answer rests on the binary
and not on a Windows drive.

- The `Bash` tool's executor names its provider as a literal:
  `vn=await ype(Xe,b.signal,"bash",{…})`. The providers are
  `lwr={bash:…,powershell:…}`, and the `powershell` entry is reached from a
  separate tool named `PowerShell`, which calls `ype(D,h.signal,"powershell",
  {…})`. That tool is Q224, since the manifest does not match it.
- On Windows, `Bash` is offered only when Git Bash is found (`function
  rl(){if(O()!=="windows")return!0;return v5()!==null}`). When it is found,
  startup sets the variable this ladder reads:
  `process.env.SHELL=e,t(\`Using bash path: "${e}"\`)`. `e` is the Git Bash
  path, which comes from `CLAUDE_CODE_GIT_BASH_PATH` when that names a
  `bash.exe`, `sh.exe`, `bash` or `sh`, and from detection otherwise.

So the row's second reading closes as well. No provider is chosen ahead of
the ladder for `Bash`, and `SHELL` names the shell that runs. If
`CLAUDE_CODE_GIT_BASH_PATH` names an `sh.exe`, the ladder's basename test
answers *not bash*. That is conservative rather than right: Git for Windows'
`sh.exe` is bash running in POSIX mode, so the ladder defers where it could
expand. It is friction, never a fail-open.

None of this matters on a machine without Git Bash. There, the hook command
itself runs under PowerShell, which is Q224.

**On the trap.** This machine runs no `pwsh`, so a local probe would have
come back empty and said nothing about Windows. The reading above does not
rest on a probe here. It is a read of the code a Windows install runs,
assuming the Windows build bundles the same JavaScript as the macOS one. That
assumption is the one thing a `windows-latest` drive would settle.

## The defect the third reading turned up

The row's third reading asked what the deferral costs on Windows. It costs
every glob. `executableBy` on `!unix` is `mode.Perm()&0o111 != 0`. Go's
`os/types_windows.go` (1.27.1, lines 179 and 181) gives a regular file `0444`
or `0666` and sets `0111` only on a directory, so `bash.exe` never passes. The
answer errs toward deferring rather than toward a wrong expansion, so this is
friction and not a fail-open. It also means the glob expansion in
`internal/hook/glob.go` is dead code on Windows.

**Fix.** On `!unix`, take the harness's own test rather than an execute bit:
the file exists and is a regular file. The harness applies exactly that to
`CLAUDE_CODE_GIT_BASH_PATH` (`existsSync`), and it sets `SHELL` itself from
that result. Then repoint the comment in `shell_other.go` and the sentence in
`docs/design/README.md` that ends "which is `Q192`'s platform anyway", both of
which still describe the question as open.

**Done** is a `windows-latest` test asserting that `toolShellIsBash()` is
true with `SHELL` set to an existing `bash.exe`, with the two citations
repointed. Whether an existing `sh.exe` should also answer bash turns on
whether bash in POSIX mode globs the same way for the patterns `glob.go`
expands. That has not been measured, so until it is, `sh.exe` keeps the
conservative *not bash*, and the test pins it. The cost was not measured: no
Windows coverage log exists, so how many calls this turns from a record into
a verdict is unknown.
