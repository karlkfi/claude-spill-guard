# Whether a Bash tool call can reach the PowerShell provider

The shell resolution now reads `CLAUDE_CODE_SHELL` and `SHELL` and answers
*bash* or *not bash*, and every measurement behind it was taken on macOS. The
harness carries a PowerShell provider beside the posix one, and the launcher
ships for Windows, so there is a third answer nothing here has looked for.

## What is already settled, so it is not re-derived

The posix ladder is driven and recorded in
[`docs/design/README.md`](../design/README.md) under *And the shell it is
expanded by*. On a machine where neither variable names bash, a glob operand is
a coverage failure and the call defers. That arm is the conservative one, so if
Windows falls through it, Windows already gets a record rather than a wrong
expansion -- which is why this is an open question and not a bug.

## What it owes

Three readings, in order, and the first may retire the rest:

- **Does a `Bash` tool call on Windows reach the PowerShell provider at all,
  or is the provider reached only by a different tool?** If a `Bash` call is
  always posix, the question closes and the design says so.
- **If it can, what does `CLAUDE_CODE_SHELL` hold there, and does the ladder
  even run?** A provider selected before the shell ladder would make both
  variables irrelevant on that platform, and `toolShellIsBash` would be
  answering about a shell that is not the one running the command.
- **What does the deferral cost there?** PowerShell's wildcard set is not
  bash's, so the right answer is very likely the same record. What is unknown
  is whether every `Bash` call on Windows then defers on any pattern, which
  would be a friction number rather than a correctness one, and the 509-of-540
  measurement behind *defer on a gap* was taken on one macOS machine.

## Why it is not in the sibling row

`Q184` covers the rest of the zsh delta -- glob qualifiers, `=cmd`, named
directories, the segmentation port's reserved words. That is a question about
two posix shells disagreeing. This is a question about whether a third kind of
shell is reachable at all, and it is answered by a Windows machine rather than
by `env -i <shell> -c`.

## What would close it

A `Bash` tool call driven on Windows with a probe `PreToolUse` hook that prints
its environment, which is the instrument the posix ladder was read with. Short
of a Windows machine, reading the provider selection out of the shipped binary
is second-best and is what the posix steps 2 and 3 rest on already -- state
which of the two any answer came from.
