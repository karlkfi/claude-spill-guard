# Signing, attestation and upload have no mutation control

Every gate in `.github/workflows/tests.yml` is paired with a job that breaks the
property and requires the gate to go red, because a check that has never failed
is a claim rather than evidence. Three steps in `.github/workflows/release.yml`
have no such pairing, and they are the three a pull request cannot reach at all:
cosign signing, `actions/attest-build-provenance`, and the upload.

`dry-run` covers the rest. It builds the archives, and
`dry-run-mutation-control` breaks the target list and the checksums file and
requires red on both. What no pull request exercises is everything after
`--skip=sign`, so the verification step — the one asserting that a signature
minted from a branch does not verify as the release's — has never run.

Two candidates, and picking between them is most of the item:

- **A rehearsal on a schedule.** Tag a throwaway prerelease, let the pipeline
  run end to end, assert the verification passes, then delete the tag and its
  draft. Real signing, real Rekor entries, real attestations, on a cadence
  rather than only when someone remembers.
- **A negative control on a real tag.** Verify the published `checksums.txt`
  against a deliberately wrong `--certificate-identity` and require it to fail,
  so the check is proved capable of rejecting rather than only of passing. This
  is cheap and runs inside the release job, and it proves less: it says the
  verifier discriminates, not that the signing path works.

`docs/development/release-process.md` currently tells a maintainer to rehearse
with a prerelease tag by hand. That is the manual version of the first option
and the reason this row is not just a nice-to-have: a step nobody automated is a
step that gets skipped on the release where it mattered.

## The surface grows, which is why this is `accruing`

The three steps above were the count on 2026-08-31. Q58 — merged 2026-09-02 as
#79 — added a fourth and widened a fifth, both inside the same tag-only job:

- **A new upload step**, *The provenance travels with the release, not only in
  the API*, which copies the attestation bundle to
  `dist/spill-guard_<version>.intoto.jsonl` and refuses an empty one. Nothing
  on a pull request runs it, so its empty-bundle guard has never been shown to
  fire.
- **A widened verification step**, *The published assets verify as an outside
  consumer would check them*, which now byte-compares the bundle against what
  the run built and verifies each archive a second time against the attached
  bundle rather than only through the attestations API.

So the `release` job carries eight named steps and five of them assert
something no pull request can reach. That is the mark this row now carries:
every change to the release path adds uncontrolled surface, because the only
place to put such a change is behind the tag. The cost of deferring is not
flat, and it grew measurably in one batch.

The second of those two is also the one [Q115](Q115.md) reports has no
consumer on the install side, so the same step is the subject of two rows from
different directions — Q115 owns the consumer measurement and this row owns
the control gap.

## What the deferral cost, measured on v0.1.0

The first release was cut on 2026-09-02 and the runbook's mandatory rehearsal
found four defects, one per attempt. Every one of them lived behind the tag,
so no pull request could have reached any of them:

| Attempt | What was wrong |
|---|---|
| `v0.1.0-rc.1` | `.goreleaser.yaml`'s `signs:` passed `--output-signature` and `--output-certificate`. cosign v3 defaults `--new-bundle-format` to true, which makes both no-ops and `--bundle` mandatory, so signing died with `create bundle file: open : no such file or directory`. |
| `v0.1.0-rc.1` again | `check-release-artifacts.py --signed` still required `checksums.txt.sig` and `.pem`, which the fix above stopped producing. `--skip=sign` on every pull request means `--signed` never runs there. |
| `v0.1.0` | `changelog: disable: true` makes GoReleaser ignore `--release-notes`. The draft published ten correct, signed, verifiable assets and a body of two newlines. |
| after publishing | `release-claims-mutation-control` had two arms reading real release state rather than forcing it, so publishing disarmed them — one of them asserted on the README's own standing "there is no release yet", a defect it did not create and could not keep. |

Three cost a tag cycle each. The third is the one that matters most for this
row's argument: **every assertion the release job made was about assets**, so
eight green steps sat on top of a release with no notes, and the rehearsals
inherited the same blind spot. Fixed in #85 by comparing the published body to
the notes file, which is one more tag-only assertion — the surface grew again
while being repaired.

So the row's `accruing` label is now measured rather than predicted. The cost
of having no automated rehearsal is four manual tag cycles per release path
change, and the only thing standing between that and a bad permanent tag was a
person choosing to rehearse.

**What this does not settle.** The two candidates at the top of this row are
still the decision. The v0.1.0 experience argues for the scheduled prerelease
over the negative control, because three of the four defects were found by
running the pipeline end to end and none by discriminating a verifier — but
that is one release, and a scheduled rehearsal has a standing cost this
repository has not priced.
