# A budget overrun lets every small file in the call cross unscanned

When a call's scan runs past the 45-second budget, the hook defers and reaches
no verdict on any buffer in the call. A prompt that names one big file and one
small file holding a key therefore lets the key into the model's context, with
only a coverage record to show for it. That breaks the rule `CLAUDE.md` states
under *Block on a finding; defer on a gap*: "A gap does not hide a finding
beside it".

This happens in two ways, and both have been driven. `scanCall` reads the
buffers one after another in prompt order: the prompt text first, then each
`@` file in the order `atTokens` returns them.

- **(a) A finding already made is discarded.** When the small file comes first,
  it is scanned and matched, and then a big file behind it runs out the budget.
  The overrun branch is
  `internal/hook/hook.go:120:return abstain(stdout, stderr, call, event, overran(budget), nil)`,
  and `within` returns nothing unless the whole call finished.
- **(b) A buffer behind the overrun is never read.** When the small file comes
  last, the budget fires while the scan is still on a big file, so the small
  file is never scanned at all.

## Driven 2026-11-01

All runs used `claude -p` 2.1.290 under a clean `HOME`, with the binary as the
only `UserPromptSubmit` hook at `timeout: 60`. `notes.txt` is a copy of
`testdata/corpus/planted/aws-access-key-id.env`. A "leak" below means the run
ended at `Not logged in` with a budget record in the coverage log, and the
transcript held a `file` attachment for `notes.txt` whose content matches
`AKIA[0-9A-Z]{16}`.

| Build | Prompt | Load | Wall | Result |
|---|---|---|---|---|
| `main` at `162fcf9`, budget 45s | `@part0.txt … @part5.txt and @notes.txt` | 115 | 49.702s | leak, arm (b) |
| `162fcf9` tree, budget set to 1s | `@notes.txt and @real-128.txt` | 22 | 1.855s | leak, arm (a) |
| `162fcf9` tree, budget set to 1s | `@real-128.txt and @notes.txt` | 22 | 2.165s | leak, arm (b) |
| `162fcf9` tree, budget set to 1s | `@notes.txt` alone | 118 | 5.831s | blocks, `aws-access-key-id` |
| `main` at `162fcf9`, budget 45s | `@notes.txt and @part0.txt … @part5.txt` | 27 | 40.626s | blocks, 503 matches; did not reach the budget |

The `partN.txt` fixtures are 400 MiB each and `real-128.txt` is 128 MiB, all
real text. The last row is not an arm (a) reading at 45s. Load had dropped, so
the scan finished inside the budget. Arm (a) is driven only under the 1s
budget.

PR #220's reviewer found the leak first and drove it at 1s. The same reviewer
then read arm (b) out of the code, against this row's first draft, which had
named arm (a) alone. Claude reproduced the 1s run and took the rest.

**Reaching the budget depends on load as well as size.** On this machine the
budget was reached by 2.4 GiB of real text at load 96–130, and by a single 400
MiB file on all three runs at load 58–119. On a quiet machine the same text
scans at about 60–73 MiB/s of CPU, so reaching the budget would take roughly
2.7–3.2 GiB. That figure is composed from the rate, not driven.

## What is owed

**A fix that closes both arms.** Keeping findings already made closes (a)
alone. (b) needs the buffers the harness will actually send to be read before
the ones it will not, or every buffer to get its own budget. Those are the
reviewer's proposals. Neither has been built or measured. The scan runs on its
own goroutine, and the verdict is written by the goroutine waiting on it
(`internal/hook/deadline.go`), so publishing findings as each buffer finishes is
one plausible shape for (a).

**Two tests, one per arm,** each pairing a key buffer with one that uses up a
short budget. For (a) the key comes first; for (b) it comes last. Each must
block, naming the rule. Then invert the fix for each arm and watch that arm's
test go red. A single test with the key first passes under a fix that leaves
(b) leaking. That is the gap this row's first draft had.

**Every surface is in scope.** `Bash` with several operands and `Grep` over a
file add up the same way a prompt does. `Read` carries one buffer, so it
reaches this only through the order of its decode and raw pass. Only the prompt
surface has been driven.
