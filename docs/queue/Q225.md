# An unresolved variable as the command name is read as having no row

Three commands read the key in bash 5.3.15 and get no verdict and no coverage
record from the hook. Driven 2026-11-01 under `env -i PATH=/usr/bin:/bin bash
--norc --noprofile -c` and through `hook.Run` by a throwaway test on the Q188
branch:

| command | why `$C` / `$V` is unresolved |
|---|---|
| `C=$(command -v cat); $C <key>` | the value is a substitution |
| `true && V="cat <key>"; $V` | the `&&` rule drops an assignment behind a command it cannot settle |
| `IFS=:; V="cat:<key>"; $V` | an IFS change stops the map |

Q188 made `$V` the command it carries wherever the value is a literal that
default-IFS whitespace splits. These are the rest. Where the head is still an
unresolved `$NAME`, nothing knows what runs, `internal/readers` finds no row
under `$C`, and the segment contributes no operands -- the reading the design
gives a command with no row, applied to a command that may well be a reader.

The question is the verdict. Either defer, recording the gap (no friction, a
coverage line per call), or keep allowing under the stated no-row limitation.

**Measure:** the traffic, which nobody has counted. An unrefined sweep on
2026-11-01 found 570 of 234,266 `Bash` calls in this machine's transcripts with
a `$NAME` in command position, an upper bound that counts heredoc script bodies
and environment variables (`$EDITOR`, `$SHELL`) alike. Refine that count, then
decide.
