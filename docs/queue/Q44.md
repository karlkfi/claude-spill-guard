# `golangci-lint` is pinned and no gate runs it

`tools/go.mod` pins `github.com/golangci/golangci-lint/v2 v2.13.1` and
`tools/tools.go` imports its command, so it is fetched, resolved and carried in
`go.sum`. `GATES` in the [`Makefile`](../../Makefile) does not name it and no
job in `.github/workflows/tests.yml` invokes it. It has never run here.

The `test` gate is gofmt, `go vet` and `go test`. `go vet` is a much narrower
instrument than golangci-lint and the two are easy to conflate when reading the
gate table, which is what makes this quiet.

**The shape is what matters, more than the one tool.** `tools/` shipped in #12
with three tools and no consumer for any of them. Of the three:

- `govulncheck` has one as of Q20 — the `vulns` gate.
- `actionlint` has one waiting in [Q22](Q22.md) — ready now, not blocked — and
  does not currently compile — [Q43](Q43.md).
- `golangci-lint` has none anywhere: no `GATES` entry, no job, no
  `.golangci.yml`.

**The count this row was filed with was wrong when it was written, and the
conclusion above does not rest on it.** It said "zero mentions of `golangci`,
`staticcheck` or `golint` anywhere in `docs/queue/`", measured 2026-08-23.
[Q43](Q43.md) was filed in the *same commit*, `42ce6ee`, carrying two mentions
of `golangci-lint` — so the probe ran against a tree that did not yet hold its
own commit's other file, and returned an empty result that read as a finding.
Re-measured 2026-08-28, excluding this row: two hits, both in Q43. Neither is a
consumer, which is what the bullet actually claims, so read the gate table
rather than a grep for the name.

A pinned tool reads as covered. Somebody choosing a version, writing it into a
module and adding it to `go.sum` looks exactly like somebody adding a check,
and the difference is invisible unless you go looking for the gate.

## What this row has to settle before it is work

Not "add a `lint` gate" — golangci-lint over a codebase this small, with the
scanner not written yet, will either be near-silent or produce a wall of
opinions nobody chose. The decision is which linters, and that is worth taking
deliberately rather than inheriting a default set.

Three answers, and any of them closes this:

- **Configure and gate it.** A `.golangci.yml` naming the linters this project
  wants, a `lint` gate, a job and a mutation control.
- **Defer it until the binary reaches the scanner.** This option's condition
  has been met: the pipeline, the ruleset and the hook entry that calls them
  have all shipped, so `spill-guard hook` scans a payload and blocks today.
  There is no longer a wait to defer behind, which leaves this as a choice
  between the other two.
- **Drop the pin.** If nothing is going to run it, carrying it in `go.sum` buys
  nothing and asserts something false.

What is not an answer is leaving it as it is, because that is the state that
reads as covered.
