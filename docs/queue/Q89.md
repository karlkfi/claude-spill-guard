# The reason inventory in `TestNoReasonNamesTheOverride` is hand-kept

`internal/hook/verdict_test.go` asserts that no reason this package emits names
`SPILL_GUARD_OVERRIDE`, because telling the model how to proceed without a scan
hands it the bypass. The assertion is right and its **population is a literal
slice somebody maintains**, so a reason helper added later is not covered and
nothing says so — the test still passes, and it passes for a smaller set than
its name claims.

**That premise is driven rather than asserted** — twice, on two branches by two
sessions, the arms differing only in whether the body is in the slice:

| `dumped()` made to name `SPILL_GUARD_OVERRIDE=` | in the slice | dropped from it |
|---|---|---|
| `go test ./internal/hook/ -run TestNoReasonNamesTheOverride` | **FAIL**, both leads | **PASS**, exit 0 |

So the crossing cannot tell a body it never iterates from one that is clean.

It has already under-covered four times, which is what makes this a row rather
than a caution:

- Q74 added `unread()` and the slice went on listing `found()` and `failed()`,
  with the comment above it opening "Neither reason" over three helpers. Caught
  by the author, on a prompt from a sibling rather than from a gate.
- Q73 added `confirmLead` and `noReasonGiven`, and widened the slice to four
  entries by hand. Same shape, one size larger.
- Q73's rebase onto the merged trunk wrote the lead-body crossing from the
  branch's own bodies, and `unread()` — on the trunk since Q74 — was not among
  them. Caught by the integration reading the trunk, again not by a gate.
- Q120 added `overran()`, the body a scan that overruns its budget blocks with,
  and the crossing went on listing four. Caught in review by a reader who
  compared the slice against the package, and the fix — one entry — covered
  both leads for free. **This one arrived after the row was filed**, which is
  worth more to whoever picks this up than the three above it: the row predicted
  that the next helper would be missed, and the next helper was missed.

None of the four shipped a reason that names the override. The defect is that
the checking was a person remembering, and the fourth is the instance that
shows the prediction was not merely plausible.

## The two it was still missing when this row was filed

Both have since been added, and the Q120 instance above went the same way:
found by a reader comparing the slice against the package, not by anything
running.

Both found by the reviewer reading the slice rather than by anything running,
which is the point. Enumerating them here saves the implementation re-deriving
them:

- **`confirmLead + failed(err)`** — reachable, and nobody had listed it: `Run`
  calls `decide(…, overridden, failed(err))` whenever a scan errors on an
  overridden call.
- **`refuse()`'s stderr reason** — outside the slice entirely, and one of two
  that interpolate a payload-controlled string (`clip(got.HookEventName)`).
  `failed()` is the other: `../../internal/hook/hook.go:424:reading the file this call would send`
  wraps a caller-supplied path into the error it formats with `%q`. Neither is
  a hazard — the escaping holds — but an implementation scoped to `refuse()`
  alone would miss half the class.

**That citation is right by coincidence, which is worth knowing before anyone
repoints it.** `reading the file this call would send` occurs **twice**, and
`queue.py lint` matches the fragment *at the named line* — so either occurrence
satisfies it and a repoint to the wrong one passes at `--citation-window 0`
saying nothing.

Both are inside `toolTargets`'s `Read` branch, thirty lines apart in the same
function, which is what makes them hard to tell apart from a line number alone:

| Site | What it follows | On `origin/main` |
|---|---|---|
| the one this row wants | `os.Stat(*in.FilePath)` | 393 |
| the other | `os.ReadFile(*in.FilePath)` | 423 |

`internal/hook/bash.go` is **not** a third candidate: its wording is "reading
**a** file this **command** would send", a different string. Note the path —
there is also an `internal/bash/` package, the segmentation port, and it carries
neither string.

**One function with the same string in two adjacent arms is a sharper hazard
than two surfaces would be**, and it is why this is in the row rather than in a
comment. An edit *between* the two shifts the second and not the first, so the
pair stops moving together — and at that point a pointer at either one still
matches its fragment, so nothing reports which it now names.

Read on `origin/main` on 2026-09-04. Both occurrences have so far shifted
together — measured by the Q120 lane at +21 on its own branch, and this row's
own pointer moved the same way — so a repoint landing on the first site does so
because the insertions happened to be above both, not because anything checked
which site it was. That is the ordering luck the paragraph above is about, and
it is not a property anyone should rely on twice.

So whatever derives the inventory has to name the `os.Stat` site by something
that distinguishes it — the preceding call, or the `fs.ErrNotExist` branch above
it — because matching the fragment cannot. Until then the row's pointer is the
next thing to go quietly stale, and it will still be green when it does.

Neither can leak the name today; both are compositions of covered parts or of
the caller's own text. Q73 has since replaced the flat slice with every lead
crossed against every body, plus `refuse` named separately, which is what
caught the first. That crossing is still hand-kept — the leads and the bodies
are both literals somebody maintains — so it moves the problem one level up
rather than closing it.

## The fourth and fifth happened in one afternoon, in two lanes that never saw each other

The `overran()` bullet above is one half of a pair. The other is
**`dumped()`**, the shape-refusal body Q108 added: it reaches `decide` under
both leads, and the crossing's body slice went on listing the same four. Two
sessions, neither reading the other's diff, both adding a reason body without
the crossing following, in the same afternoon.

Both were caught by a reviewer reading the change and repaired **after** the
commit that introduced them — read from the ref on 2026-09-04, `overran()` was
absent from the slice at `d9c5ba42` and present at `efbcdfd6` an hour later.
That is the instance rather than the end state: the property this test claims
held on neither branch at the moment its author believed the work was finished,
and every gate was green on both while it did not hold.

Neither named the override, so neither would have shipped a bypass, and every
instance this row records held because somebody remembered. `dumped()` is the
sharpest of them: its text names three commands a reader should run instead of
the one they wrote, which is deliberately the most instructional reason this
package emits, and therefore the body you would least want outside the check.

Two lanes stepping in the same hole on the same day, on two different bodies, is
the frequency argument this row did not have when it was filed.

**And those two produced a third case of a different kind.** Everything above
is a body *added* and not covered; `overran()` and `dumped()` also collide in
one merge, where taking either side drops an entry from the slice — so this one
is a body silently **removed** by a mechanical operation nobody performs
deliberately, and not reported. That distinction came from the session
integrating the batch, resting on the drive at the head of this row, which is
what makes *removed and not reported* a reading rather than a worry. It is the
only case here the batch produced rather than recovered, and it sets the bar: a
derived inventory has to survive a merge, not only somebody forgetting to add
an entry.

## Why a wider slice is not the fix

Four hand-kept entries fail exactly as two did. What the test needs is an
inventory it derives, and one that **refuses an input it cannot place** rather
than skipping it: an under-derived inventory reports the same green as a
complete one, and the check that would have fired is the one that went missing.

Two shapes worth costing before picking:

- **Over the package source.** Parse `internal/hook` with `go/ast` for string
  constants and reason-returning helpers, and require every one to be exercised.
  Derived, and it fails closed on a helper whose shape it does not recognise.
- **Over what the binary emits.** Drive `Run` across the payload classes that
  block and assert on every reason produced. Closer to the property, and its
  own completeness then depends on the payload list — which is a curated
  inventory again, one level out.

The first is the one that matches the claim, and the second is the one that
looks more end-to-end while covering less: it can only see a reason some
payload class actually reaches, so a helper that is wired up but unreachable
reads as covered. Every instance this row records happened to be reachable, so
this is not an argument against driving `Run` — it is the reason the row has to say which
shape the claim rests on rather than treating them as interchangeable. Have
both; rest the assertion on the first.

## The neighbouring case, same mechanism

`hook-attribution` requires the plugin name at position 0 of every emitted
string. Nothing gates that either, and it has the same population problem — so
whatever derives the inventory here should carry both assertions rather than
leaving the second to a second row. Q73 split the `spill-guard: blocked. `
opener into per-verdict leads, so there are now two openers where there was one
literal, and a third helper that forgets both is a silent failure.
