# `matchRule` chooses its arm inline, so no test can see which one ran

[`matchRule`](../../internal/scan/scan.go) picks between running a rule at its
prefilter hits and scanning the whole buffer for it. The two arms are required
to return identical findings — that is what the 824-finding differential in
`anchor_test.go` establishes — so **nothing but cost separates them**, and the
choice is made by an expression inline in the function. No test observes it.

The consequence is bounded and real: a rule that quietly stops taking the
anchored arm costs throughput and nothing else. Excluding one rule from the arm
leaves `go test ./internal/scan/ ./internal/rules/` at **exit 0** while the
ruleset's throughput falls. That exit code is the load-independent half and is
the whole of what this row rests on.

**How far it falls is not established, and no figure should be quoted until it
is.** This row first carried 36%, from a single run of the reviewer's; that run
also moved the whole-buffer arm from 7.21 to 2.79 MB/s, which the mutation
cannot touch because it removes one rule from the anchored path only. So the
machine changed under the measurement and the number went with it. It was
withdrawn, and re-taking it wants a quiet machine — this one has been between
load 10 and load 72 all day. A magnitude copies forward more readily than the
caveat attached to it, which is the hazard this store already records against
release notes in [Q132](Q132.md).

## What is already covered, so nobody re-adds it

`TestWhichShippedRulesRunFromTheirKeywordPositions` pins each rule's
eligibility boolean **and** its `Reach`, so a `reach+1` fails seven rows.
`TestEveryAnchoredRuleRefusesADenseHitListAndKeepsASparseOne` asserts both
budget arms for every anchored rule, so `budget()` returning 0 fails seven.
`TestReachIsTheLongestMatch` in `internal/rules` pins the computation.

Those went in with the change. **They do not close this**, and the drive says
so rather than the argument: with all three in place, putting
`rule.ID != "openai-api-key" &&` in front of the eligibility check leaves the
suite at exit 0. They assert `keywordPositions` and `Reach`; none of them
observes the arm `matchRule` takes.

## What would close it

**The arm is observable, and not by timing.** `testing.AllocsPerRun` over
`matchRule` reports **16.0** allocations for `aws-access-key-id` on a sparse
buffer and **3.0** with that rule excluded from the anchored path, because the
anchored arm builds a hit list and the whole-buffer pass does not. Driven
2026-09-04 on this tree, mutation applied and reverted. So the cheap close is a
test asserting that an anchored rule allocates more than the same rule forced
down the whole-buffer arm.

Assert the *direction*, not the count. 16 and 3 are this compiler's numbers and
a gate pinning them would fail on a Go bump for no defect — which is the
brittleness that makes an allocation assertion look like a timing one when it
is not.

The alternative, if the allocation route proves unstable, is to extract the arm
choice from `matchRule` into a predicate the test can call, so the condition is
asserted where it is decided rather than copied. Today `anchor_test.go`
recomputes `rule.Anchor != nil && boundedKeywords(...)` as its own expression,
which is the duplication that lets the two drift. That is the larger change and
it is why it is second here rather than first.

What is ruled out is a wall-clock assertion: this repo's own benchmarking rules
make one untrustworthy, and the throughput-only consequence does not earn a
flaky gate.

## Why it is not urgent

Every direction of this failure costs throughput. It cannot cause a missed
secret, a precision regression or a wrong verdict, because the fallback arm
reports byte-identical findings. Filed so it is not lost with the review that
found it.
