# Offer the output filter where a reader operand cannot be resolved

A reader whose file operand cannot be settled — a `$VAR` the string never
assigned, a glob this cannot expand, a relative path after a `cd` it cannot
follow — defers: the call goes through unscanned and a coverage record is
written. `spill-guard filter` now exists and reads the command's output, which
is what crosses, so any of those calls could be refused toward
`set -o pipefail; <command> | <binary> filter` the way a recursive grep is.

**This is a reversal of the 2026-09-05 decision for a class, and needs the
measurement that made it.** That decision was that 94.3% of blocks were
coverage failures and the next call got through within four attempts 99.2% of
the time; a refusal that names the filtered form costs one turn rather than
four and a prompt, which is a different trade from the one measured.

What decides it:

- The coverage log split by reason once Q200's records name the operand, and
  how many of those calls write output the model reads rather than to a file.
- Which readers it is safe for. A filter withholds the whole output on a
  finding, so `cat $F | spill-guard filter` and `sed -n 1p $F | …` are fine,
  and a reader whose exit status a session tests (`diff`, `cmp`) loses it to
  the pipe in the same way grep's `-q` would have.
- Whether `jq` and `yq`, whose operands are usually literal and already
  scanned whole, are worth a row entry at all: they defer only when the
  operand is a variable.

Filed from the session that built the filter (Q203), on a question asked
during it rather than anything measured.
