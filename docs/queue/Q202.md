# A valid quote idiom inside `$(…)` fails to parse, so the call is unread

A command bash accepts is rejected by the segmenter as unclosed, and the
whole call defers, so every reader in it goes unscanned rather than the one
segment carrying the idiom. Driven 2026-10-01 on v0.5.0, each command checked
with `bash -n` first:

| Command | Result |
|---|---|
| `printf 'a'"'"'s b'; cat w/a.txt` | resolves |
| `echo "$(printf 'a'"'"'s b')"; cat w/a.txt` | defers: `no closing quotation` |

The `'"'"'` idiom is how an apostrophe gets into a single-quoted string, and
sessions write it inside `"$(printf …)"` for commit messages. The difference
between the two rows is the enclosing double quote around the substitution,
so the lexer is likely reading the inner `'` under the outer `"` rather than
starting fresh at `$(`.

Nine of 2,400 coverage records (0.4%) from 2026-09-07 to 2026-10-01 are this
reason. The class is small, and each one costs the whole call, including a
`cat` the parse failure has nothing to do with.

Drive the same pair through `claude-workspace-guard` first. The segmenter is a
port, so if upstream fails the same way the fix is upstream's and is ported
here.
