# Nothing retires a release-scope record when its tag is cut

`docs/plan/<tag>.md` says what a release is for, and it is read before the tag.
After the tag it is a document naming a version that exists, asserting that
version is still ahead — which is the one failure mode the arrangement was
shaped to avoid. `docs/development/release-process.md` now carries the deletion
under *Publishing the draft*, and that is the whole of the enforcement: a step
somebody performs by reading it back.

The runbook says so in its own words —
`development/release-process.md:174:Nothing checks this. It is a step somebody performs by reading it back`
— and that sentence is the row. This repository has priced the same
construction twice in one week: *Nothing checks this at tag time* stood over
the plugin manifests until #87 gated them and deleted the line, and the release
job's eight asset assertions sat on top of a draft with an empty body until
#85. Both were invariants stated in prose beside the person expected to honour
them.

**The asymmetry is what makes it worth a gate rather than a reminder.**
Forgetting the deletion leaves a stale plan doc that reads as current and
nothing reports it, so the failure is silent and permanent. Performing it when
there is nothing to delete costs a `git rm` that fails loudly. Only one
direction has a symptom.

## What the check reads

The same two facts `check-release-claims.py` already reads — whether a release
exists, and what the tracked tree says — one join further on: a
`docs/plan/vX.Y.Z.md` whose version `gh release list` reports as released is a
finding, and so is a row still carrying the matching `vX.Y.Z` label. Both are
decidable from the release list plus the tree, which is what puts this in the
tier a gate can hold rather than the tier a person has to.

The release job is the wrong place for it. A tag that has just published *has*
a plan doc, legitimately, because the deletion is a step after publishing — so
a check there fails every correct release. It belongs on the pull request that
takes the deletion, which is where `release-claims` already reads real release
state and where the previous tag's record is the thing under review.

## Two things it must not become

- **A gate that fails a fresh clone.** `release-claims` reads `gh release list`
  and this would too, so it inherits whatever that gate does about a machine
  with no network or no `gh`. Match it rather than inventing a second answer.
- **A gate with no mutation control.** Every gate here is paired with a job
  that breaks the property and requires red, and a check over an *absence* is
  the shape that most easily passes for the wrong reason — a run that found no
  `docs/plan/` at all reports clean exactly as a correctly retired one does.
  The control has to plant a stale plan doc and require the finding by name.
