# A command prefix on a reader hides its operands from the scan

A reader run through a wrapper that execs its argument has its file allowed
unread. `cat aws-access-key-id.env` in `testdata/corpus/planted` is denied, and
each of these reads the same key and exits 0 with no verdict and nothing on
stderr -- no finding and no coverage record:

| Command | bash prints the key | Verdict |
|---|---|---|
| `cat aws-access-key-id.env` | yes | deny |
| `command cat aws-access-key-id.env` | yes | none |
| `command -p cat aws-access-key-id.env` | yes | none |
| `exec cat aws-access-key-id.env` | yes | none |
| `nice cat aws-access-key-id.env` | yes | none |
| `nohup cat aws-access-key-id.env` | yes | none |
| `time cat aws-access-key-id.env` | yes | deny |

Driven 2026-09-26 with `SHELL=/opt/homebrew/bin/bash` on a build of #181's
head. `command cat` answers the same on v0.4.1, so it is not that PR's
regression; the review of #181 surfaced it beside Q195. `time` is covered
because `lex.go` peels it as a reserved word.

The command name is the wrapper, which has no row in `internal/readers`, so
the segment contributes no operands. The design states that a command with no
row contributes none, but that limitation was written about programs that
open files by their own logic, and these open nothing: they run the next word
as the command. Peeling them before the reader lookup is the likely fix, with
each wrapper's own flags (`command -p`, `nice -n 5`, `exec -a name`) skipped
the way `altersGlobbing` now skips `command`'s.

Before choosing the list, read what `claude-bouncer`'s workspace-guard peels.
The segmentation is a port kept structurally identical, so a peel it already
has should be taken from there rather than written here. `env`, `sudo`,
`xargs` and `timeout` are the same shape with argument grammars that are
harder to skip; measure which of them real traffic carries before deciding
whether they are in scope or recorded.
