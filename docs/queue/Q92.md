# A quoted assignment arms the override where bash would not

Blocked by [Q100](Q100.md), which files the same defect against
`claude-bouncer`. The fix belongs in the shared lexer, not here — see
**Checked upstream** below. The one half not waiting on that is widening
`TestAQuotedAssignmentInCommandPositionArmsTheHatchToo`, which under-describes
the behaviour it pins and can be done at any time.

`internal/hook/override.go` finds the hatch by taking the tokens
`bash.StripEnvPrefix` drops off the head of a segment. Those tokens have already
been through the lexer, which strips quotes, so `assignmentRE` matches a word
bash would never have treated as an assignment:

    'SPILL_GUARD_OVERRIDE=x' cat .env      arms the hatch
    "SPILL_GUARD_OVERRIDE=x" cat .env      arms the hatch

bash reads a **quoted** word in command position as a command *name*. Neither of
those sets a variable; both try to run a program called
`SPILL_GUARD_OVERRIDE=x`. The hook sees a prefix where the shell sees a command,
so the two disagree about what the call even is.

## The class is wider than those two, driven 2026-08-31

The two spellings above were the ones somebody wrote down. Deriving the
signature instead — and driving `override()` rather than reading it — the rule
is that quoting any character of the **name** makes the word a command, while
quoting inside the **value** leaves it an assignment. bash 5.3.15:

```
SG_OVR=x env             set    -- an assignment
'SG_OVR=x' env           --     command not found
"SG_OVR=x" env           --     command not found
SG_OVR='x y' env         set    -- an assignment
'SG'_OVR=x env           --     command not found
SG_OVR=x"y" env          set    -- an assignment
```

`override()` arms on every one of the six, so it is wrong on three rather than
two: `'SPILL'_GUARD_OVERRIDE=x` and `SPILL_GUARD_OVER''RIDE=x` are the ones no
test names. It is right about the two value-quoting forms, which matter because
they are the ones a fix must not break — `SPILL_GUARD_OVERRIDE='a reason with
spaces'` is the documented way to write a reason.

A third shape is looser rather than wrong: a prefix inside a subshell segment
arms the whole call, though `Segment.Persists` is false there and the assignment
would not survive into the next command.

## Why it is bounded, and why it is still worth closing

The destination is a confirmation, never an allow, so the worst case is a prompt
where there should have been a block. Nothing is sent without somebody
approving it. That is why this is a row rather than a defect on the PR that
introduced the hatch.

It still matters, because the stated defence of command-position-only is
**legibility**: the override sits in the command the human is being asked to
approve, and a reader can see it. These are spellings no reader would call an
override, and one of them is a plausible thing to type by accident when quoting
a value.

## Why it was pinned rather than fixed

Recovering the distinction needs to know whether a token was quoted, and that
information is gone by the time `override()` sees it. Restoring it is a change
to `internal/bash`, which `CLAUDE.md` holds structurally identical to its
`claude-workspace-guard` upstream so a fix there transfers by inspection.
Diverging it for this is a decision, not a patch — and the same tokens feed
`internal/readers`, so a change reaches operand resolution too.

`TestAQuotedAssignmentInCommandPositionArmsTheHatchToo` pins both spellings, so
the behaviour is deliberate and a change to it is a decision rather than a
regression somebody discovers.

## Checked upstream, and it does have it

Driven 2026-08-31 against `plugins/prod-guard/scripts/bash-prod-guard.py`:
`'PROD_GUARD_OVERRIDE=x' cmd` and `"PROD_GUARD_OVERRIDE=x" cmd` both arm its
hatch, because its lexer strips quotes before `extract_env_prefix` matches
`ASSIGNMENT_RE`. Same defect, same cause, and the regex is shared out of
`lib/bouncer_parse.py`, so a fix there reaches all five guards.

So this is a `claude-bouncer` finding before it is a change here, exactly as this
row anticipated, and [Q100](Q100.md) carries the measurement for that filing.

**This row is now blocked on that fix landing upstream**, rather than on anyone
deciding anything here. `CLAUDE.md` holds `internal/bash` structurally identical
to its `claude-workspace-guard` upstream so a fix transfers by inspection;
writing a divergent one here to close this row would cost that property to buy a
confirmation prompt that was never an allow.

### A partial fix would pass the documented cases and fail the undocumented ones

Worth knowing before anyone writes the fix, because it inverts which spellings
are load-bearing. Driven by mutating `internal/bash/lex.go` to retain a closing
quote rather than drop it — one plausible shape of "keep quote provenance" —
and running the widened pin:

```
'SPILL_GUARD_OVERRIDE=x' cat f    still arms   (lexes to SPILL_GUARD_OVERRIDE=x')
"SPILL_GUARD_OVERRIDE=x" cat f    still arms
'SPILL'_GUARD_OVERRIDE=x cat f    no longer arms
SPILL_GUARD_OVER''RIDE=x cat f    no longer arms
```

The quote lands in the *value* for the two spellings this row names, so the
assignment shape still matches and the hatch still arms; it lands in the *name*
for the two it does not name, so those stop. A fix of that shape would leave
both documented spellings broken and look like it had worked. Which is the
argument for the widened pin: the two subtests added for the undocumented forms
are the only ones that discriminate under it.

`TestAQuotedAssignmentInCommandPositionArmsTheHatchToo` pins the behaviour, and
before this it pinned a strictly narrower version of it than the tree has — it names the two
quoting-the-whole-word spellings and neither of the partial ones. Widening it is
worth doing whenever this is picked up, even if the fix is still upstream's,
because a pinning test that under-describes the behaviour makes a later change
look smaller than it is.
