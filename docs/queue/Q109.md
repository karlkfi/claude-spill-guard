# Re-drive the prompt oracle in CI, which needs no credential

`internal/hook/testdata/prompt-oracle.json` is the harness's own answer to the
`@`-token grammar, and a test compares the resolver against it on every `go
test`. What nothing does is re-take it. The fixture was driven on 2026-08-28
against Claude Code 2.1.238; every run since has compared the resolver to that
recording rather than to the harness.

So the fixture cannot drift from the resolver — that is gated — and it drifts
silently from the thing it stands in for. A grammar this project does not own
is pinned by a file nothing re-derives.

## It is cheap, which is what [Q94](Q94.md) measured

2026-09-01 against 2.1.251: all 24 cases replay under `claude -p` with a clean
`HOME` holding no credential, at 3.63s a case and 87s for the set, and 24 of 24
agreed with the recorded `harness_files`. The run never authenticates — it
reports `Not logged in · Please run /login` and bills nothing — because the
harness resolves `@` tokens and writes the transcript before it makes an API
call.

A fork's pull request gets no secrets. This needs none, so it is not one of
those jobs.

What is not measured is how a runner gets the binary. This machine's is a
native executable under `~/.local/share/claude/versions/`, installed by hand
and not an npm global, so the install channel is this row's first step rather
than a detail — and it is the step that decides whether the job can run on a
fork at all.

## What the job does

Install the binary, rebuild the fixture's tree, replay each case's prompt, read
`attachment.type == "file"` out of the session transcript, and compare the set
against `harness_files`. The only thing it can report is the fixture having
gone stale against the harness, which is the whole reason to run it.

Three things it needs that a local drive did not:

- **A version in the data.** The fixture carries `name`, `prompt`,
  `harness_files`, `resolver_also_scans`, `harness_also_splices`, `why` and
  `note`, and no field naming the harness it was taken against. That version is
  a Go comment — `internal/hook/prompt_test.go:123:Driven 2026-08-28 against
  2.1.238` — so nothing can say which two versions a disagreement is between.
  Give the fixture the field, and have the job record what it ran.
- **A floor, for the reason the Go test already has one.**
  `internal/hook/prompt_test.go:62:if len(cases) < 10 || spliced < 10` refuses
  a run with too little in it to mean anything. A replay that drove nothing —
  a binary that failed to install, a `HOME` the harness would not write under —
  agrees with all ten of the cases that expect an empty splice and reports
  green. Assert the 14 non-empty cases and the 33 files, and fail on a shortfall
  rather than passing.
- **A pinned version, not `@latest`.** The job exists to report drift between
  a recorded version and a named one. Resolving the binary to whatever shipped
  that morning makes a red run un-attributable and a green one un-repeatable.

## What it cannot cover

The `Read` and `Bash` surfaces, for [Q94](Q94.md)'s reason: those reach a hook
only once the model has chosen a tool call, which is an API call, which needs a
credential. Across 25 unauthenticated runs `PreToolUse` fired zero times. A job
over this surface is not a job over the class, and saying so in the design doc
is what Q94 keeps.
