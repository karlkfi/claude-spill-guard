# `private-key-block` misses three PEM formats it appears to cover

The rule requires a base64 body line on the line after the PEM header, which is
what stops it reporting prose that quotes a header. An RFC 1421 encrypted
key — the PKCS#1 form OpenSSL writes with `-p` — puts its own headers in
between:

```
-----BEGIN RSA PRIVATE KEY-----
Proc-Type: 4,ENCRYPTED
DEK-Info: AES-128-CBC,7A1B2C3D4E5F60718293A4B5C6D7E8F9

QUJDREVGR0hJSktMTU5PUFFSU1RVVldYWVowMTIzNDU2Nzg5YWJjZGVmZ2hpamts
```

The next line is `Proc-Type:`, so the clause finds no base64 and the key is not
reported. Measured through the compiled rule, four cases, both arms marked so
neither can be a silent no-run: plain and CRLF match, prose correctly does not,
RFC 1421 does not and should.

It is a common path rather than an exotic one: `ssh-keygen -q -t rsa -N <pass>
-m PEM` writes exactly that header pair, measured here, so it is not only
`openssl -p`.

**A PKCS#8 encrypted key is fine**, which is worth stating because the
alternation enumerates `ENCRYPTED ` and that reads at a glance like the whole
encrypted case is broken. `-----BEGIN ENCRYPTED PRIVATE KEY-----` has base64
straight after it and the rule matches.

**Two further arms match nothing their toolchain emits, and both predate the
body-line clause** — they miss on a bare header too, so they have been dead
since the rule was written. Each alternation arm run against the header its
real toolchain produces:

| Arm | Verdict |
|---|---|
| `RSA ` (PKCS#1), PKCS#8 plain, PKCS#8 encrypted, `OPENSSH ` | match |
| `SSH2 ENCRYPTED ` | miss |
| `PGP ` | miss |

`SSH2 ENCRYPTED ` cannot reach RFC 4716 armor, which is four dashes with inner
spaces where the rule requires five and none. Measured: `ssh-keygen -e -m
RFC4716` emits `---- BEGIN SSH2 PUBLIC KEY ----`, byte-checked with `od -c`.

`PGP ` cannot reach `-----BEGIN PGP PRIVATE KEY BLOCK-----`, because the rule
requires `PRIVATE KEY-----` and real armor carries ` BLOCK` before the dashes.
**Spec-derived rather than measured — `gpg` is absent on the machine this was
taken on**, so weight it below the SSH2 line and confirm before acting.

**Keep the two dead arms.** Deleting them looks like a free no-op and is not:
the five-dash spellings they describe *would* match if anything wrote them, so
removal is a judgement about what real toolchains emit rather than a proof.
And the trade is one-sided. With the body-line clause in force, all an arm can
add is `-----BEGIN <X> PRIVATE KEY-----` followed by base64 — which is a key
block, or a document displaying one. The second is the Q60 class that every
other arm already carries, so these two add **no precision risk that is not
already tracked**. Deleting something that costs no precision, to buy tidiness,
on an unprovable negative, is the wrong trade in a repo that ranks precision
first.

So this row is about the widening only. The arms stay, and `rules/README.md`
says they are dead, which is where a reader would otherwise over-read the
coverage.

## Why this is a row and not a fix

It is recall, and this repo ranks recall below precision on the stated grounds
that a missed secret gets reported by whoever missed it while noise trains
everyone to stop reading the output. It is also not a regression: nothing on
`main` matched an encrypted key before the rule existed.

The candidate is a bounded lazy window instead of an immediate newline, which
is RE2-clean and leaves group 1 alone:

```
[\r\n][\x20-\x7e\r\n]{0,200}?[A-Za-z0-9+/=]{32,}
```

It fixed all four cases with the full gate still at exit 0. What it has not had
is a precision reading: it lets up to 200 bytes sit between the header and the
base64, so a document that quotes a header and then shows any 32-character
base64-ish run within 200 bytes becomes a finding. The corpus cannot answer
that today, which is the actual work here rather than the regex.

So: take the reading first. Add an RFC 1421 fixture to
`testdata/corpus/planted/`, widen, and check the clean half still reports zero
— including `testdata/corpus/clean/tls-runbook.md`, which exists to hold this
rule down and is the file a widening would break first. If the widening cannot
keep the clean half at zero, the narrow clause is the right rule and this row
closes by saying so in `rules/README.md`.

proposed — which is the argument for driving a proposed fix against cases its
author did not pick.
