# `private-key-block` misses an RFC 1421 encrypted key

The rule requires a base64 body line on the line after the PEM header, which is
what stops it reporting prose that quotes a header. An RFC 1421 encrypted
key — the PKCS#1 form OpenSSL writes with `-p` — puts its own headers in
between:

```
-----BEGIN RSA PRIVATE KEY-----
Proc-Type: 4,ENCRYPTED
DEK-Info: AES-128-CBC,7A1B2C3D4E5F60718293A4B5C6D7E8F9

QUJDREVGR0hJSktMTU5PUFFSU1RVVldYWVowMTIzNDU2Nzg5YWJjZGVmZ2hpamts
```

The next line is `Proc-Type:`, so the clause finds no base64 and the key is not
reported. Measured through the compiled rule, four cases, both arms marked so
neither can be a silent no-run: plain and CRLF match, prose correctly does not,
RFC 1421 does not and should.

**It is only the PKCS#1 form.** A PKCS#8 encrypted key opens
`-----BEGIN ENCRYPTED PRIVATE KEY-----` with base64 straight after, and the
rule matches it — verified rather than assumed, because the rule's alternation
enumerates `ENCRYPTED ` and that reads at a glance like the whole encrypted
case is broken. It is not. The gap is the `RSA ` arm carrying RFC 1421 headers.

## Why this is a row and not a fix

It is recall, and this repo ranks recall below precision on the stated grounds
that a missed secret gets reported by whoever missed it while noise trains
everyone to stop reading the output. It is also not a regression: nothing on
`main` matched an encrypted key before the rule existed.

The candidate is a bounded lazy window instead of an immediate newline, which
is RE2-clean and leaves group 1 alone:

```
[\r\n][\x20-\x7e\r\n]{0,200}?[A-Za-z0-9+/=]{32,}
```

It fixed all four cases with the full gate still at exit 0. What it has not had
is a precision reading: it lets up to 200 bytes sit between the header and the
base64, so a document that quotes a header and then shows any 32-character
base64-ish run within 200 bytes becomes a finding. The corpus cannot answer
that today, which is the actual work here rather than the regex.

So: take the reading first. Add an RFC 1421 fixture to
`testdata/corpus/planted/`, widen, and check the clean half still reports zero
— including `testdata/corpus/clean/tls-runbook.md`, which exists to hold this
rule down and is the file a widening would break first. If the widening cannot
keep the clean half at zero, the narrow clause is the right rule and this row
closes by saying so in `rules/README.md`.

Found by review on Q7's pull request, in a patch that same review
proposed — which is the argument for driving a proposed fix against cases its
author did not pick.
