# Resolve an operand from a literal assignment in the same command

`resolve` refuses any operand carrying `$` or a backtick —
`internal/hook/bash.go:273:strings.ContainsAny(operand, "$`")` — because the
value is not this process's to know. That is right for a variable the shell
inherits and wrong for one the command string assigns two segments earlier,
where bash and this hook are reading the same literal.

**Measured 2026-09-04** over 1,802 session transcripts on this machine, in the
131 that carry a spill-guard denial: 393 calls were refused, 135 of them on
this arm. Of the 137 recovered commands on the arm, **86 assign a literal path
to a variable earlier in the same command string and then use that variable
inside a path-shaped token** — the shape bash resolves without consulting
anything outside the string. The other 51 read a variable the string never
assigns, and those stay refused.

The commonest instance is a session writing its own scratchpad path down once:

```
SP=/private/tmp/claude-501/<project>/<session>/scratchpad
python3 -m unittest … > "$SP/unit.log" 2>&1; rc=$?; tail -30 "$SP/unit.log"
```

The `tail` is refused, so the whole call is, so the test never runs. That path
is the per-session tree Claude Code hands the session, which the sibling guard
in the same marketplace read/write-exempts outright.

## The mechanism is a port, not a design

`claude-workspace-guard` already does this, and the segmentation layer under
`internal/bash` is a port of the same upstream. Its resolver carries
`literal_assignment_value`, `substitute_vars`, `apply_assignment_group` and
`poison_vars` — the last being the half that matters here. A variable assigned
from a substitution, from another variable, or from anything the string does
not settle is *poisoned* rather than guessed at, and a poisoned variable
refuses exactly as today. So the fail-closed direction is the port's own, not
something this repo has to add on top.

Take `poison_vars` with the rest or leave the whole thing. A port that
resolves the easy assignments and quietly guesses at the rest scans a file the
command never opens and reports the call clean, which is the failure the arm
exists to prevent, arriving through the fix.

## What decides it

The bite rate is 86 refusals in two days of one machine's sessions, all of them
on read-only inspection during ordinary code reading, and none of them a call
this scanner could have found a secret in. Precision is the product here, and a
false refusal is a precision defect that spends a person's attention rather
than a reviewer's.

What would refute the row: an `argv[0]`-shaped divergence between what
`substitute_vars` resolves and what bash does, found by driving the ported
resolver against real assignments rather than by reading it. Drive it before
shipping it — the segmentation port has [Q63](Q63.md) open for exactly the
question of nothing re-checking it against upstream.
