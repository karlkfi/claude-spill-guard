# A `$(…)` in a stage before the grep filter reads the matches around it

`grep -rn deploy . | grep -v "$(cat >&2)" | spill-guard filter` gets no verdict from the hook, and running it puts the matched lines on stderr, which the `Bash` tool returns to the model.
Driven 2026-11-27 under bash 5.3.15 with a planted key the filter withholds, on binaries built from `main` at 01e2f9d and from the branch that closed Q264:

| Command | `main` | Q264 branch | Run |
|---|---|---|---|
| `grep -rn deploy . \| grep -v "$(cat >&2)" \| spill-guard filter` | no verdict | no verdict | key on stderr |
| `grep -rn deploy . \| grep -v "x$(cat >&2)" \| spill-guard filter` | no verdict | no verdict | key on stderr |
| `grep -rn deploy . \| grep -v nomatch \| spill-guard filter` | no verdict | no verdict | key withheld, rc=3 |

A command substitution in a pipeline stage is expanded in that stage's subshell, whose stdin is the pipe, so its body reads the grep's output.
Q264 found the same thing of a `<(…)` body (`echo hi | cat <(cat >&2)` prints `hi` on stderr) and closed it by reading the body's segments as stages, which works because `bash.Segments` emits a process substitution's body as segments of its own just ahead of the stage.
A quoted `$(…)` is not split that way: the probe printed `["grep" "-v" "$(cat >&2)"]` as one stage token with no body segment, and a backtick body is the same.
So `copiedAround` in `internal/hook/grep.go` never sees the `cat`: of a stage's arguments it reads only `tee`'s, `dd`'s and what `passThrough` checks.
The same construct inside a `<(…)` body is closed already: Q264's review found `| grep -f <(echo "$(cat >&2)") |` leaking, and `substitutedAround` now refuses a body token holding `$(`, a backtick or a bash 5.3 `${ …; }`. What is left is the stage's own arguments, and the review found `${ …; }` there too: `grep -v "${ cat >&2; }"` as a stage argument gets no verdict, by its drive and not re-taken here.

The fix is a reading of a downstream stage's tokens for a substitution body, refused outright or read the way `substitutedAround` reads a `<(…)` body; the hook already marks substitution bodies elsewhere (`substStates` in `internal/hook/bash.go`), which may be the place to get them from.
Traffic is unmeasured.

**Done** when both `$(cat >&2)` rows are refused, the `grep -v nomatch` control still gets no verdict, and a backtick body and a `${ …; }` or `${| …; }` body are covered too.
