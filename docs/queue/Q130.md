# PRIVACY.md's read list was written from the design, not from the code

`PRIVACY.md`'s **The scanner** section lists what the hook reads. One of its
five bullets is right. The list is published as it stands at `v0.1.0` and at
`v0.2.0`.

| The bullet | What the code does |
|---|---|
| the tool call's arguments from the hook payload | correct |
| the file named by a `Read`, or by a file operand of a common reader in a `Bash` command | correct, and incomplete: `internal/hook/prompt.go` opens the `@` target of a prompt too |
| `rules/spill-guard.json` shipped with the plugin | false. `rules/embed.go` compiles it in, and `scanCall` uses `embedded.Shipped` |
| `.claude/spill-guard.json` under the project root, when it exists | false. `scanCall` passes a nil override, and `rules.LoadFiles` — the only function that opens either path — has no caller outside `internal/rules/load_test.go` and `internal/scan/corpus_test.go` |
| the `SPILL_GUARD_*` environment variables | imprecise, in the direction that matters. The launcher reads `SPILL_GUARD_BIN`; the binary reads no environment variable at all |

Four are wrong, and the two outright false ones are not the two that cost a
reader most.

**The omitted `@` target is the one a privacy document most owes its reader.**
Typing `@deploy.env` splices a file into the model's context, and
`UserPromptSubmit` is where the hook opens it — a real read of a real file on
disk, absent from the list of files it reads.

**The environment bullet inverts a property the code went out of its way to
have.** `SPILL_GUARD_*` reads as including `SPILL_GUARD_OVERRIDE`, and
`internal/hook/override.go` refuses that read by name: an exported variable and
a `settings.json` `env` block are both durable, both silent and both writable
by the model, so an environment read "would turn a per-call hatch into a
standing one that nothing reports". The hatch is command-position only. A
reader auditing the escape hatches is told the opposite of what the design
says about them.

The `.claude/spill-guard.json` bullet is the one with a user behind it.
`rules/README.md` says plainly that nothing reads the file yet, but that is the
page a rule author reads; this is the page somebody reads while deciding
whether to trust the tool, and it tells them their project config is honoured.
A user who writes that file to catch their own token format gets a scanner
that reports the clean result it would have reported anyway.

**Nothing checks any of it.** `git grep -n PRIVACY -- scripts Makefile .github`
returns no match, so no gate reads this file and neither `status-drift` nor
`release-claims` covers it. The list has been wrong across two releases with
every gate green.

## What to build

Rewrite the list against what `scanCall` opens, then gate it — a list corrected
by hand goes stale the way this one did. `status-drift` is the precedent worth
reading first: it holds the README's status table against what the tree can
actually do, and this is the same shape one document over.

## Not the same row as Q73

[Q73](Q73.md) retires the project ruleset, which makes the fourth bullet
permanently wrong rather than merely wrong now. Different mechanism — that row
