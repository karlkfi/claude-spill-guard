# Card rules need a placeholder denylist beside the Luhn check

Found while building `internal/validate`. Luhn is a transcription check, so it
accepts every number that was *constructed* to pass one — and the numbers a
scanner meets most often were.

`0000000000000000` passes. So does `4111111111111111`, which is the Visa test
number in Stripe's docs, in every payment gateway's sandbox page, and in the
fixtures of anything that has ever taken a card. `5555555555554444` and
`378282246310005` are the Mastercard and Amex equivalents and pass too. All
four are pinned as passing in `internal/validate/validate_test.go`, so this is
measured rather than suspected.

A card rule shipping `validators: ["luhn"]` therefore flags every payments
README in the repo it scans. That is precisely the shape the inherited ruleset
failed on: a check that looks discriminating, a rule that fires on
documentation, and a user who stops reading the output.

## What this is not

Not a change to `Luhn`. The function is right — it answers the question it
claims to answer, and a card rule is not the only thing that will ever want a
Luhn check. The denylist is a second validator the card rule names as well.

Source the list from the published test numbers each network documents, plus
the degenerate runs (a single repeated digit, and any candidate whose digits
are all zero). Both directions get a table, as `Q6` established: a denylist
with only positive cases silently grows into one that suppresses real cards.
