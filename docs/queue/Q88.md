# A directory splice is assumed one level deep and never driven

`@a/directory` in a prompt does not splice file contents. It splices an
attachment whose `attachment.type` is `directory`, carrying the entry names —
measured 2026-08-28 on 2.1.238, where `@nested` produced exactly
`inner.txt\ndeep` for a directory holding a file and a subdirectory. Those
names crossed, so `internal/hook/prompt.go` scans them, and it builds the
buffer with a plain `os.ReadDir`.

That is one level, and one level is what the measurement showed — for a
directory with two entries, one of them a subdirectory whose own contents did
not appear. What it does not show is what happens on a tree the harness might
decide to walk further, or on one large enough to trip a bound the way the
2,000-line file truncation does. The direction that matters is the one that
under-reads: if the harness lists more than `os.ReadDir` returns, names cross
that nothing scanned, and the run reports clean.

The reading is cheap and the shape is already built. Drive `@path` at a
directory holding a nested tree and at one holding several hundred entries, in
the throwaway project Q77 used, and read the attachment's `content` out of the
transcript. Then either the one-level assumption is confirmed and gets a
sentence saying so, or `listing` grows a walk.

Two things to hold on to while doing it:

- **The case is already declared as a divergence in the oracle**, in
  `internal/hook/testdata/prompt-oracle.json`, because a census over `file`
  attachments cannot see a `directory` one. So a new measurement here changes
  the `resolver_also_scans` entry rather than adding a case that agrees.
- **`os.ReadDir` does not filter and the harness may.** Where the harness
  leaves an entry out, this reports a name that did not cross, which is the
  cost side and not a defect to chase.
