# Decide what to do about pointers that describe the merged tree

Q45 promoted `stale-citation` to bind on every event. `--strict` names a class
and the class is four separate checks, so promoting the one that matters
promoted three others with it. Found in review of that PR, twice — the first
pass caught that the promotion's stated reason was false, and the second caught
that its replacement was still wrong.

## What the four arms do

`queue.py lint` emits `stale-citation` for four conditions. The axis that
matters is not which arm fired but **who moved the line**, and that cuts across
all four:

- **Your own diff moved it.** The citation was correct when written and your
  branch's edits invalidated it. Your branch goes red, you re-point it, done.
  This is what promotion buys and it is the whole of what promotion buys.
- **A sibling branch moved it.** Your branch is green, because the citation is
  correct against the tree in front of you. `main` reddens on the merge. No
  event split reaches this: the merged tree is the first place it is visible.

Measured 2026-08-26 on Q45's branch against live PR #28, which edits
`scripts/check-doc-links.py`:

| cited | on this branch | with #28's file present |
|---|---|---|
| a fragment only #28's version carries | exit 2, `no longer carries` | exit 0 |
| the fragment at #28's line number | exit 2, `which is now at line 96` | exit 0 |
| the fragment at this branch's number | exit 0 | exit 2 |

And self-inflicted drift, same tree: a citation exact at
`exhibit:scripts/gates.py:40` exits 0, and exits 2 with `now at line 60` once
twenty lines are inserted above it on the same branch. Marked, because it is a
record of a drive rather than a pointer this row depends on, and `gates.py` is
a file an ordinary PR edits.

## No arm split helps, which is what two review passes established

The obvious fix is to sort the arms: demote the ones a sibling can flip, keep
the ones the branch settles. That was this row's first draft, and it does not
work, because **all four arms behave identically**. Every one of them can fire
on a pointer correct about the merged tree and wrong about the branch carrying
it — the `dangling-link` shape — and every one can stay silent on a branch and
redden `main`.

Measured on this branch against live #28, which edits
`scripts/check-doc-links.py`. Each row cites something correct about the merged
tree and absent from this one:

| what is cited | on this branch | with #28's file present |
|---|---|---|
| a file #28 adds | exit 2, `does not resolve` | exit 0 |
| a line past this tree's copy | exit 2, `past the end` | exit 0 |
| a fragment #28 adds | exit 2, `no longer carries` | exit 0 |
| the fragment at #28's line number | exit 2, `now at line 96` | exit 0 |

The first draft of this row put "no" in the last two rows and its own measured
evidence, two paragraphs above, already contradicted it. The reason is simple
once stated: `lint` sees one tree. Which arm fires depends on *how* the two
trees differ. Whether the branch or the trunk reddens depends only on which
tree the author wrote against, and the checker cannot know that.

## What to do instead, and it is an open question

Arm-granular `--strict` is still a reasonable thing for `queue.py` to have —
`NOTE_CLASSES` already argues a caller must not inherit a promotion it did not
ask for, and that holds inside a class as well as across them. It just does not
solve this, and should not be filed as though it does.

What would solve it is a way for a row to say *this pointer is about the merged
tree, not this branch*. `exhibit:` is the nearest thing and it is the wrong
tool: it means "this pointer is my subject, never check it", so using it here
overloads the marker and never expires — the pointer stays unchecked after the
sibling lands, which is exactly when checking it would start working. A
distinct, expiring marker is the shape to consider.

Choosing between "add a marker" and "accept the cost and document it" is the
ask. Accepting is defensible: the failure is loud, it names the file, and a
contributor who hits it can mark the pointer and move on.

`queue.py` is vendored, so any change is upstream work in `session-backlog`
plus a `make vendor` refresh; `scripts/README.md` pins it by digest and the
`vendor` gate fails an edit in place.

## The instance already filed against this

[Q64](Q64.md) is a defect on the unresolvable arm: `CITATION_RE`'s leading `\b`
drops the dot from a dotfile path, so a citation into `.github/workflows/`
resolves from nowhere and is reported stale whatever its line says. Under Q45
that reddens the branch filing the row. Landing this row first demotes that arm
to merged-only, which turns Q64 back into a note on a branch — the defect
unchanged, the urgency lower. [Q30](Q30.md) settles `--citation-window`, which
reaches neither of the two arms this row moves.

## What it does not fix

Nothing here closes the hole Q45 narrowed. A sibling that moves a cited line
still leaves a branch green and reddens `main` on the merge, whichever arm
fires and however `--strict` is spelled. `MERGED=true` on the trunk is what
catches that, and it catches it one merge late by construction.
