# A cd run through eval is not followed

`eval cd w; cat x` reads `w/x` in bash 5.3.15, and the hook resolves `x`
against the directory the call started in. With the key in `w/x` the call
crosses with no verdict and no coverage record. `eval 'cd w'; cat x` does the
same. The reviewer of the Q212 change measured both on a built binary of `main`
at `162fcf9` and found it pre-existing. Claude re-drove both on bash on
2026-11-01, and each printed `w/x`.

The tracker reads `eval` as a command with no row: it is not `cd`, so
`classifyCd` returns nothing, and the directory stays known. The Q212 fix loses
the directory after `eval` only once a moving function is defined, because
there `eval f` may be the call. With no function in the string, the `cd` is
inside the eval's own words and nothing reads them.

The same reasoning reaches the other builtins that run a word as code in this
shell: `source` and `.` of a file holding a `cd`, and `trap 'cd w' DEBUG`.
None of those three has been driven through the hook.

The likely fix makes any in-shell `eval`, `source` or `.` lose the directory,
which turns a silent allow into a deferral. A `cd` after one is already lost,
because either may have assigned `CDPATH`. What that costs is the number of
real calls with one of these words ahead of a relative operand, and nobody has
counted it.
