# Report the quoted-assignment override divergence to claude-bouncer

[Q92](Q92.md) is this repo's copy of a defect that is not this repo's. `prod-guard`
reads a quoted word in command position as an inline assignment, so
`'PROD_GUARD_OVERRIDE=x' cmd` arms its escape hatch where bash would try to run a
program of that name. The measurement is below, ready to paste into a
`claude-bouncer` backlog row.

Same shape as [Q16](Q16.md) and [Q54](Q54.md): the row lives here because this is
where the measurement was taken, and the work is a row filed in the other repo.

## What was driven

Two guards and the shell, on the same spellings, 2026-08-31. Nine
name-quoting or -escaping forms, three value controls, one negative control.

`prod-guard` 2.5.2, its real `extract_env_prefix` over `bouncer_parse.lex`
output — not a reimplementation of its arming test:

```
 1  whole word, single     'PROD_GUARD_OVERRIDE=x'       ARMED
 2  whole word, double     "PROD_GUARD_OVERRIDE=x"       ARMED
 3  part of name, single   'PROD'_GUARD_OVERRIDE=x       ARMED
 4  part of name, double   "PROD"_GUARD_OVERRIDE=x       ARMED
 5  empty pair in name     PROD_GUARD_OVER''RIDE=x       ARMED
 6  empty pair before =    PROD_GUARD_OVERRIDE""=x       ARMED
 7  backslash, leading     \PROD_GUARD_OVERRIDE=x        ARMED
 8  backslash, mid-name    P\ROD_GUARD_OVERRIDE=x        ARMED
 9  backslash on the =     PROD_GUARD_OVERRIDE\=x        ARMED

C1  plain assignment       PROD_GUARD_OVERRIDE=x         ARMED   correct
C2  quoted value, single   PROD_GUARD_OVERRIDE='a b'     ARMED   correct, value 'a b'
C3  quoted value, double   PROD_GUARD_OVERRIDE=one"two"  ARMED   correct, value 'onetwo'
C4  unrelated command      cmd deploy.env                -       negative control
```

C4 is in the table because eleven ARMEDs in a row is the shape of a probe that
cannot return anything else.

bash 5.3.15, the same forms, reading whether the variable was set or whether the
word was executed:

```
SG_OVR=x env             set    -- an assignment
SG_OVR='x y' env         set    -- an assignment
SG_OVR=x"y" env          set    -- an assignment
'SG_OVR=x' env           --     command not found
"SG_OVR=x" env           --     command not found
'SG'_OVR=x env           --     command not found
"SG"_OVR=x env           --     command not found
SG_OVR''=x env           --     command not found
\SG_OVR=x env            --     command not found
S\G_OVR=x env            --     command not found
SG_OVR\=x env            --     command not found
```

**The rule the drive establishes:** quoting *or escaping* any character up to
and including the `=` makes the word a command; quoting inside the *value*
leaves it an assignment. Nine spellings are in the class and both guards arm on
all of them; neither guard's tests name more than two.

`SG_OVR\=x` is the one to carry into the filing. The escaped character is the
`=` itself, which is neither name nor value, so a spec written as *quoting the
name* does not classify it — and backslash is a third quoting mechanism that a
pass over `'` and `"` alone never reaches. A shared-lexer fix written against
the narrower spec ships, turns its flipped pins green, and leaves that spelling
arming in all five guards.

## Why it is one row and not two

Both guards read tokens from a lexer that has already removed quotes, and both
match with `ASSIGNMENT_RE` out of `lib/bouncer_parse.py`. Recovering the
distinction means keeping quote provenance through the lexer, which is one change
in the shared parser rather than a fix per guard — so the `claude-bouncer` row
wants the `lib` label, because the fix reaches all five.

## One constraint on the fix, and no design

A probe that keeps the quotes in the token — the obvious way to carry
provenance — breaks six `TestLex` cases upstream: a quoted operator character, a
quoted newline, two backslash-in-quotes cases, a backslash before a closing
quote, and an empty quoted word. So the lexer's contract is that callers receive
quote-stripped tokens, and `internal/readers` and `extract_env_prefix` both
consume them on that basis.

That is a constraint on any fix — provenance has to travel *beside* the token
rather than in it — and it is not a design. Nobody has measured what shape it
should take, and this row deliberately does not guess.

That is also why Q92 cannot be fixed here first. `CLAUDE.md` holds
`internal/bash` structurally identical to its `claude-workspace-guard` upstream
so a fix there transfers by inspection, and inventing a divergent one here would
break exactly the property that makes the port maintainable.

## What it is worth

Bounded in both places, and worth saying so in the filing rather than letting a
maintainer discover it. `PROD_GUARD_OVERRIDE` skips a prompt; spill-guard's
downgrades a block to a confirmation. Neither is an allow, so nothing is sent or
run without a human seeing it.

What it costs is the stated defence of command-position-only, which is
**legibility**: the override sits in the command a human is being asked to
approve, and a reader can see it. `'PROD_GUARD_OVERRIDE=x'` is not a spelling any
reader would call an override, and it is a plausible thing to type by accident
when quoting a value.
