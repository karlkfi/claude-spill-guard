# A <( on a stage before the grep filter loops the refusal

A recursive grep whose later stage takes a process substitution is refused,
and the reason asks for `spill-guard filter` as the last stage. Adding the
filter does not clear it. Driven 2026-11-10 on a binary built from the branch
that closed Q255, under bash 5.3.15, with a planted key on a line holding
`deploy`. "Key printed" is the filter's exit 3 on what the run printed:

| Command | Hook | Run |
|---|---|---|
| `grep -rn deploy . \| grep -v -f <(echo nomatch)` | deny, the reason asks for a filter stage | rc=0, key printed |
| `grep -rn deploy . \| grep -v -f <(echo nomatch) \| spill-guard filter` | deny, the same reason | rc=3, key withheld |
| `grep -rn deploy . \| grep -v nomatch \| spill-guard filter` | no verdict | rc=3, key withheld |

The second row is the loop: the form the reason asks for is refused with the
reason that asked for it. The design says a rewrite is checked against the
same test before it is offered, so that a refusal cannot loop. No backticked
rewrite is offered here, but the prose instruction loops all the same.

The cause is in `internal/bash/bash.go`, at the redirect branch of
`Segments`. It records the `(` of a `<(…)` and of a `>(…)` the same way in
`Segment.Redirects`, so `copiedAround` in `internal/hook/grep.go` cannot tell
an input from a copy and refuses both. Q255 skipped the paren on the grep's
own segment, where matches leave only by stdout. A later stage can write
through a `>(…)` (`| tee >(cat >&2) |`), so this has to be decided where the
lexer still knows which operator it saw.

Traffic is about zero: the reviewer of #268 found 7 regex hits over local
transcripts, read 6, and all six were spill-guard development probes.

**Done** when the second row gets no verdict, `| tee >(cat >&2) |` is still
refused, and the bash package's redirect tables say which form was recorded.
