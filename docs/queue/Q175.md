# A command-prefix assignment reaches no scanner and leaves no record

`FOO[0]=x cat <key file>` is allowed. No verdict, no coverage record, nothing on
stderr — the same silence a call carrying no secret produces, on a call that
reads a credential file straight into the model's context.

Measured 2026-09-17 against a built binary at the head of `main` and at the base
of the branch that was in flight, identical at both, so this is live rather than
a regression. Found by an independent review of Q168's pull request (#165),
which was fixing the neighbouring spelling.

**The near-miss spelling is covered and this one is not.** `FOO+=x cat <key>`
was the subject of Q168 and now reads as an assignment, so the segment's command
name resolves to `cat` and the operand is scanned. An *indexed* assignment —
`FOO[0]=x` — takes a different path, and the call goes through with no
`aws-access-key-id` finding on a file holding one.

## Why the silence is the defect rather than the allow

A coverage failure defers and records. That is the design's answer for a call it
could not read: the permission flow runs unchanged, and a line lands on stderr
and in the capped JSONL that `spill-guard coverage` groups. Either outcome is
defensible here.

What is not defensible is producing neither. An operand nothing resolved should
be a coverage record naming it, and this one is indistinguishable from a clean
scan of a file with nothing in it. The record is what a later sweep reads to
find out what the scanner has been missing, so a gap that writes nothing is a
gap nobody can count.

## What to establish before fixing

Which of the two layers drops it — `internal/bash`'s segmentation, where an
indexed assignment may not be read as an assignment at all, or
`internal/readers`, where the segment arrives with a command name that is not
`cat`. The fix differs: the first is a lexer arm, the second a resolution arm.

The port boundary matters here. Shell segmentation in this repo is a port of
`claude-workspace-guard`'s, kept structurally identical so a fix there transfers
by inspection — so check whether upstream reads `NAME[sub]=value` as an
assignment before writing one here. If upstream is also silent this is an
upstream row first, and if upstream already handles it the fix is a transfer
rather than an invention.

Bash's own reading is the oracle, and it is not obvious from the grammar:
`FOO[0]=x cat f` runs `cat f` with `FOO[0]` assigned in the command's
environment only when `FOO` is already an array, and is otherwise an error the
shell reports rather than a command it runs. Drive the arms before choosing
which one this must match.
