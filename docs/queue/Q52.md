# Differentially fuzz the capture-length bound against real captures

`maxCaptureBytes` in `internal/rules/capture.go` may over-estimate and must never
under-estimate: an over-estimate leaves a dead rule loaded, and an
under-estimate refuses a live rule at startup, which takes the scanner down over
a rule that works. The walk's own doc comment says so and the unit tests pin
about twenty patterns by hand, which is a sample rather than a property.

A differential harness turns that into one: for each pattern, compare the bound
against the longest group-1 capture `FindAllSubmatch` actually produces over a
corpus, and fail on `bound < observed`. The assertion is one-sided on purpose —
over-estimates are the design, so a two-sided check would fail on the intended
behaviour.

Run once during the review of the change that added the walk, over roughly
400 KB: zero under-estimates across seventeen patterns. It was first reported as
twenty, and the re-measurement that produced the guard below found three of those
matched nothing at all — so seventeen is the figure, and the other three proved
neither the presence nor the absence of a defect.

## What the corpus and the patterns have to hold

**Fail a pattern whose match set is empty.** This is the load-bearing line and
it is not the corpus. A pattern needing a literal sequence — `(?i)(straße)`,
`((?:ab){1,3})`, `(?i)(kelvin)` — never appears in a corpus assembled from
random runes, so `FindAllSubmatch` returns nothing, the comparison has nothing
to compare, and the case passes. Silently.

Against this row's own rationale that is the worst available outcome: the
patterns are carried because trouble was expected and not found, so an empty
case reads as coverage and is none. It is also the defect this repository is
built around — a check reporting nothing being indistinguishable from a check
that ran and found nothing, which is why the loader fails closed on a regex that
will not compile. A recipe for a test that cannot fail is that same failure
arriving through the backlog instead of through the scanner. The guard is the
same rule as the `git diff --quiet` precondition on a mutation control: assert
the thing you are measuring actually happened.

Then seed those literals rather than hoping for them — `straße`, `STRASSE`,
`ſtraße`, `ababab`, `kelvin`, `KELVIN`, `Kelvin`, `aaaaaa`, `bbbbbb` — spliced in at
a fixed stride alongside the random runes.

Build the rest of the corpus from random runes over a set that mixes plain ASCII
with the fold and width traps, with a **fixed seed** — a corpus reseeded per run
is a flake generator, and this is a gate. The set that earned its place:

    a z A Z 0 9 - space é ß ſ K İ ı Ω ω 𐍈 \n x

The patterns worth carrying are the ones where trouble was expected and not
found, since those are what a future edit to the walk would break first:

| Pattern | What it probes |
|---|---|
| `(?U)([a-z]{2,6})`, `(?i)([a-z]+?)` | non-greedy, where the longest match is not what the engine returns |
| `((?:a*){3})` | a repeat over a star |
| `([^a]{2})` | a class with one range spanning encoding widths — `[\x62-\x{10FFFF}]` crosses one byte to four, and negation is just the ordinary way to write that. Also pinned directly in `TestMaxCaptureBytes` now, since nothing else could tell the ends of a range apart |
| `([\x{10000}-\x{10FFFF}]{1,2})` | astral ranges, four bytes a rune |
| `(\p{L}{1,4})`, `(\p{Greek}{2})` | Unicode classes |
| `(?i)(straße)`, `(?i)(SS)` | folding that changes encoded width |
| `([\x{0130}\x{0131}i]{1,3})` | the dotted/dotless I pair |
| `(?i)([\x{017F}\x{212A}s k]{1,2})` | long s and Kelvin, the two cases the fold walk exists for |

Folding is the half most likely to rot. `syntax.Parse` expands a class's folds
into its ranges but leaves `FoldCase` on a literal, so the two arms of `maxBytes`
reach the same answer by different routes, and only one of them walks
`unicode.SimpleFold`. A refactor that unifies them is exactly the edit this
catches.
