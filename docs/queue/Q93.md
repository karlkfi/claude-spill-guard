# The PR body is on the discard side of the squash boundary

`gh api repos/karlkfi/claude-spill-guard --jq .squash_merge_commit_message`
returns `COMMIT_MESSAGES`, and `allow_merge_commit` is `false`. So a squash here
builds its message from the branch's commits, and a pull request body reaches
`main` by no strategy this repository allows.

**That is the field to cite, and it is not the obvious one.** The three
`allow_*_merge` flags say which strategies are available and nothing about what
a squash writes — `PR_BODY` is a legal value for `squash_merge_commit_message`,
so a repository with this one's exact three flags can carry every body into
`main`. Confirmed against the trunk rather than inferred: `git log -1
--format=%B cf2c78e` is concatenated commit messages under `*` bullets, with no
body text anywhere in it.

A body is therefore a review surface, which is a different thing from an
archive, and nothing in the interface distinguishes them: it sits beside the
diff, is read at the moment a decision is made, and then stops existing
anywhere a later reader will look.

Anything that lands *only* there is gone at merge. A measurement taken by hand.
A verification CI will never re-run. A caveat about what a change does not
cover. An explicit "I could not drive this on a Mac". Each of those is written
because a reader needs it, and each is written into the one artifact guaranteed
not to reach them.

## The instance, and why it is the same mechanism twice

Q82's session filed Q83 — nothing reports a branch carrying reviewed work that
has no pull request — and then, twice in the same pull request, corrected a
claim by editing the body and left the row carrying the weaker argument.

Both corrections were real and both were held before they were needed.
`mergeCommitAllowed: false` had been read off that session's own three-field
query an hour before the row was written, and went unused. The arity argument — that a
single-parent merge commit and a non-ancestor head are each produced by a
rebase merge too, so only commit counts separate the strategies — was derived
while correcting the batch's orchestrator, and then not written into the file
that survives.

**The recursion is the finding, not a joke about it.** Q83 exists because a
squash stranded reviewed work with nothing reporting it was stranded. The
corrections went into a body the same squash discards, while the row that
survives carried the weaker half. One boundary, two payloads: a commit in
Q83's case, prose in this one. Neither was visible from the side it was
written on.

An independent reviewer found both, on two separate passes. **No gate here
reads a PR body**, and the reason is narrower than it first looks. Every `make`
target runs over the tree; a body is not in the tree; so no gate this repository
runs can have an opinion about one.

That is a fact about targets over a tree, not about what a workflow can do.
`tests.yml` triggers on `pull_request`, and a step in that context has the
webhook payload on disk at `GITHUB_EVENT_PATH`. Nothing here reads it — no
`GITHUB_EVENT_PATH`, no `actions/github-script`, no `api.github.com`, every
`github.event` reference being `github.event_name`, and the two real `gh`
invocations being `release download` and `attestation verify`. Each of those
probes was run with a positive control. **So the route is unused, not
unavailable, and this row is not an argument that no check could be added.**

Whether that route could carry one is unsettled here and worth someone's time.
The API's pull request object has a `body` field; whether the `pull_request`
webhook payload's embedded object carries it is the platform contract, and
confirming it needs a `jq` line in a workflow step this repository does not
have.

## Why the wording matters

*Put corrections in the durable artifact* is advice. It decays, nobody can
check it, and it gives a reader no way to tell whether they are about to make
the mistake.

*The PR body is on the discard side of the squash boundary* is a structural
fact with a one-line citation, and it answers the question at the moment it is
asked: this correction I am about to write, does it reach anyone? The test is
whether the sentence exists anywhere a `git log` reaches.

## The next step

A line in `CLAUDE.md`, under **Prose** or beside the backlog section, naming
the merge policy and the consequence: a correction, measurement or caveat that
belongs to the tree goes in the tree, and the body says where to find it.

This row proposes the sentence rather than writing it, deliberately. Three
blocks of `CLAUDE.md` were spoken for by items in flight when this was filed,
and a fourth writer is how a clean auto-merge becomes a conflict. Whoever works
this lands the edit when the fence comes down.

Q83, filed by #50 alongside the work described above, is the trunk-side half of
the same boundary and is worth reading first. The upstream `session-worker` §5
calls the body "the maintainer's review surface" — true, and exactly what makes
it read as durable.
