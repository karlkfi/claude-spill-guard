# Two `testvec` rejection cases cannot fail for the reason they name

`TestLoadRejects` in `internal/testvec` drives four bodies through `loadFrom`
and asserts each is refused. Its own comment says why they are listed
separately: "An assertion that has never failed is not evidence that it can."
Two of the four cannot fail for the check they are named after.

**The mechanism is the assertion, not the order of the checks.** `recorder`
stands in for `*testing.T` and its `Fatalf` does not abort — the type's own
comment says so — so `loadFrom` runs *every* check and records each failure it
finds. The assertion is `len(rec.failures) == 0`, which asks for **at least
one** failure and never for a particular one. Every fixture body holds one
vector against `minVectors = 11`, so the floor records a failure in addition to
whatever the case is about, and that alone satisfies the assertion.

Driven by instrumenting the recorder to print what it captured:

| Case | Failures recorded |
|---|---|
| a file holding fewer vectors than the floor | 1 — the floor, which is its own check |
| a field the entry does not carry | **2** — the unknown field *and* the floor |
| an entry with no value at all | **2** — the floor *and* the empty value |
| a file that is not JSON | **2** — the decode error *and* the floor |

So the named check does fire. It is simply not what the assertion is reading.

## Driven, with a control

Each mutation removes one check and asserts the removal landed before running
the test:

| Mutation | `TestLoadRejects` | Should be |
|---|---|---|
| `dec.DisallowUnknownFields()` removed | **passes** | red — "a field the entry does not carry" is the case for it |
| the `v.Value == ""` loop removed | **passes** | red — "an entry with no value at all" is the case for it |
| `minVectors` lowered from 11 to 1 | fails, and **only** on "a file holding fewer vectors than the floor" | this is the control |

The third is what makes the first two mean something. With the floor out of the
way both cases still pass, so `DisallowUnknownFields` and the empty-value check
do work — the defect is that nothing in the suite would notice if they stopped.
Remove either one today and every gate stays green.

## Two fixes work and the obvious third does not

**Reordering the checks fixes nothing**, and it is what a reader who has "the
floor fires first" in hand will reach for. The later check still runs and still
records, because nothing aborts. This row used to say that, and it was wrong.

What works:

1. **Assert which failure**, by matching the recorded message rather than
   counting. This is the narrow repair and it couples nothing.
2. **Give each body enough entries to clear the floor**, so the only thing that
   can refuse it is the check it is named for.

The second has a cost worth naming: it couples those fixtures to the value of
`minVectors`, and a separate row filed in this same change records that the
floor now equals the real vector count with zero slack. Those two pull in
opposite directions — padding fixtures to 11 entries makes the floor harder to
lower later. Whichever lands first should say what it did to the other.

Either way, keep the padded values non-matching: a credential-shaped literal
here would put this file back in the class `self-scan` names.

## Provenance

Found 2026-09-07 while working the census row, by inverting the code behind a
fixture that had only had its *value* changed. The first write-up of this row
had the observation right and the explanation wrong — it said the floor fired
first, which is an ordering claim. The Q142/Q143 lane pushed back, and driving
the recorder settled it: the checks all run, and the assertion is what cannot
tell them apart. The value was never what these
cases assert on, which is what the change turned on and what the inversion
confirmed twice over. The one-vector bodies predate that change, so this is not
a regression it introduced.
