# The loader accepts keywords the prefilter will never read

`internal/rules` already refuses a rule that carries configuration nothing
reads, and gives the reason in `compile`: a setting with no check behind it
loads, runs, and reports more than its author meant it to. Two of the three
fields with that property are covered — `labels` without `context-label` and an
entropy floor without `entropy` are both startup errors. `keywords` on a `pii`
rule is the third and is accepted in silence.

The prefilter gates the credential family and nothing else, which
[`docs/design/README.md`](../design/README.md#pipeline) states twice and
`internal/scan` implements. So a `pii` rule's keywords are read by no stage.
Pinned as ignored in `TestBufferDoesNotPrefilterThePIIFamily`, which is a test
of the pipeline's behaviour rather than an endorsement of the rule shape.

The failure is the one the naming split exists to catch. An author who writes
keywords onto a numeric rule has said "gate this on a literal" and been given an
ungated full-corpus regex pass — the shape that produced 5,679 matches and zero
credentials on the inherited ruleset. Nothing tells them, and the difference
between a gated rule and an ungated one is invisible from the output.

The fix is a fourth clause beside the two already there: a rule carrying
keywords that does not belong to the family the prefilter gates is rejected,
naming the family. It is the same shape as the other two and the same argument.

Not the same item as Q27, named without a link because that row is completed
by a sibling branch and the file goes with it. That one is the other direction
— configuration that can never let a named check fire — and it needs the regex
to answer. This one is readable straight off the rule.
