# A builtin or compound reads a `<` target that no reader row covers

A `<` target is read only when the command beside it has a row in
`internal/readers`, so the shell's own readers go past it. Driven
2026-11-01 under `env -i PATH=/usr/bin:/bin`, with the planted AWS key in the
file. "bash" is 5.3.15 under `--norc --noprofile -c`, "zsh" is 5.9 under
`-f -c`, and the hook columns are a built binary of the Q219 branch over
`826fed2`.

| command | bash | hook, bash | zsh | hook, zsh |
|---|---|---|---|---|
| `read -r y < one.env; echo "$y"` (key on line 1) | prints | allow, silent | prints | allow, silent |
| `mapfile -t a < k.env; echo "${a[@]}"` | prints | allow, silent | nothing | allow, silent |
| `while read -r l; do echo "$l"; done < k.env` | prints | allow, silent | prints | deny |

The zsh deny on the last row is an accident. The redirect sits on the `done`
segment, the keyword peel leaves no command word, and Q219's zsh arm reads
the target as `$READNULLCMD` would.

`read`, `mapfile` and `readarray` read their stdin into a variable, and the
variable crosses once something prints it. A redirect on a loop's `done`, or
on a `{ … }` or `( … )` closer, feeds every command inside. Whether every
such target should be read, whatever command is beside it, is the question.
That would close all three rows, and it over-reads `wc -l < f` and `sort < f
> out`. Nobody has counted that cost.

**Measure:** how many real `Bash` calls put a `<` target beside a command
with no reader row, and how many of those are `read`, `mapfile` or a
compound closer. The CLAUDE.md figure, 141 of 360 input redirects in the week
to 2026-09-04, is the upper bound to refine.

Found by the reviewer of the Q219 change, and kept out of it because it is a
different mechanism.
