# Detect a JWT longer than the bound by splitting detection from extent

`Q133` gave `jwt` a bounded repeat so the loader would hand it an
`Anchor`, which bought 2.2x on the shipped ruleset. It cost a recall ceiling:
a header or payload segment past 1,003 bytes goes unmatched, and a production
access token with many claims is that shape.

**The ceiling is an artifact of the engine, not of the secret.** Go's
`regexp/syntax` refuses a bounded repeat above 1,000 — driven, `{8,1000}`
compiles and `{8,1001}` returns `invalid repeat count` — so 1,000 is the
largest single bound expressible, and nothing about it was measured as
sufficient. Q133 says so in its own body. A 5,000-byte JWT is an ordinary
credential this build now misses silently.

## What makes it fixable

One pattern is doing two jobs, and only one of them needs to span the token.

- **Detection** — does a JWT start here? A bounded head suffices, and a
  two-segment one is highly selective: over 0.46 GB in 60,000 files of this
  tree and `~/go/pkg/mod`, 554 bare `eyJ` keyword hits and **27** reaching a
  second `eyJ` segment past a dot. 4.9%, a 20:1 rejection, on a pattern
  compiling to a fraction of the thousand states `{8,1000}` needs.
- **Extent** — how far does it run? A forward walk over `[A-Za-z0-9_-]` and
  `.` from the match start. Linear in the token, and run only on the ~5% that
  survive detection rather than at every keyword hit.

`passes` in [`internal/scan/scan.go`](../../internal/scan/scan.go) already
receives `(buf, lo, hi)` — the whole buffer, not just the capture — and
`validate.NearLabel(buf, lo, …)` already reads outside the match bounds. So a
check that walks past the capture is precedented here rather than new.

## Three things a session must settle rather than assume

**Where the extent lives.** A validator that returns a bool cannot widen a
finding's bounds, so this is either a new phase between match and validate, a
rule-schema field, or a special case in the match loop. The schema change is
what Q133 declined as buying nothing — against *leaving it unbounded*, which
is not the alternative any more. Weigh the three; do not assume the schema.

**Whether it is actually faster.** The 4.9% is a rejection rate, not a
benchmark. `BenchmarkRule` and `BenchmarkRuleset` exist and Q133's table is the
baseline to beat: 77.66–77.80 MB/s on the shipped set, `jwt` alone at 757–764.
Keep its control arm — every `Anchor` cleared, which did not move — because
that is what says a difference is the change rather than the machine.

**Precision, in both directions.** The clean corpus must stay at 0 and every
planted case must still report exactly one finding. A forward walk can
over-extend where the old bound truncated, so the terminator needs a case of
its own. And the extent must hand `jwt-sample-key` the *whole* token: Q133
measured that a bound below the longest HMAC signature makes the HMAC
comparison fail and **unsuppresses a published sample as a credential** —
`TestABoundBelowTheHMACSignatureUnsuppressesAPublishedSample` drives 43
against 1,000 and shows 1 finding against 0. A correct extent should make that
failure mode structurally unreachable rather than merely avoided.

## What it retires if it lands

The `jwt` row on v0.4.0's *What it does not read* list, and the CAUTION banner
half that describes it. Both are written in
`docs/releases/v0.4.0.md` on the pre-tag branch, so
whoever completes this owes that file an edit as well as this one.

Chaining a second repeat was measured by Q133 and dropped: it raises the
ceiling to 2,003 and costs 3.76 MB/s against 18.5 on back-to-back JWTs. That is
a deeper ceiling, not the absence of one, so it is not this row's answer.
