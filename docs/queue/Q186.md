# A standalone CDPATH assignment sends `cd` to a tree nothing scanned

`CDPATH=/elsewhere; cd sub && cat key.env` is scanned against `./sub/key.env`,
and bash reads `/elsewhere/sub/key.env`. The verdict is about a file the call
never opened, and the file it did open was never scanned.

Driven 2026-09-19 against a binary built from the Q175 branch, with
`testdata/corpus/planted/aws-access-key-id.env` under `testdata/`:

| command | verdict | what bash reads |
|---|---|---|
| `CDPATH=/tmp cd testdata && cat corpus/planted/aws-access-key-id.env` | defers, records the operand | nothing -- the search may leave the tree |
| `CDPATH=/tmp; cd testdata && cat corpus/planted/aws-access-key-id.env` | **deny**, naming the file under `./testdata` | whatever `cd` found, which need not be that file |

The prefix form is right, and it is right because `assigns` reads the segment's
own inline prefix. The standalone form is a different segment, so nothing
asks.

## CDPATH wins over the local directory, which is what makes it a fail-open

Driven the same day on bash 5.3.15 with `target/f` present in both the current
directory and the search path: `CDPATH=<away>; cd target; cat f` prints the
copy under `<away>`, and the same command without CDPATH prints the local one.
So this is not a case of the search merely widening what `cd` might find --
where both exist, the one the scanner assumed is the one bash does **not**
take.

## It is the plain spelling, not the subscripted one

Worth saying because Q175 arrived through subscripts and this was found beside
it. `CDPATH=/x` is an ordinary assignment the tracker records into its variable
map; what is missing is any reading of that map by the `cd` tracker, which asks
`assigns` about the prefix and about nothing else. `CDPATH[0]=/x; cd sub`
searches too -- `$CDPATH` is `${CDPATH[0]}` -- so the subscripted spelling has
the same gap, and closing the plain one closes both if the check goes through
`SplitAssignment`.

## The shape of the fix, and the one thing to settle first

The tracker already holds a variable map that knows `CDPATH` was assigned, so
the reading is available where the decision is made -- `follow` in
`internal/hook/bash.go`, beside the `os.Getenv("CDPATH")` arm it already has.
The answer is the same one the prefix form gets: lose the directory and record
the operand.

What to establish is the cost. The environment arm is already unconditional, so
a machine with CDPATH exported defers every relative `cd` today; measure how
many real `Bash` calls assign CDPATH in-string before assuming the new arm is
free. The prefix arm's own row measured 0 in 95 commands for the neighbouring
globbing options, so the honest expectation is that this is rare and the arm is
a guard rather than a cost -- but that is an expectation and not a reading.
