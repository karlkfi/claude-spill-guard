# `selftest` cannot see a fail-open an allowing arm would meet

`spill-guard selftest` reports each arm as blocked, allowed, or anomalous, and
an arm that is *supposed* to be allowed is the only one that can silently agree
with a wrong answer. A blocking arm disagrees with everything but a block by
the canary rule, so it fails whatever went wrong. That asymmetry is why the
allowing arms exist, and it also bounds what they can see.

**They see it only where an arm's payload reaches the defect.** Two cases where
that does not hold today, found while reviewing
[`internal/selftest`](../../internal/selftest/selftest.go):

- **A confirmation on an event with no confirmation encoding.** `confirm()`
  refuses anything but `PreToolUse`, landing on exit 2, which blocks — the
  fail-closed path working as
  [`verdict.go`](../../internal/hook/verdict.go) says it should. `selftest`
  surfaces it as a *refusal* rather than a block, which is accurate and is not
  what an arm is looking for.
- **The case `verdict.go`'s own comment names as the hazard**: a future caller
  emitting a `PreToolUse` deny object on `UserPromptSubmit`, which Claude Code
  accepts and ignores, so "the prompt would run with the secret in it and
  nothing would turn red". No allowing arm meets that, because it needs a
  finding to reach a verdict at all — and a blocking arm would see a block and
  pass.

Neither is a defect in the shipped binary. Both are places the check a user
runs would report a clean bill.

## What would close it, and what it costs

Two shapes reach a verdict without a finding, and they cost different things.
Both driven 2026-08-31 against `drive`, on a UTF-32 file carrying no secret:

| payload | branch | cost of an arm |
|---|---|---|
| the file, plus `SPILL_GUARD_OVERRIDE=` | a verdict that is not a block | ships an override in the user-facing report |
| the file alone | blocked, but not by the canary rule | a fixture and nothing else |

**The second needs no override**, which is the half an earlier draft of this row
mispriced. `selftest` shipping an arm that exercises the override hatch is a
user-visible behaviour rather than a test fixture, and the report would have to
explain a fourth outcome to whoever runs it; an undecodable fixture costs a
file.

**The honest limit is that neither recovers the asymmetry this row is about.**
An arm pointed at an undecodable file would want `blocks`, because a declared
encoding this build cannot decode blocks by design — so it is a blocking arm,
and blocking arms already fail on every wrong value. It makes part of the class
reachable more cheaply than the row first said; it does not make an *allowing*
arm able to see it. The per-event encoding hazard above is not reached by
either, and needs a caller that does not exist yet.
