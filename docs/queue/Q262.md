# A literal command run through `eval` is never judged

`eval cat key.txt` runs `cat key.txt`, and the hook reads `eval` as a command
with no row in `internal/readers`, so the segment contributes no operands.
Driven 2026-11-09 on bash 5.3.15 against a binary built from `main` at
`b814140`: with `key.txt` holding a key, the call exits 0 with no verdict and no
record, and bash prints the key. `cat key.txt` beside it denies.

This is not the unresolved head Q225 holds open. There the command name is a
`$NAME` nothing can resolve; here every word is literal, and bash's own reading
is known: `eval` joins its words with spaces and parses the result as a command
string.

The change that completed the in-shell-cd row already does that parse for one
question: `evalMoves` in `internal/hook/bash.go` segments the joined words to
ask whether they move the shell. The same text could be queued as a body, so its
readers get their verdict, which would also follow a literal `eval cd w` instead
of losing the directory. What it costs is unmeasured: count the real calls with
a literal `eval` ahead of a reader before choosing.
