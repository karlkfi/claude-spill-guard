# A zero budget races the scan it is meant to outrun

`TestAnOverrideOnACoverageFailureIsInert` in
[`deadline_test.go`](../../internal/hook/deadline_test.go) drives a call with
`driveWithin(t, 0, payload)` and requires the coverage record a deadline
produces. A zero budget is not a guarantee that the deadline fires. It is a
guarantee that the timer is *ready*, and `within` selects between that timer
and a buffered channel the scan goroutine may already have filled:

```
	select {
	case got := <-done:
		return got, true
	case <-timer.C:
		return scanned{}, false
	}
```

Go picks uniformly at random among ready cases, so whenever the scan goroutine
reaches `done <- ...` before the main goroutine reaches the `select`, the test
is a coin flip. The payload is `cat clean.txt` over a six-byte file, which is
the fastest scan the suite has.

## Measured

Failed once in CI, on 2026-09-07:

```
--- FAIL: TestAnOverrideOnACoverageFailureIsInert (0.00s)
    --- FAIL: TestAnOverrideOnACoverageFailureIsInert/default (0.00s)
        exhibit:deadline_test.go:201: stderr is empty, want the coverage record
```

The pointer carries the `exhibit:` marker because it is quoted CI output, not
a citation this row relies on; the assertion it names is the `deferred` check
in the subtest above.

Empty stderr is the scan branch: `within` returned `ok=true`, the clean file
produced no finding, and the verdict was an ordinary allow with nothing to
record. Two of sixty `tests.yml` runs failed in the sampling window and this
was one of them; the other was an unrelated prose gate.

**It does not reproduce here, and that is the interesting half.** 800 repeats
of the test at `GOMAXPROCS` 1, 2 and the machine default: zero failures. The
timer wins every time because the scan goroutine has not been scheduled yet
when the `select` runs. A contended runner is what closes that gap.

The mechanism was driven separately rather than inferred, with the control that
says the probe can come back either way — the `select` shape above, the scan
result pre-loaded or not:

```
scan ready before select=false -> scan won 0/2000
scan ready before select=true  -> scan won 1004/2000
```

50.2% once the race is entered, 0% otherwise. So the failure rate is not a
property of the test; it is the probability that a loaded machine deschedules
the main goroutine for as long as a six-byte scan takes.

## What a fix has to keep

The test is asserting something real — that the override is not consulted on a
coverage failure, on both permission modes — and the deadline is only the way
it manufactures one. Two directions:

- **Make the deadline unambiguous rather than merely expired.** `within` could
  check the timer before the select when the budget is already spent, so a
  zero or negative budget can only take the deadline branch. That is a change
  to shipped behaviour and needs its own argument: a budget that has already
  run out at the moment of dispatch is exactly the case where refusing to look
  at a completed scan is right, but it is a decision rather than a tidy-up.
- **Manufacture the coverage failure another way in this test**, leaving
  `within` alone. `slowToScan` already exists for the neighbouring tests and is
  what makes their deadlines real.

The second is smaller and does not touch the product. The first may be correct
anyway, which is why the row does not pick one.
