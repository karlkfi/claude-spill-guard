# Deny by shape, where there is nothing for a content match to read

Both answers the design gives for `Bash` are content answers: scan the command
string, and scan the files its reader operands resolve to. Both look for a
secret's bytes, and
`docs/design/README.md:101:Neither catches a command that synthesizes a secret at runtime`
already says what that leaves out. `env` is the sharpest instance. The bytes
exist only in the tool process's environment, so at `PreToolUse` there is
nothing to open and nothing to match, and
[`PostToolUse` cannot withhold a result](../design/README.md#posttooluse-cannot-withhold-a-result)
rules out catching it afterwards. A scanner that only matches values is
structurally blind to it.

This row proposes the other control: refuse the call on its shape, and put a
redacted alternative in the denial reason so the model applies the fix and no
human is interrupted. Two rules.

**Environment dumps.** `env`, `printenv` with no operand, `export -p`,
`declare -p`, bare `set`, and the interpreter forms —
`python3 -c "print(dict(os.environ))"`, `node -e "console.log(process.env)"`.
The reason names the fix: `printenv PATH HOME` for the variables you want,
`${FOO:+set}` to test presence without printing a value, `env | cut -d= -f1`
for names only.

**Secret-bearing config reads.** `~/.claude/settings.json` first, then the
class: `.env`, `~/.aws/credentials`, `~/.netrc`, `~/.git-credentials`,
`~/.docker/config.json`, and kubeconfig. The reason names a filtered read —
`jq 'del(.env)' ~/.claude/settings.json`.

## The threat model is accident, not an adversary

Say this in the reason and in the docs, because it is what makes a deny
proportionate rather than theatre. A session that wants the value writes
`jq .env` and gets it; nothing here stops that, and this repo has already
settled that a control the scanned content can talk its way past is worthless —
`CLAUDE.md:220:**No in-band bypass tag.**` is the same argument one level down.
What a shape deny stops is the ordinary case: a session reaching for `env`
while debugging a PATH problem, and writing 58 variables into a transcript that
keeps them.

That also sets the bar the rule has to clear. It may not fire on the careful
form, because the careful form is what sessions already write — see below.

## Measured

Taken 2026-08-31 on one machine, against workspace-guard 1.11.0
(`installed_plugins.json`), Claude Code's own hook script driven with a JSON
payload on stdin. Every verdict below ran with controls: `echo hi` returns
silent/allow and `cat /etc/hosts` returns `ask`, so the instrument separates.

**The environment is the larger exposure, and the file is the smaller one.** A
Bash tool process carries 58 environment variables. `settings.json` holds 2,
both filesystem paths, and both names appear in that 58 — which is the check
that the `env` block really is injected into every tool process rather than
merely documented as such. `CLAUDE_CODE_MESSAGING_TOKEN` is in the 58 and in
neither of the 2, so the harness put it there and no config change removes it.

**Nothing guards the environment today.**

| command | workspace-guard 1.11.0 |
|---|---|
| `env`, `printenv`, `export -p`, `declare -p`, `set` | silent/allow |
| `python3 -c "import os;print(dict(os.environ))"` | silent/allow |
| `cat ~/.claude/settings.json` | `ask` |
| `python3 -c "print(open('/Users/karl/.claude/settings.json').read())"` | silent/allow |
| `cat .env` (inside the project root) | `allow` |

Three readings follow, and two of them are why this cannot be built as a
command allowlist.

The `ask` on `settings.json` is a path-boundary verdict, not a secrets one: its
reason is `Outside-workspace path(s)`, the same sentence `cat /etc/hosts` draws.
Nothing in it knows the file holds an `env` block, and the read and the write
draw the identical verdict for the identical reason.

An interpreter read of the same path is allowed where `cat` asks, so existing
coverage is keyed on the command rather than on the path. A rule that inherits
`internal/readers` inherits that hole too — `CLAUDE.md` already states it for
the `Bash` surface, that a command with no row contributes no operands — so the
config half covers the reader table and no more, and should say so rather than
imply a path is protected.

An in-repo `.env` is allowed outright, being inside the root. That is the one
case in the config half where a deny is not duplicating a prompt somebody
already sees.

**The shape has fired zero times in a week, and that is the honest number.**
Over 443 transcript files touched in the seven days to 2026-08-31: **0** bare
environment dumps, and **0** occurrences of a messaging-token value in any
transcript. All 18 `env` calls in that window were filtered —
`env | grep -E '^CCTEST_'`, `env | cut -d= -f1`, `env | wc -l`. The fix this
row wants to write into a denial reason is already what sessions write
unprompted.

The detector was controlled both ways before that zero was believed: it matches
all five denied forms, including `cd /tmp && env`, and declines
`env | grep FOO`, `printenv PATH` and `env FOO=1 make`. Zero means no
occurrence, not a broken probe.

Guarded-reader calls at a path in the config class, same window: 15, all 15 at
`~/.claude/settings.json`, across 11 files. No call at `.aws/credentials`,
`.netrc`, `.git-credentials`, `.docker/config.json` or a kubeconfig. The class
generalizes; on this machine only one member of it is live.

## What the measurement does not support

Rank this as a fail-closed control for a shape nobody has met, not as a
response to a spill. One machine, one week, one operator whose habits are
already careful — that population is the least likely to produce the accident,
so a zero here is weak evidence about anyone else and no evidence at all that
the consequence is small. The consequence is measured: 58 variables, one of
them a harness-issued token, into a file that keeps them.

The 18 filtered calls are the corpus that matters. A rule keyed on the command
name denies all 18 and is worse than no rule, because a guard that fires on the
careful form teaches the session to stop being careful. The rule fires on an
unfiltered dump — a segment whose whole content is the bare command — and the
18 are its negative cases.

## Which way it gets built

**Reads and writes need separate justifications; do not lump them.** A read of
`settings.json` leaks the `env` block. A write to it changes what the harness
does — adds environment variables, edits `hooks`, disables a guard — which is
not a spill at all and is not this tool's goal. Today they collapse into one
verdict for one reason, which is the gap; this row covers the read, and states
that the write is a different control that spill-guard should not quietly
acquire on the way past.

**Do not reach for `updatedInput`.** `PreToolUse` really does accept it
alongside `permissionDecision` in `hookSpecificOutput` (Claude Code hooks
reference, read 2026-08-31), so the hook could rewrite `env` into
`env | cut -d= -f1` and allow it silently. Refuse that. The transcript would
then record a command nobody issued, and this project's whole verification
posture — every measurement here taken by driving a real hook and reading what
reached the transcript — depends on the transcript saying what ran. A deny that
names the fix costs one extra turn and leaves the record honest.

**The two halves compose with content matching rather than duplicating it.**
`slack-webhook-url` is a shipped rule, one of 14 in `rules/spill-guard.json`,
and content matching finds a value like that wherever it appears. The two fail
differently and that is the argument for having both: a content match needs the
secret to look like something a rule knows, and a shape deny needs the crossing
to happen through a shape the table knows. Neither covers the other, and only
the shape deny reaches a dump with no file behind it.

**The halves may want splitting.** They share a mechanism and a denial style,
and they rest on different evidence: the environment half is structurally
unreachable by any content rule, while the config half is reachable whenever a
reader operand resolves, already prompts under workspace-guard for every path
but an in-repo `.env`, and is capped by the reader table. If the config half
grows past a page, give it its own ID.

Both need corpus cases in both directions, per the repo's standing rule — the
rule fires on the shape it was written for, and stays quiet on the 18 filtered
forms.

## Provenance

Came out of a prompt-friction analysis in `karlkfi/claude-bouncer`; the
surrounding measurement is in
[that repo's PR #69](https://github.com/karlkfi/claude-bouncer/pull/69), rows
Q139 and Q140. Q140 owns the `settings.json` env-injection measurement and
deliberately keeps that one path prompting while exempting the rest of
`~/.claude`; this row is the complement, turning a path-boundary `ask` into a
reasoned deny that carries its own fix. The environment is untouched by
anything there.

spill-guard is the home rather than a sixth bouncer plugin or a workspace-guard
rule, because spill-guard already owns the goal: stopping secrets from reaching
the API through a session. That was the maintainer's call.

Adjacent, not duplicate: [Q87](Q87.md) asks which payload shapes carry a path
at all, and this row's config half is bounded by whatever that settles.
[Q84](Q84.md) is the same question one layer down — what an allowed skip owes
the operator — and a deny that names its fix is the shape both answers want.
