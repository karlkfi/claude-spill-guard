# The prefilter finds the positions and the match loop throws them away

`hasKeyword` answers a yes/no and discards where it found the keyword. The match
loop then runs `FindAllSubmatchIndex` over the whole buffer to find the same
places again -- and for eight of the ten enabled rules that second pass cannot
be accelerated at all, because their patterns open on `\b`.

Measured 2026-09-03 at 64 MiB, min of three, with `regexp.Regexp.LiteralPrefix`
beside the time:

| Rule | Prefix the engine can skip to | Full pass |
|---|---|---|
| `slack-webhook-url` | `https://hooks.slack.com/services/T` | 0.001s |
| `private-key-block` | `-----BEGIN ` | 0.001s |
| the other eight | none | 1.18-1.29s each |

Go's `regexp` derives a literal prefix by walking the compiled program from the
start; an empty-width op stops that walk. So `\b(AIza[A-Za-z0-9_-]{35})\b` gets
no prefix, nothing to `memchr` towards, and the entire buffer goes through the
NFA. The two cheap rules are the only shipped patterns that do not open on `\b`,
which is the whole of the difference.

Falsified rather than read off the source. The same three patterns with the
leading `\b` removed acquire prefixes `gh`, `AIza` and `eyJ` and run **1175x to
1186x** faster on the same buffer. Measured on Go 1.26.5, and it is one
implementation's optimizer rather than something RE2 promises.

**Deleting the `\b` is not the fix and must not be read as one.** It changes what
the rule matches: `\b(gh[oprsu]_[A-Za-z0-9]{36})\b` without its leading boundary
fires inside `xghp_...`, which is the class of false positive
[`prefilter.go`](../../internal/scan/prefilter.go) already argues about at
length -- one bad keyword took the file hit rate from 1.2% to 18.9%, and
precision is the product. The `\b` is doing a job. What is wrong is asking the
regex engine to find candidates the prefilter has already found.

## Why the shape is available

A candidate-driven loop -- match anchored at each prefilter hit rather than
scanning the buffer -- is only correct where the keyword sits at the start of
every match the rule can produce. That holds for exactly the eight rules that
need it. Measured over
[`testdata/corpus/planted/`](../../testdata/corpus/planted/), the keyword's
offset inside the real match:

| Rules | Keyword offset in the match |
|---|---|
| the eight with no literal prefix | 0 |
| `slack-webhook-url` | 8 |
| `private-key-block` | 15, or 19 with the `RSA ` variant |

The two inset ones are the two that already cost nothing, so they stay on the
whole-buffer path and lose nothing. That the split falls the same way twice is
not a coincidence -- a pattern whose keyword is its head is a pattern with a
literal at the head, which is precisely what the `\b` in front is hiding from
the optimizer.

`private-key-block`'s two offsets are why a fixed back-off window is the wrong
repair even for it: the distance moves with the `RSA `/`OPENSSH `/`ENCRYPTED `
alternation.

## What it buys, and what it costs

[Q122](Q122.md) measures the timeout fail-open at ~390 MiB of text clearing all
ten prefilters, and this is not the largest term in that number so much as all
of it: 64 MiB with every rule clearing costs 9.780s and the same buffer with no
rule clearing costs 0.061s, so the eight passes are 9.719s of it. Measuring the
eight one at a time and adding gives 10.119s, 4.1% over the combined run, which
is the margin to read these figures at.

Removing them does not close Q122. [Q120](Q120.md)'s budget still has to exist,
because a fast scanner with no deadline is still a scanner with no deadline. But
it moves the crossing by roughly an order of magnitude, which changes what a
budget has to refuse and how often anyone meets it.

It is not free and the direction of the cost is content, not size. A buffer
carrying one `eyJ` runs eight anchored matches instead of one full pass and wins
enormously; a buffer carrying a JWT-shaped token every 512 bytes runs 262,144 of
them. Measured at 64 MiB, that dense case already costs 35.5 MiB/s against 52.6
for the same single rule over a sparse buffer, so the whole-buffer pass is
already the cheaper arm somewhere and where the crossover sits has not been
measured. A build that only ever gets faster needs the loop to choose, which is
a real design question rather than an implementation detail.

## Why this is M

Three things, and only the first is code.

`hasKeyword` returns a `bool` and `containsKeyword` returns on its first hit, so
both have to start yielding positions -- and the second pass over the buffer for
the upper-case head means the positions come out unordered and have to be
merged. Then the loop has to decide per rule whether to anchor or scan, which
needs the offset property above expressed as something the loader can check
rather than as a fact about today's ten rules; a rule added later whose keyword
is inset must not silently get the anchored path.

Then it has to be proved identical, not just faster. The findings this produces
must equal the findings the whole-buffer pass produces -- same rules, same
offsets, same order -- over the clean corpus and the planted corpus both, and
over random buffers from a small alphabet where near-misses and boundary
characters are common. That differential is the same shape
[`prefilter.go`](../../internal/scan/prefilter.go) already describes for the
walk-versus-`bytes.Index` change it made, including running a deliberately wrong
variant through the harness to prove the clean result means something.

And the benchmark has to satisfy the design's four rules --
[real heterogeneous files, no repeated chunk, match counts reconciled before any
two timings are compared, fixed cost measured separately](../design/README.md#benchmarking-if-you-benchmark-at-all).
The figures above are min-of-three over synthetic non-repeating buffers, which
meets the second rule and not the first, so they size the item and do not settle
it.

## What is not claimed

The 1175x is a microbenchmark of one pattern against one buffer with no matches
in it, on one machine. It says the prefix skip exists and is large; it does not
say a candidate-driven loop is 1175x, because that loop pays per candidate where
this pays nothing at all. Nobody has built the loop or measured it.
