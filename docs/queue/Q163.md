# The tool shell defaults to zsh, and the expansion assumes bash

Measured 2026-09-19. The question this row filed is answered in both
directions: the tool shell is **readable** from inside the hook, and it is
**not bash** unless something on the machine names bash. The shipped expansion
assumes bash anyway, and the gap is a silent under-scan rather than a stated
residual.

## The hook can read it

Driven on Claude Code 2.1.275 by installing a probe `PreToolUse` hook and
reading what the harness hands one. The environment carries 57 variables, and
two of them are the ones the harness's own shell selection reads:
`CLAUDE_CODE_SHELL=/opt/homebrew/bin/bash` and `SHELL=/bin/zsh`. The first
arrives from `~/.claude/settings.json`, so a value set in settings reaches the
hook's environment rather than only the tool's. This is the instrument the row
asked for, and it is cheaper than the snapshot Q150 went looking for and could
not reach.

## What the harness does with them

Read out of the shipped binary, and the same function in the 2.1.270 CLI and
the 2.1.275 the desktop app runs -- alpha-equivalent rather than byte-identical,
since the minifier renames every identifier in it:

1. `CLAUDE_CODE_SHELL`, if its path contains `bash` or `zsh` and is executable,
   is the shell. It is a substring test on the whole path, not a basename, so
   `SHELL=/opt/bashful/bin/fish` takes the bash branch.
2. Otherwise `SHELL`, on the same two conditions.
3. Otherwise `zsh` and `bash` resolved on `$PATH`, and a fixed list over
   `/bin`, `/usr/bin`, `/usr/local/bin` and `/opt/homebrew/bin`. The list is
   name-major -- all four `zsh` paths precede all four `bash` paths -- and the
   `PATH` hit for the preferred name is unshifted ahead of it while the other
   is pushed behind, the whole order reversing only when `SHELL` contains
   `bash`. Reproducing this needs a hand-rolled `PATH` walk: `exec.LookPath`
   is in `os/exec`, which the build graph is gated against.

So bash is the tool shell only where something names bash. A machine whose
`SHELL` is unset, or names `fish` or `/bin/sh`, gets zsh. What that means for
the population is not measured here and one machine cannot measure it; what is
measured is that this machine's login shell is `/bin/zsh` and that the harness
followed it for 96 tool shells.

The executable test is `access(X_OK)`, falling back to running `<path>
--version` only when that throws. A resolver here can reproduce every step
except the fallback, with no `os/exec` -- and the fallback decides nothing a
shell could reach, since a path that fails `access(X_OK)` cannot be spawned
either. `os.Stat` mode bits are not that test: where they say executable and
`access(X_OK)` would not, the harness falls through to detection and may spawn
zsh while a resolver reading mode bits answers bash, which is the one
under-scanning direction in the resolver. `syscall.Access` is stdlib.

**The ladder was executed, not only read.** The independent review of this row
extracted the 882-byte function from the 2.1.270 binary verbatim, stubbed its
three externals and ran it under `jsc` across nine environment arms, all nine
agreeing with the reading above -- including `SHELL=/opt/bashful/bin/fish`
returning bash off the substring test. That is one rung short of end-to-end and
well above corroboration.

**`SHELL` in a tool process does not say what the harness read.** bash rewrites
it in its own process, so `printenv SHELL` inside a `Bash` call reports
`/opt/homebrew/bin/bash` here while the hook, a child of the harness, reads
`/bin/zsh`. Both are correct and only the second is the ladder's input. Anyone
cross-checking this row the first way will conclude it is wrong.

## This machine ran zsh for a month, and the switch is dated

Recovered from 2,232 session transcripts, 1,374,388 records, 231 of which name
a shell snapshot: 212 distinct tool shells, 96 zsh and 116 bash, with no
interleaving anywhere.

| | |
|---|---|
| last zsh tool shell | 2026-08-24 09:17:09 |
| `CLAUDE_CODE_SHELL` committed to `~/.claude/settings.json` | 2026-08-24 10:01:55 |
| first bash tool shell | 2026-08-24 14:13:07 |

Re-taken independently two days later over 2,247 transcripts: 96 zsh and 117
bash, the same two runs in the same order with the same boundary seconds. The
zsh count is closed and only the bash one accrues, which is what a switched
machine looks like.

`dscl . -read /Users/karl UserShell` still reports `/bin/zsh`. So the 96 are
not an old machine or an old harness: they are what this machine does with the
setting removed, and the setting is 26 days old against a project that assumes
what it produces.

## The consequence, driven end to end

zsh recurses `**` by default and bash does not. On a fixture holding
`top.env`, `sub/mid.env` and `sub/deep/low.env`, driven on bash 5.3.15 and
zsh 5.9:

| operand | bash 5.3.15 | zsh 5.9 |
|---|---|---|
| `**/*.env` | `sub/mid.env` | all three |
| `nomatch*` | the literal word | `no matches found`, and the command never runs |
| `$v` where `v="a b"` | two words | one word |

Through a binary built from `f4150dd`, four payloads and two controls, with an
AWS-shaped key planted in `sub/deep/low.env`:

- `cat **/*.env` exits 0, silent, with nothing written to the coverage log. A
  zsh tool shell sends that key.
- The same file named directly denies on `aws-access-key-id`, so the scanner
  can read it and the expansion is what hid it.
- Moving the key into `sub/mid.env` -- the one file bash's expansion reaches --
  makes the same payload deny, so the silent arm was a considered allow over
  the bash file set rather than a call that did nothing.

**Both controls are load-bearing and a re-take fails without them.** A silent
allow is what this scanner does for a clean file, an unreadable one and a file
it never opened, so the first arm alone distinguishes nothing. The independent
review lost a cycle to exactly that: its first fixture planted
`AKIAIOSFODNN7EXAMPLE`, which the `aws-placeholder` validator rejects by design,
so control 1 exited 0 and the silent arm would have reproduced for the wrong
reason.

That is the failure this project indicts the predecessor for, arriving through
a shell rather than through a rule: a clean exit over a file nothing opened,
with no record that anything was missed.

**Two shapes that look like the same defect are not.** `nomatch*` reads nothing
under either shell, so the divergence is inert unless a file by that literal
name exists, which is Q92's superset and already known. `V="a b"; cat $V`
already defers here, so word splitting costs a record and never an allow.

**The glob is not the only under-scan, and saying so was wrong.** Driven by the
independent review on the same binary: `cat =ls` exits 0 silent with no coverage
record, where zsh's `EQUALS` resolves `=ls` to `/bin/ls` and bash leaves it a
literal. So the class is *any zsh-only expansion that resolves to a real file*,
and `**` is the member that was measured first rather than the only one. What is
true of the glob alone is that it is the only under-scan reachable through an
operand this hook already expands.

## What this row now owes

Resolve the shell from `CLAUDE_CODE_SHELL` and `SHELL` by the ladder above, and
where it is not bash, refuse to expand: a glob operand becomes a coverage
failure and the call defers, which is the verb this project already has for
*could not settle what this reads*. It costs nothing where the shell is bash,
and it replaces a silent allow with a record everywhere else. Refusing only
`**` is the narrower fix and is not available yet, because it rests on the rest
of the expansion agreeing, which `Q184` is the measurement for.

**That fix closes the glob and not the class, and the completing PR must not
claim otherwise.** `=ls` carries no glob metacharacter, so an operand-level glob
deferral never sees it; the remainder is `Q184`'s, which already names `=cmd`.
A reader who takes *Q163 shipped* for *the zsh fail-open is closed* will be
wrong, and this row is where that is said.

The completing PR carries the measurement above into
[`docs/design/README.md`](../design/README.md) beside *A glob operand is
expanded*, and states there what the tree cannot otherwise say: every operand
this hook resolves is conditional on a shell it now reads, rather than on bash.
A row does not survive its own squash, and this measurement is the reason the
design's residual is the wrong shape rather than merely incomplete.

## Residuals, stated rather than closed

- **No headless drive of the detection path, and it may not be closeable
  here.** `claude -p` refuses on the CLI and the desktop binary both -- with
  `OAuth session expired` from this session's environment and `Not logged in`
  from a throwaway `HOME`, and no snapshot is written either way, so the
  snapshot follows authentication. An authenticated run would close it and
  contaminate what it closed: it would write a synthetic zsh snapshot, and a
  transcript naming it, into the population the 96 is counted from. The
  executed-from-binary arms above are what stands in for it.
- **How often a recursive glob reaches a reader is bounded, not counted.** 447
  of 188,898 real `Bash` calls carried a `**/`-shaped word on 2026-09-19, and
  that is an upper bound. The independent review classified a re-take two days
  later: 525 of 191,385, of which 374 are inside heredocs, 105 quoted and 46
  bare -- and several of the 46 are regex artifacts rather than globs. The exact
  count needs this repo's own segmenter. **The metric contaminates itself**:
  total calls grew 1.3% over those two days and `**/` hits grew 17%, because
  writing about this shape is what puts it in transcripts.
- **Windows is unmeasured.** The harness carries a PowerShell provider beside
  the posix one; nothing here establishes whether a `Bash` tool call can reach
  it, and the launcher ships for Windows.
