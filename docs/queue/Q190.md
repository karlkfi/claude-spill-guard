# Three files promise an ungated credential rule the loader never took

`internal/scan/prefilter.go` tells a rule author what to do when a credential
rule's regex does not open on `\b`, because the prefilter will then refuse to
hand it text its pattern would match:

> Such a rule ships with `keywords` empty and pays for the full pass.

The loader does not accept that. Driven 2026-09-19 against `main` at f4150dd,
loading a credential rule whose regex is `sk-[A-Za-z0-9]{32}` with each
spelling of the field, positive control a rule whose regex does not compile:

| `keywords` | `main` |
|---|---|
| absent | refused |
| `[]` | refused |
| `[""]` | loads |
| `["", ""]` | loads |
| `["sk-"]` | loads |

So the documented spelling -- `keywords` **empty** -- has never worked in this
loader, and the repo's own vocabulary keeps the two apart: `gates()` in
`internal/scan/scan.go` says "A list naming no literal -- empty, or holding
nothing but empty strings", which is the distinction that makes `[]` the empty
one. The two spellings that did work are the ones the page does not name.

The pull request completing the row that refuses an unusable keyword value --
named in prose, because its file is deleted by a pull request in flight --
closes those two as well, so after it lands no spelling loads. That changes
nothing about the sentence's truth, which is why this is a row rather than a
hunk in that diff: it was false before that change and is false after it.

**The decision, which is what this row is for.** Either an explicitly-ungated
credential rule exists or it does not, and three files currently answer
differently:

- `internal/scan/prefilter.go` says it exists and names a spelling.
- `rules/README.md`, "Adding a rule" step 1, states the failure mode -- a regex
  not opening on `\b` gets text the gate never hands it -- and gives no remedy.
- `docs/design/README.md`, the `keywords` row of the rule schema, says every
  spelling is a startup failure.

If it should not exist, the fix is to delete the promise and say in
`prefilter.go` that such a regex has to be rewritten to open on `\b`. If it
should, a rule needs a way to declare it that a reader can tell from an author
who simply forgot -- which is the whole reason the loader refuses a bare empty
list today, and any design has to answer it.

**Nothing shipped needs the capability**, which is why this is not urgent. Both
credential rules whose regex lacks a leading `\b` -- `slack-webhook-url` and
`private-key-block` -- carry keywords that sit behind a non-word byte in real
text, `/` before `hooks` and a space before `PRIVATE`, so the gate hands them
their matches. The capability looks accidental rather than designed.

Found by the independent reviewer of the pull request above, which is the
reading worth keeping: it read the prose against the clause rather than against
the diff. Its framing was that the change closed the last working spelling of a
documented remedy; the table shows the documented spelling was never among
them, which moves this out of that diff and into here.

Neighbour: Q189 asks for a gate reconciling `rules/README.md` with what the
loader refuses, and would have caught all three of these sentences. This row is
the decision that gate would then hold the tree to, so Q189 is worth doing
second rather than first -- a gate pinning an answer nobody has chosen pins the
wrong one.
