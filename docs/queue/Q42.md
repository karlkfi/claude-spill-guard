# No gate runs the fresh-machine scripts on bash 3.2

`CLAUDE.md` asserts how bash 3.2.57 behaves, and nothing in CI ever runs that
shell. Every job in `.github/workflows/tests.yml` is `runs-on: ubuntu-latest`,
where `/bin/bash` is 5.x — measured 2026-08-23: one distinct `runs-on` value
across all 21 jobs. So the claim is asserted in prose and checked nowhere,
which is the shape [Q39](Q39.md) walked straight through.

Two first-party bash scripts are developer-machine-facing, and both are
`#!/usr/bin/env bash`:

| Script | Reached by | Under `/bin/bash` 3.2.57 |
|---|---|---|
| `scripts/check-tools.sh` | `make doctor`, on a fresh clone | rc=0, output byte-identical to 5.3.15 |
| `.githooks/pre-commit` | every `git commit`, once `make hooks` runs | rc=1 at line 20 ([Q39](Q39.md)) |

`make doctor` invokes it as `bash scripts/check-tools.sh` (Makefile:104), so
the shell is whatever is on `PATH` rather than what the shebang names — on a
stock Mac that is 3.2.57.

The measured state is that one script is clean and one is broken, and no gate
distinguishes them. check-tools.sh is clean because someone hit the problem and
guarded it; it is not held that way by anything, so the next edit can undo it
silently. That is the whole finding: the gap is not that a defect exists, it is
that the gate which would have caught Q39 does not exist, so the next one lands
the same way.

## What the gate would have to do

Run both scripts under a real 3.2.57. GitHub's `macos-latest` image ships it as
`/bin/bash`, and **this repo is public, so macOS runner minutes are free** —
verified 2026-08-23 with `gh repo view --json visibility` returning `PUBLIC`.
That removes the usual objection to adding a macOS job. Confirm the image still
carries 3.2.57 before relying on it; that is a property of the runner image,
not of macOS, and it is the kind of thing that moves.

Per this repo's convention the job needs a mutation control, and the control is
cheap: a script carrying an unguarded 4.0+ construct must go red. Assert the
mutation mutated — that the shell under test really is 3.2.x — rather than
trusting the runner label, which is the `PATH=/usr/bin:/bin` lesson.

## Why a static check is not a substitute

Q22 and [Q35](Q35.md) are converging on a lint over the errexit prologue, and a
pattern match would catch `shopt -s inherit_errexit`. It catches only that.
`declare -A`, `mapfile`, `readarray`, `${var^^}`, `&>>` and `lastpipe` are all
4.0+ and none of them look like the pattern. Today the only 4.0+ construct in
either script is `inherit_errexit` — guarded in one, bare in the other — so the
surface is small, which is the cheap moment to put an execution gate under it
rather than the expensive one.

Worth deciding together with Q35, since both answer "how does this repo keep
working on a stock Mac" and a static lint plus a documented convention is a
legitimate answer if a macOS job is judged out of proportion for two scripts.

## The prose measurements this came from

The bash-version claims in `CLAUDE.md`'s runner-inputs list — the
`inherit_errexit` bullet and the `&&` errexit bullet corrected in Q38 — are
re-run by nothing, because no runner has both shells. They were measured by
hand on a Mac with 3.2.57 and 5.3.15 both present. A gate of the shape above
would cover the second bullet's claims as a side effect; the first bullet's are
already covered by running check-tools.sh at all.
