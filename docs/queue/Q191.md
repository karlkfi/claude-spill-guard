# The claim check asks whichever remote it was handed, and says origin

`make queue` asserts that every backlog id added by a branch holds a
`refs/queue-ids/<id>` ref on origin -- **every** `make queue`, and therefore
every `make check`. `claims --strict` is unconditional in the recipe; `MERGED`
reaches only `lint`'s `dangling-link` and the release-notes check, so the
trunk-strength run is not what turns this on. It reads that namespace off the
**remote**, with `git ls-remote origin 'refs/queue-ids/*'` -- so the check is
correct wherever `origin` is the repository the ids were reserved against, and
wrong wherever it is not, while printing the same sentence in both cases.

A clone made from a local path is the venue where it is not.
`alloc-queue-id.sh` pushes a reservation straight to GitHub and nothing fetches
it back, so a checkout on this machine need carry none of them in its own ref
store. Clone such a checkout and its `origin` is the checkout, which answers
`ls-remote` with nothing. `ls-remote`
exits 0, which the check reads as *the remote answered and nothing is claimed*,
and every added row is named as unclaimed.

Driven 2026-09-19 and re-driven 2026-09-21, one tree, one branch, one row
added, changing nothing but the origin URL between the arms:

| `origin` | `ls-remote` refs | `queue.py claims` |
|---|---|---|
| a clone whose origin has never seen the namespace | 0 | **exit 1**, `Q191.md files an id holding no refs/queue-ids/Q191 on origin` |
| `git@github.com:karlkfi/claude-spill-guard.git` | 191 at the time, 193 now | exit 0, `1 added id(s) hold a claim on origin` |

**Arm 1 is named by a property and not by a path, because the path stopped
working.** Both drives above used a clone of this machine's checkout, which
held 0 of the namespace at the time. It holds 192 now: a reviewer of this row's
own pull request fetched `refs/queue-ids/*` into it, on an instruction written
by citing this row. So a direct clone of that checkout no longer reproduces
arm 1, and a clone *of such a clone* does -- which is how the reviewer re-drove
it. The mechanism is untouched and the venue is unchanged; what went stale is a
number and a label that pointed at a mutable thing. Verifying a claim about a
population can move the population.

No fetch in either arm, and the clone's own `refs/queue-ids` stayed empty in
both -- the namespace missing from local refs is not what fails the check,
because the check never reads local refs. `git ls-remote origin
refs/queue-ids/Q99999` returns empty at exit 0 against the GitHub arm, which is
the control: an empty answer is indistinguishable from a wrong-remote one, and
that is the whole of the defect.

**The first drive of this changed two things at once and credited the wrong
one.** Its second arm repointed origin at GitHub *and* fetched the namespace,
and the row written from it said the check reads local refs and that
`refs/queue-ids/*` being outside a clone's default refspec is the cause. The
refspec is irrelevant. The arms above hold the fetch out, and the cure is the
repoint alone.

**What makes it worth a row rather than a note about somebody's clone.** The
message states a fact about origin that the checkout is not in a position to
know, and the remedy it gives is wrong twice over: renaming the file burns an
id that was correctly allocated and rewrites a row that was right, and
`--allow` suppresses the check that would have caught a genuinely unclaimed id
later. A reader who trusts the message does damage; a reader who does not has
no way to tell this arm from the real failure, because the two are
byte-identical.

**And the venue is one this repo's own practice sends people to.** Reading
another repo, or this one at a known commit, by cloning into the session
scratchpad is the documented alternative to reading a checkout you do not
control -- and a scratchpad clone of a local path is exactly the clone whose
origin is the wrong repository. `--depth 1` neither helps nor hurts.

**The fix is known and already written once, in a sibling caller.**
`merged-set-lint.py` in the `session-orchestrator` skill runs `queue.py claims`
over an extraction it builds by `git init`, hit this same class against this
repository on 2026-08-23, and closed it by adopting the source clone's own
remote URL before running the check -- its `adopt_remote` carries the
measurement in its docstring. So the answer to whether that script needs the
same treatment is no: it is the precedent rather than a second victim, and what
lacks the fix is every hand-made clone, which has no extraction step to hang an
adoption on.

**The fix merged upstream as `claude-skills#544`** at 21:25:27Z on 2026-09-21,
so this row no longer proposes one. It does both of the things worth doing, and
the second is there for a reason this row did not have: **the two cases are not
separable by anything the check can see.** A repository that has genuinely
reserved nothing answers `ls-remote` exactly as a wrong remote does, so
refusing on an empty namespace cannot be conditioned on which one it is.

1. An entirely empty namespace goes through the same `disclose` path as an
   unreachable remote and a shallow history. Non-strict skips, `--strict`
   fails, and the message names the ids left unchecked and `--remote <url>` as
   the repair.
2. The remote label resolves to its URL, so the failure reads `origin
   (/path/to/clone)` rather than `origin`, and a per-id refusal gains a line
   naming the address and the reservation count it was read against -- which is
   the evidence that it could have gone the other way.

**It does not restore the practice the paragraph above calls unusable, and the
row should not be read as saying it does.** `--strict` is hardcoded in this
repo's `queue` recipe, so the new `disclose` arm becomes a failure here --
upstream's own test asserts that arm exits 1 under `--strict`. What the fix
buys is a message that names the address it asked and `--remote <url>` as the
repair, instead of a false accusation against a correctly reserved id. A green
gate from a clone needs `--remote` passed, or `--strict` reconsidered, and
neither is decided.

**Where the fix lands.** `queue.py` is vendored here, and `scripts/README.md`
digest-gates the copy, so a change written into `scripts/vendor/claude-skills/`
fails the `vendor` gate and forks the file. The fix belongs upstream in
`session-backlog/scripts/queue.py` and arrives here by re-vendor. This row is the consumer's record that the gate
misreports in a clone, which is a fact about this repo's gate and stays here
whatever upstream does.

**Nothing will tell this repo when that fix lands.** `scripts/README.md`
already says no gate here watches upstream, and gives the reason -- the skills
repository is private, so a network oracle would need a token this repo does
not carry. What is new is that upstream has a `vendor-check` whose job is to
send exactly this notice, and it cannot see this repo: its consumer map
hardcodes `scripts/queue.py`, and the copy here lives at
`scripts/vendor/claude-skills/queue.py`. It reports the three sibling
consumers as stale and says nothing about this one. So the re-vendor is a
hand-triggered step, and it is the last thing this row needs before it can be
deleted.

**And it is not a single-change import.** The copy here is pinned at upstream
`c0a239b` (2026-08-22) and still hashes to it exactly, while upstream has
15 commits touching `queue.py` since -- `#544` is only the most recent.
`alloc-queue-id.sh`, vendored beside it, has none. So whoever takes this on is
importing a month of lint and citation changes along with the fix, and that is
a review of 15 commits rather than a `cp`. Worth its own row if it does not fit
the one that does the re-vendor.
