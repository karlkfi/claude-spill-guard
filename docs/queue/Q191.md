# The claim check cannot tell a missing claim from an unfetched namespace

`make queue MERGED=true` asserts that every backlog id added by a branch holds
a `refs/queue-ids/<id>` ref on origin. It reads that namespace out of the local
checkout, and `refs/queue-ids/*` is not in a clone's default refspec, so a
checkout that has never fetched it reports every added row as unclaimed --
naming the files, and prescribing a remedy that would destroy correct work.

Driven 2026-09-19, two arms over one tree, a branch adding `Q189.md` and
`Q190.md` whose refs both exist on origin:

| Checkout | `refs/queue-ids` | `make queue MERGED=true` |
|---|---|---|
| clone of a local path | 0 | **exit 2**, both rows named |
| same clone, origin repointed at GitHub and the namespace fetched | 190 | exit 0, "claims: 2 added id(s) hold a claim on origin" |

The message in the failing arm:

```
queue: Q189.md files an id holding no refs/queue-ids/Q189 on origin: allocate
one with alloc-queue-id.sh and rename the file, or pass --allow Q189 if it was
claimed elsewhere
```

Both refs were on origin the whole time -- `git ls-remote origin
refs/queue-ids/Q189` returns `a45d5e5f` and `Q190` returns `6cf97f82`, with an
`ls-remote` of a nonexistent id returning empty as the control.

**What makes this worth a row rather than a note about somebody's clone.** The
message states a fact about origin that the checkout is not in a position to
know, and the remedy it gives is the wrong one twice over: renaming the file
burns the id that was correctly allocated and rewrites a row that was right,
and `--allow` suppresses the check that would have caught a genuinely
unclaimed id later. A reader who trusts the message does damage; a reader who
does not has no way to tell this arm from the real failure, because the two
are byte-identical.

**And the venue is one this repo's own practice sends people to.** Reading
another repo, or this one at a known commit, by cloning into the session
scratchpad is the documented alternative to reading a checkout you do not
control -- and a scratchpad clone is exactly the checkout with no
`refs/queue-ids`. `--depth 1` does not help; the namespace is missing either
way.

**What a fix could be**, unmeasured and in preference order. Have the check
read the namespace from the remote rather than from local refs, so the sentence
"on origin" is one it has earned; failing that, have it refuse rather than fail
when the local namespace is empty, with a message naming the refspec to fetch.
A third option is to fetch the namespace as part of the target, which is the
cheapest and spends a network call on every run.

Found by the independent reviewer of the two pull requests that added Q189 and
Q190, after recommending the trunk-strength gate be run from a scratchpad clone
-- which is good advice that this defect makes unusable the moment a branch
adds a row.
