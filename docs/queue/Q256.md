# A stalled stat defers a key the call itself carries

A filesystem that stalls can defer a call whose own text holds a key. The call's
strings are matched ahead of its files since Q227, so a stalled **read** no longer
hides them, but the `os.Stat` that resolves an operand runs before any of that text
is matched, so a stalled **stat** still does. `main` behaved the same before Q227,
so this is a limit that remains rather than a regression. The v0.7.0 notes state it
under *Known limits and costs*, and until now no row carried it.

## What is known

The reviewer of #244 simulated this by replacing the call in a test build, at
`ab6e5c6`, on 2026-11-04. With the read blocked, five arms matched their controls.
With `os.Stat` blocked, every arm deferred. **No real stalled filesystem has been
driven**, so how a hung mount reaches this code, and whether the budget's own
deadline is what ends it, is unmeasured.

## What is owed

Match the strings a call carries ahead of the walk that stats its operands, so no
filesystem state can defer a key the payload already holds. The test is the
simulated stat, red on a key in the command string today. A real hung mount is the
control that would settle how much this matters, and it may not be drivable on a
runner.
