# Four mutation controls in `release.yml` repeat one failure assertion

`dry-run-mutation-control` in
[`release.yml`](../../.github/workflows/release.yml) breaks the release config
or the artifacts four different ways, and every step ends in the same eight
lines: run `check-release-artifacts.py` into `mutant.log`, echo the exit code,
`cat` the log, refuse `rc` of 0, and `grep` for the finding that names the
mutation. Only the last `grep` differs.

Two of the four were there before Q97 and two arrived with it, so the shape is
now the file's idiom rather than a copy — which is the argument for extracting
it and also the reason Q97 did not. Restructuring a job three streams were
editing at once would have been the wrong change to bundle.

**The direction that fails quietly is the `grep`.** It is what separates *the
check failed on my mutation* from *the check failed for some other reason*, and
it is the line each copy has to get right on its own. A copy whose phrase drifts
out of `check-release-artifacts.py` still fails red on a broken checker and
stops being able to tell the two outcomes apart — which is Q103's class arriving
through duplication rather than through a stale fixture.

A shell function in the job, or one `scripts/` helper taking the expected phrase
as an argument, leaves four call sites of two lines each. Whichever it is has to
keep the per-step assertion that the mutation had an *effect*, which is not
shared: it reads `checksums.txt` in one step, `git diff` in another, and a
recomputed digest in a third.
