# A coverage record repeats a key in a path it could not open

`coverage.go` says the reason on a record never names the token, and the `CLAUDE.md` rule is
no fragment "because stderr reaches the API". Four `%w` sites wrap an `os` error, whose text
holds the path, into that reason: `reading the file this call would send`, twice for `Read`,
and `reading the path this Grep call searches` and `reading the file this Grep call searches`
for `Grep`. So the value reaches stderr, which rides into the transcript's `hook_success`
attachment, and the log.

## Driven 2026-11-04

A built binary at Q245's head. The key is a file's name, inside a directory with mode `0o000`:

| Call | Key on stderr | Key in the log |
|---|---|---|
| `Read` of that path | yes | yes |
| `Grep` in `content` mode over that path | yes | yes |

A NUL in a `Grep` path reaches the same stat arm and also put the key on stderr.
The prompt surface already holds this: `TestNoPromptRefusalCarriesTheToken` asserts an `@`
token stays out of both streams.

The population is small, since a path has to hold a key and also fail to open. It was not
counted. Also unmeasured: whether this attachment reaches the model.

## What is owed

Name the failure without the path at those four sites, using the `*fs.PathError`'s `Err`,
and keep the path in `Operands` where the log is meant to hold it. Pin it with the
two-stream assertion the prompt test uses.
