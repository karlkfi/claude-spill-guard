# A coverage record names no operand, session or directory

A coverage record says which command it was and nothing a person could use
to find the call. The `Bash` reasons name the command (`"grep"`) and never the
operand, and the record carries `time`, `event`, `tool` and `reason` only. So
`spill-guard coverage` can say 1,364 calls had a directory operand and cannot
say which directories, in which repo, from which session.

Measured 2026-10-01 on v0.5.0: attributing the 2,175 `Bash` records from
2026-09-07 onward needed a timestamp join against every `Bash` `tool_use` in
`~/.claude/projects/**/*.jsonl` (193,138 calls), then a replay of each
candidate through `spill-guard hook` with `XDG_STATE_HOME` redirected. Replay
reproduced 1,362 of them. The rest stayed unattributed, mostly because the
worktree or the files had moved on, and 1,213 of the joins had more than one
candidate inside the window, because parallel sessions issue `grep` within the
same seconds.

That join is what every row closing a coverage class has had to re-derive, and
it is what turned "1,364 directory records" into "1,361 are `grep`, and all
636 that parse are recursive". Q199 and Q201 were sized off it.

Add `session_id` and `cwd` from the payload, and the operand that failed, to
each record. Have `coverage` keep the command name when it groups, where it
currently elides every quoted span to `…`. Both reach `PRIVACY.md`, which says
what the hook writes, and the `privacy-drift` gate holds that against the
source, so the doc change lands in the same PR. The record already carries
paths on the `Read` arm, so a path is not a new class of data in this file.
