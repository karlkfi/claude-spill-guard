# Measure what the card placeholder denylist misses

Blocked by [Q7](Q7.md). Needs the precision corpus to measure against.

`NotPlaceholderCard` lists 34 numbers, the union of two gateways' primary
"valid test card" tables read 2026-08-22 — Stripe's 18 rows and Braintree's 19,
sharing three. That boundary was chosen because it is reproducible, not because
it is complete, and two shapes are known to be outside it.

**A gateway's behavioural matrix.** Stripe publishes 149 distinct numbers once
the decline, 3-D Secure, dispute and per-country tables are counted; 148 pass
Luhn. Those appear in the fixtures of anything integrating with Stripe, which
is exactly the material a scanner reads. Listing them is 115 more entries from
one vendor, and the next vendor starts the argument again.

**Sequential runs.** `1234567890123452` passes Luhn and is not a run of one
digit, so nothing drops it. A structural rule for ascending digits is the kind
of guess that suppresses a real card, which is what the denylist exists to
avoid.

So this is a measurement rather than a design question. Plant a payments
fixture in `testdata/corpus/` — a Stripe integration's test file is the honest
sample — and read what the card rule reports. If the residue is a handful of
numbers, extend the list and say where the new boundary is. If it is the whole
matrix, the answer is a different mechanism and the corpus is what says so.

Nothing here justifies widening the list on a hunch: an entry that is not a
published test number suppresses a real card, and that failure is invisible.
The negative table in `internal/validate/card_test.go` is what holds the line.
