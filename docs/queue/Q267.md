# A space-preceded @ in an inline code span now blocks, unmeasured

`atTokens` in `internal/hook/prompt.go` starts a token at an `@` preceded by
whitespace or by nothing, and reads no markdown. So in ``run `see @.env`
here`` the `@.env` is a token, because a space precedes it, even though it
sits inside an inline code span. In ``run `@.env` here`` it is not one,
because a backtick precedes it.

The census in `internal/hook/testdata/prompt-oracle.json` covers the second
form and not the first. Its `code-span-and-fenced-block` case has
`` `@secret.txt` ``, backtick-adjacent and not spliced, and `@nested/inner.txt`
on its own line inside a fenced block, which is spliced. No case puts a
space-preceded `@` inside an inline span, so whether the harness splices that
form is unknown.

Q236 raised the cost of not knowing. Driven 2026-11-10 against a binary built
from `main` at `939715e`, from a directory holding a `.env` with `PORT=3000`:

| Prompt | Hook |
|---|---|
| ``run `see @.env` here`` | block, on the path |
| ``run `@.env` here`` | exit 0, empty |

Before Q236 the first prompt got a content scan, which this `.env` passes. Now
the path alone blocks it. If the harness does not splice this form, the block
is a false positive on a prompt that quotes a command. Precision is the
product, so that matters. If the harness does splice it, the block is
correct, and the census is missing a case the tokenizer depends on.

This was reported by the independent review of #267 at `64b726c`.

**Measure:** one census case, taken by `prompt-oracle.yml` against the pinned
`claude`, since only the harness can say whether the form splices.

## Done

`prompt-oracle.json` carries a case with a space-preceded `@` inside an inline
code span, taken against the pinned harness by `prompt-oracle.yml`, and
`atTokens` agrees with it. If the harness does not splice the form,
`atTokens` stops treating it as a token, and the census case pins that.
