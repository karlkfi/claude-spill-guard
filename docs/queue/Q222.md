# A deferred UserPromptSubmit leaves no hook_success attachment

Two sentences say the coverage record's stderr line "rides into the
transcript's `hook_success` attachment":
`docs/design/README.md:1533:attachment; and a capped JSONL under` and
`CLAUDE.md:663:attachment, and a capped JSONL under`.

The design's own channel table disagrees, for one event. Its row
`docs/design/README.md:1608:| the marker on stderr | — | — |` was driven
2026-09-01 on 2.1.251 with a real `UserPromptSubmit` hook, and says a hook's
stderr on exit 0 reaches neither the stream nor the transcript.

**Driven again 2026-11-01, on 2.1.290, the table holds.** `claude -p` under a
clean `HOME`, the shipped binary as the only `UserPromptSubmit` hook, one prompt
naming six 400 MiB text fixtures so the scan reached its 45-second budget and
deferred. The coverage log under `$XDG_STATE_HOME` got its record. The session
transcript got no hook attachment of any type: no `hook_success`, no
`hook_non_blocking_error`, nothing naming the hook. The same drive with the
budget lifted produced a `hook_cancelled` attachment, so the instrument can see
hook attachments when the harness writes one. Both drives, and how the
fixtures were cut, are in `docs/design/README.md` under *Driven end to end, on
built binaries*.

## What is owed

`PreToolUse` is the half nobody has driven. A `Read` or `Bash` call reaches the
hook only after the model has chosen it, which is an API call, so this
credential-free route cannot reach it. Either drive it against a real session,
or scope both sentences to what was measured. As written, they promise a trace
in the transcript that the one event measured twice does not leave. A reader
looking for a deferral's record there finds nothing and concludes nothing
deferred.

The coverage log is unaffected: it is the sink that did record the deferral.
