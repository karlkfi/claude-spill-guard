# A combined diff writes two marker columns and neither is crossed

`private-key-block` crosses one diff marker in front of a line. `git show` of a
merge commit emits `--cc` output, which writes **one column per parent** — so a
conflict-resolved key arrives with two:

```
@@@ -1,2 -1,2 +1,6 @@@
++-----BEGIN RSA PRIVATE KEY-----
++Proc-Type: 4,ENCRYPTED
```

Driven 2026-09-21 against the shipped rule, on constructed `--cc` layouts:

| Prefix | Plain layout | Encrypted layout |
|---|---|---|
| `++` | reported, by the base64 accident | **not reported** |
| `--` | **not reported** | **not reported** |
| `+ ` | reported | reported |
| `- ` | reported | reported |
| ` +` | reported, by the same accident | **not reported** |
| ` -` | **not reported** | **not reported** |

The one-column-plus-space forms are what `--cc` writes when only one parent
changed the line, and those are covered. What is not is a doubled marker, and a
marker in the **second** column: the clause reads a marker and then horizontal
whitespace, so ` +` and ` -` put them the wrong way round. The ` +` plain cell
is the base64 accident a third time — `[-+]?` takes nothing, `[ \t]*` takes the
space, and `+` is inside the body class — which is why the encrypted layout
beside it, where the accident cannot reach the `Proc-Type` line, is the cell
that says what the shape really does.

The marker-then-whitespace ordering is deliberate and is what keeps an indented
list item off the rule — see `rules/README.md` under the diff markers — so the
fix is not to relax it.

The `++` plain row is the same accident Q157 recorded: `+` is in the base64
alphabet, so the body line reads as base64 starting two bytes early. Nothing
chose it and it does not reach the encrypted layout.

**Do not read this as a licence to widen.** `[-+]{0,2}` is the obvious arm and
it buys an unmeasured false-positive surface — `-- ` is the conventional email
signature separator, and `++` opens a line in more than one markup dialect.
`rules/README.md` requires a widening to be paid for by a measurement, and the
sweep Q157 took cannot pay for this one: of 263,734 files in `~/go/pkg/mod`,
303 were patch-shaped and **none** carried `PRIVATE KEY`, so that population
says nothing about the diff family in either direction.

**The instrument to use instead already exists and is named in
`rules/README.md`.** The independent review of the Q157 pull request walked
`~/workspace` with the same four arms — 8,514,452 files, 13,737 carrying
`PRIVATE KEY`, 876 patch-shaped of which **24 do carry one**. That is a
population with real key-bearing patches in it, so it can price a marker arm
where the module cache cannot. Start there, and read that section's caveat
first: the tree holds live worktrees and does not reproduce between runs, so a
figure from it is one run rather than a re-runnable gate.

**What is not measured**, and what would settle it:

- whether a combined diff ever reaches a session carrying a key. A `--cc` hunk
  needs a merge commit that resolved a conflict *inside* the key block, which
  is rarer than the single-parent shapes Q157 covered.
- what `[-+]{0,2}`, or a second marker admitted only when it equals the first,
  costs on the clean corpus and on a differential.
- whether ` +` is worth separating from the doubled case. It is one character
  in a different position and may be the cheaper half.

The producer is Q157's, narrowed: `git show <merge>`, `git log -p --cc`, and
`git diff` against two parents. `git format-patch` does not emit combined diffs.

Found by the independent review of the pull request that closed Q157, which
drove the first four rows; the two second-column rows were driven answering it,
twice and independently — once by that review and once by the authoring session,
on separately written fixtures that agreed on all twelve cells. It is a
different mechanism from [Q187](Q187.md) — that one is about a line the key's
file never had, this one about how many columns sit in front of a line it does.
