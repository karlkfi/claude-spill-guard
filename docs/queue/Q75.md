# No gate builds the scanner for Windows, or for any non-host target

`scripts/cross-compile.py` builds `./cmd/...` for five targets. `cmd/spill-guard`
imports none of this module's packages, so what the gate proves builds on
`windows/amd64` is a `main` that prints a version string. Measured 2026-08-27:

```
$ go list -deps ./cmd/... | grep -c 'claude-spill-guard/internal'
0
$ go list -deps ./...     | grep -c 'claude-spill-guard/internal'
4
```

The second line is the control. Without it a zero reads as the probe being
unable to see `internal/*` at all.

`cross-compile` is also the only gate that varies `GOOS` — nothing else under
`scripts/` names it. `test`, `no-deps`, `no-network` and `vulns` all walk
`./...`, so they do reach the four packages. What decides the platform is where
those jobs run, and that is a property of the workflow rather than of any
script. Parsed out of `.github/workflows/tests.yml`:

```
runs-on: ubuntu-latest        29 jobs
runs-on: ${{ matrix.os }}      2 jobs  -- launcher, launcher-mutation-control
```

29 + 3 + 2 is the 34 jobs `gh run view --json jobs` reports for one run, so the
parse is complete. `launcher` is the only matrix job in the file.

Put the three readings together — `./cmd/...` reaches 0 of 4, `cross-compile`
is the only gate that varies `GOOS`, every other job is `ubuntu-latest` — and
the statement is not "not just Windows":

> `internal/bash`, `internal/rules`, `internal/scan` and `internal/validate` are
> compiled for `linux/amd64` and for no other target, ever, in CI.

Five targets ship. The scanning core is built for one. Each reading alone is
arguable; the three together are not. The `launcher` job does run on
`windows-latest`, and what it exercises there is a `.cmd` polyglot rather than
any Go.

## Why this is worth a row rather than a shrug

Nothing is broken today. The gate table in [`CLAUDE.md`](../../CLAUDE.md) says
`cross-compile` covers "all five shipped targets build", the gate prints `all 5
targets build`, and both are true statements about a `main` that prints a
version string. That is the shape
this repo keeps refusing: a check whose green is a fact about something other
than what a reader takes it for, with nothing in the output to say which.

## What retires it

Q50 wires `cmd/spill-guard` to `internal/*` — the `go:embed` of the shipped
ruleset lands there — and on the day it merges this gate starts covering what
its name claims, with no edit to the script. The link is deliberately not here:
the pull request implementing Q50 deletes that row, so a href would dangle the
moment both land.

That pull request is open, and it does retire this. Measured 2026-08-27 on its
branch: `cmd/spill-guard/main.go` imports `internal/hook`, which calls
`scan.Buffer`, so `go list -deps ./cmd/...` stops reporting 0. Until it merges,
a `windows/amd64` build of the scanner has never happened in CI.

Two ways to close the gap before that: point the script at `./...`, which makes
it a cross-platform build gate rather than a shipped-artifact gate and is a
change to what it means; or leave the script alone and add a step that vets the
library packages per target. The second was taken by hand on Q47 —
`GOOS={windows,linux,darwin} GOARCH=amd64 go vet ./internal/...`, exit 0 on all
three — which is the measurement a gate would be automating.

Whichever is chosen, say in the script's docstring which question it answers.
The confusion is not that the current answer is wrong; it is that the name does
not distinguish the two questions.
