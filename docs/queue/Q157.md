# A unified diff that *adds* a private key is not matched at all

`private-key-block` steps from the header to the body over whitespace and line
endings. A unified diff prefixes every line of an added file with `+`, which is
neither, so no part of the clause crosses it: not `[ \t]*` in front of the
body, and not the `[ \t]*` in front of `Proc-Type:` and `DEK-Info:`. The whole
block goes unreported.

Driven 2026-09-07 against the shipped rule, on `git diff --cached` output for a
newly added encrypted PKCS#1 key — git 2.55.0, a scratch repository:

| Where the key sits in the patch | Reported |
|---|---|
| context lines, prefix `` (one space) | yes |
| **added lines, prefix `+`** | **no** |

The first row is the shape the whitespace-separator work landed, completed in
the same pull request that filed this row. It is the *rarer* of the two: a key
shows up in a patch's context only when something near it changed, where a key
being committed shows up as added every time. So the direction with traffic
behind it is the one still missing.

**Do not read this as a licence to widen.** `rules/README.md` is explicit that
each widening is paid for by a measurement, and this one is wider than it looks:
admitting an arbitrary prefix in front of the body is the bounded-window shape
that section already refuses by name, because it crosses prose.
`testdata/corpus/clean/tls-runbook.md` is the file that refuses it, and any
candidate has to leave the clean corpus at zero. `+` and `>` are the two
concrete prefixes worth pricing — the second is a quoted-reply email — and a
per-prefix arm is a different proposition from a window.

**What is not yet measured**, and what would settle it:

- whether any real population carries the shape at all. The differential taken
  for the separator work — `~/go/pkg/mod`, 244,160 files, 753 carrying
  `PRIVATE KEY` — was not re-run against a prefix-tolerant candidate, so its
  cost is unknown in both directions.
- what a `+`-prefixed arm costs on the clean corpus, which is 13 files and
  cannot settle precision on its own. The differential is what can.

The producer is not in doubt: patches reach a session through `Read`, through a
`Bash` reader pointed at a `.patch` file, and through an `@` splice. Only the
recall is.

Found while completing the whitespace-separator row, which is in flight in the
same pull request as this one and is a different mechanism: that one is about
what the separator may contain, this one about what may sit in front of every
line. Widening the separator does not close it, which is why they are two rows.
