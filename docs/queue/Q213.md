# A nameref assigns a name the tracker never sees

`declare -n r=CDPATH; r=<away>; cd target; cat f` makes `r=…` assign CDPATH,
so bash's `cd` searches `<away>` and reads `<away>/target/f`. The tracker
reads `r=<away>` as an assignment to `r`, follows the `cd` to `./target`, and
scans the clean local copy. With the key only in the CDPATH copy, that is a
silent allow. Driven 2026-10-25 on built binaries, bash 5.3.15 under `env -i
bash --norc --noprofile -c`:

| command | bash reads key | `main@9f0fbdc` | Q186 branch `f91bcfb` |
|---|---|---|---|
| `declare -n r=CDPATH; r=<away>; cd target; cat f` | yes | allow | allow |
| `typeset -n r=CDPATH; r=<away>; cd target; cat f` | yes | allow | allow |

Found by the reviewer of #203, who counted 4 of 223,749 real `Bash` calls
carrying a `-n` nameref (their count, not re-taken here).

The mechanism is not CDPATH's. `clobbers` and `poisonVars` key on the
identifier at the head of each `declare` argument, which for `r=CDPATH` is `r`.
Nothing in `internal/hook/vars.go` models a nameref, so the same aliasing
should reach any name the map or a stop rule tracks: `declare -n r=P;
r=/x; cat $P/f` and `declare -n r=IFS; r=/; …`. Neither has been driven. The
reviewer flagged IFS as likely, unverified.

The fail-closed answer is small: a `declare`, `typeset` or `local` carrying
`-n` (alone or in a flag cluster) is treated as `eval` is, which kills the map,
stops propagation, and sets the CDPATH flag. Drive the P and IFS rows before
deciding whether anything finer is worth it.
