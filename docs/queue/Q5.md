# The scan pipeline: binary skip, prefilter, match loop

Blocked by [Q4](Q4.md). Consumes compiled rules.

Four stages, specified in `docs/design/README.md` under **Pipeline**. Each one
exists to keep the next off work it does not need to do, and two of the four
have a measured trap attached.

## The two that are easy to get wrong

**The prefilter needs word boundaries, not `strings.Contains`.** Naive matching
finds `sk-` inside `disk-containerd-…`, and one broad keyword (`AC`) took the
file hit rate from 1.2% to 18.9% on real files. It is worth roughly 280x
— 255–307 MiB/s against 1.0 MiB/s for the regex pass — and it is exquisitely
sensitive to keyword quality. It gates the credential family only; numeric PII
has no literal to anchor on.

**Never fold the rules into one alternation.** Measured at 0.5x in Go and 0.7x
with Rust's `RegexSet`: the DFA state space explodes and the lazy-DFA cache
thrashes on heterogeneous input. Two independent engines, same result, so this
is a property of the approach rather than of either implementation. Run the
patterns separately.

Binary skip is a NUL byte in the first 8 KiB. In the benchmark corpus one PNG
was 55% of all bytes.

## Benchmarking, if this item benchmarks at all

Real heterogeneous files, never a repeated chunk — a 176-byte block repeated
47,662 times overstated one engine by roughly 10x. Verify match counts agree
before comparing any two timings, and measure fixed startup cost separately
from throughput: below about 8 KB it dominates, and a per-invocation hook lives
there. `docs/design/language-choice.md` §2 has all four in full.
