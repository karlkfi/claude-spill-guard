# `make release-claims` runs one of the three arms CI requires

The gate target invokes the checker once, in whatever release state the
machine is actually in:

```
Makefile:180:	$(PYTHON) scripts/check-release-claims.py
```

The workflow's mutation-control job runs three, and the two it adds force the
state rather than reading it, in the baseline step of
`release-claims-mutation-control` in
[`tests.yml`](../../.github/workflows/tests.yml):

```
make release-claims
python3 scripts/check-release-claims.py --assume-release none
python3 scripts/check-release-claims.py --assume-release released
```

The comment above that step says why they are there: every red below is attributable to
its own mutation only if the tree is green *in the state that arm forces*. So
they are not decoration a gate could skip. They are the property the prose is
supposed to hold — true whether or not a release exists — and `make check` has
no reader for it.

## What that costs, measured

Prose that passes every local gate reddens CI on push. Taken 2026-09-07 on a
branch whose only relevant change was one sentence in
`docs/design/distribution.md`:

```
make release-claims                                   EXIT=0
check-release-claims.py --assume-release none          EXIT=1
unbuilt claim: docs/design/distribution.md:335: ... so nothing already
shipped is refused by it.
release-claims: 1 sentence(s) claim a release produced something, and
there is no release.
```

`already` within 40 characters of `shipped`, beside a release reference, is a
completed-aspect claim under `--assume-release none`. Three releases exist, so
the real-state arm reads it as true and returns 0. The failure surfaced as a
red job on a pushed pull request, was reproduced locally by running the arm by
hand, and was fixed by rewording the clause — a round trip that the gate the
repository tells sessions to run could not have saved.

## Why this is not just a missing flag

`CLAUDE.md` says `make check` is every gate and that one pass reports the whole
tree, and the `queue` gate is already the documented exception: `make queue
MERGED=true` is named as *the only local command that sees what the push to
`main` will see*. This is a second exception that is not named anywhere, which
is the difference. A session reading the gate table has no way to learn that
`release-claims` is weaker locally than in CI.

Three answers, and picking between them is the work:

- **Run all three arms in the target.** Simplest, and it makes the local gate
  slower by two subprocess invocations over the same file set. It also changes
  what a green `make check` means on a machine mid-release, which is the case
  the single-arm form was presumably written for.
- **A `MERGED=true`-shaped opt-in**, matching what `queue` already does, so the
  weaker default is at least the documented one.
- **Leave the target alone and document the gap** in the gate table, which
  costs a round trip per occurrence and is the status quo with a warning on it.

Whichever lands, `gate-drift` pins the gate table and the CI job list, so the
row's diff reaches the registry the batch shares.
