# A finding inside the buffer the budget stops on is lost

When the deadline fires, the verdict reads what the scan published, and the scan
publishes a buffer only once it has finished that buffer. So a match made in the
buffer still running is thrown away with the rest of it.

Driven 2026-11-04 on a binary built from the fix for Q227, with the budget cut to
1s. A `Read` of a 400 MiB fixture with the planted key at byte 0 defers at
1.023s, and the same file at the shipped budget blocks, at 10.756s and at 20.820s
on two runs. The call's only other buffer is its own `file_path`, which holds no
key, so nothing else could have supplied a verdict.

`match` in `internal/scan/scan.go` already works one rule at a time, so handing
the caller each rule's findings as the rule finishes is one plausible shape. It
would not reach a key whose rule is the one still running, because
`FindAllSubmatchIndex` returns nothing until it has walked the buffer. Neither
that shape nor its effect has been built or measured.

The reach is narrower than Q227's was. On a prompt this needs a file big enough
to overrun, and the design measures the harness splicing nothing that size. `cat`
and `head` have no such limit, so `head -5 big.log` is the case to drive.

[`docs/design/README.md`](../design/README.md), *The order the budget spends*,
names this as what the buffer-level fix leaves open.
