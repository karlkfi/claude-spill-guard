# The launcher is checked out LF-only, which cmd.exe does not support

`.gitattributes` says `* text=auto eol=lf`, with a comment giving the reason:
the harness and the hook are read by bash and by Python on every platform,
including Windows under Git Bash, and a CRLF checkout breaks bash outright.
That reasoning is right about every file it was written for and does not reach
`hooks/run-spill-guard.cmd`, which cmd.exe reads as a batch file.

cmd.exe wants CRLF. An LF-only batch file mostly runs, and the constructs that
break are `goto` and multi-line parenthesized blocks, because cmd seeks by byte
offset rather than parsing the file whole. The failure is silent in the
direction this project cares about: the launcher stops before writing its deny,
the shell exits non-zero with empty stdout, and only exit 2 blocks — so the tool
call goes through unscanned with nothing in the transcript.

## What is measured, and what is inferred

Measured, on PR #24 at 42b9ffe: `launcher (windows-latest)` failed with the
launcher producing empty stdout and exit 1 in the one case that fell through
past a `for /f` parenthesized block. Every other case on that platform passed —
the two that never entered the block, and the two that left it by `goto` or
`exit /b`. Removing the block turned the lane green at 0eb7463.

Inferred, and not isolated: that the block was mis-parsed because the file is
LF-only. The discriminator fits — a `goto` resets cmd's file position and
falling through does not — but proving it needs the block restored on a branch,
and that was not worth pushing to a PR that had just gone green.

So the tree currently works by not using the construct that broke, rather than
by giving cmd.exe a file it supports. The next `goto`-heavy edit to the batch
half can reintroduce the failure, and nothing would report it until Windows CI
ran.

## The reason this is not a one-line fix

The launcher is a polyglot: cmd.exe reads the batch half, `sh` reads the POSIX
tail. CRLF breaks the POSIX half — `set -eu` followed by a carriage return is
an invalid option — so the file cannot be uniformly CRLF any more than it can
be uniformly LF.

Three shapes, and choosing is the item:

- **Mixed endings, held by a gate.** CRLF down to the `CMDBLOCK` terminator,
  LF from there on, with `-text` in `.gitattributes` so git never normalises
  it, and an assertion in `scripts/check-launcher.py` beside the mode-bit one.
  Exact, and delicate enough that it must be gated rather than remembered.
- **Keep LF and forbid the constructs.** Assert the batch half contains no
  parenthesized block, which is what the tree accidentally satisfies today.
  Cheap, and it constrains every future edit to a dialect nobody documents.
- **Two files.** Only if `hooks.json` can name a different command per
  platform, which is a question for [Q10](Q10.md) rather than an assumption to
  make here.

Whichever is chosen, it needs a Windows case that goes red on the untreated
file — the same standard the mode bit is held to.

## This is not only this repo's

`branch-guard`'s shipped `run-python-hook.cmd` is LF-only too — 0 CRLF against
90 LF in the installed 1.10.0 — and it carries `goto`, `call :label` and a `for`
block. If the inference above holds, that launcher has the same latent defect
and nothing has ever driven it on Windows, which is exactly what Q8 said about
suites that never execute the launcher — named without a link because that row
is completed by the PR that filed this one. Worth reporting upstream once this
is settled here.
