# Report the LF-only launcher to branch-guard

`branch-guard`'s shipped `run-python-hook.cmd` looks like a fail-open on
Windows, for a reason this repository measured on a file of the same
construction rather than reasoned about.

## What was measured here

`hooks/run-spill-guard.cmd` shipped LF-only, because `.gitattributes` said
`* text=auto eol=lf` for everything. On `windows-latest` the launcher exited 1
with empty stdout in the one case that fell through past a `for /f`
parenthesized block, and cmd.exe named it:

```
The system cannot find the batch label specified - deny_missing
```

Only exit 2 blocks a tool call and a `deny` object on stdout blocks whatever
the exit code, so exit 1 with nothing on stdout is neither. The launcher was
installed, silent, and enforcing nothing on that platform.

Four arms on GitHub runners, three cases each, settled it. `block x LF` failed;
`block x CRLF`, `noblock x LF` and `noblock x CRLF` all passed on Windows,
while every CRLF arm died on POSIX with `set: Illegal option -`. LF-only
endings make cmd.exe lose its file position across a parenthesized block, and
the `goto` after it cannot find its label. Removing the block was a mask, not a
cure.

The fix shipped with the PR that filed this row: CRLF down to the `CMDBLOCK`
terminator and LF after it, `-text` in `.gitattributes` so git cannot normalise
the split away, an assertion in `scripts/check-launcher.py`, and a
`windows-latest` control that reproduces the failure and requires the gate red.

## What is inferred about theirs

Measured: the installed `branch-guard` 1.10.0 ships
`hooks/run-python-hook.cmd` with **0 CRLF and 90 bare LF**, and that file
carries `goto :found`, `call :try_interp` and a `for %%I in (...) do (...)`
block with the `:found` label sitting after it.

Inferred, because their file has not been driven: that the construction fails
the same way. It is the same interpreter, the same endings and the same shape —
a `goto` whose label sits past a parenthesized block.

The consequence there is worse than a wrong answer. Their launcher's own
comment says a guard launched by a bare `python3` "silently enforces nothing"
on machines where the interpreter probe fails, which is the failure it was
written to prevent; if the label lookup dies first, the guard does not fire and
the tool call proceeds regardless of what the probe would have found.

## What this row is for

Draft a backlog row for `~/workspace/claude-bouncer` under `docs/queue/`,
labelled `branch-guard`, saying exactly the above: which half is measured here
and which is inferred about their file, the version measured, and that the
failure mode is a fail-open rather than a wrong verdict. It costs them one
`.gitattributes` line and a driven Windows case to settle either way.

Do not overstate it. Nobody has run their file, and a construction that fails
here is a strong reason to look rather than a defect proven there.
