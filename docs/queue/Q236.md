# A `@.env` in a prompt skips the path refusal

The path refusal stops `cat .env` and a `Read` of `.env` before anything opens
the file, on the argument that most of what a dotenv file holds matches no rule.
A `@.env` in a prompt splices the same file into the context and gets the content
scan alone, so a value no rule knows crosses.

Driven 2026-11-03 through the v0.6.1 binary, on a `.env` holding `A=1`:

| Payload | Result |
|---|---|
| `Bash` `cat .env` | `deny`, "is a dotenv file" |
| `Read` of `.env` | `deny`, "is a dotenv file" |
| `UserPromptSubmit`, `see @.env` | exit 0, empty stdout and stderr, no coverage record |

The README now says so, under *What it does not catch*, and its live check tells
the reader that `@.env` is allowed. Nothing in `internal/hook/guarded.go` or under
*A path refused* in `docs/design/README.md` mentions the prompt surface, so this
reads as an omission rather than a decision. That is an inference from what those
two say nothing about, so check it before writing the fix.

## The fix

Run the path class over a prompt's `@` tokens, with the block shape that surface
needs. The empty `.env` check in the README then reaches the prompt surface too,
which it cannot today, and those two sentences in the README come out with the
fix.

The class is measured against `Bash` and `Read` traffic only. How often a real
prompt names one of these paths is unmeasured, so take that first, with a sweep
of `@` tokens in the transcripts.
