# `private-key-block` misses a PEM block indented inside YAML or Markdown

The rule requires the base64 body to begin a line. A key pasted into a YAML
block scalar or an indented Markdown code block has whitespace in front of it,
so nothing matches:

```yaml
tls.key: |
  -----BEGIN RSA PRIVATE KEY-----
  QUJDREVGR0hJSktMTU5PUFFSU1RVVldYWVowMTIzNDU2Nzg5YWJjZGVmZ2hpamts
```

That is a Kubernetes secret manifest, which is one of the commoner ways a key
reaches a file somebody then `cat`s. Measured through the compiled rule when
the RFC 1421 widening landed, four arms, so neither direction can be a silent
no-run: indented by four reports nothing, the same text un-indented reports
one, indented by two reports nothing, and header-indented-body-not reports
one. It is the body's indentation that decides it, not the header's.

It predates that widening and is not caused by it. The clause has required the
body to begin a line since it was written; the widening only taught it to step
over `Proc-Type:` and `DEK-Info:` first.

**The candidate is `[ \t]*` in two places, not one.** Putting it only before
the body is the obvious form and it leaves half the defect standing: an
encrypted key's `Proc-Type:` and `DEK-Info:` lines are indented too, so the
step over them never engages and the key is still missed. Measured against the
shipped rule, six arms, both directions marked:

| | shipped | `[ \t]*` before the body only | `[ \t]*` in both places |
|---|---|---|---|
| un-indented plain | match | match | match |
| un-indented encrypted | match | match | match |
| indented plain | miss | match | match |
| **indented encrypted** | miss | **miss** | match |
| prose under a displayed header | miss | miss | miss |
| undefined field then a body | miss | miss | miss |

So the arm to write is

```
[\r\n]+(?:[ \t]*(?:Proc-Type|DEK-Info):[^\r\n]*[\r\n]+)*[ \t]*[A-Za-z0-9+/=]{32,}
```

and the fixture set needs an indented *encrypted* key, not only an indented
one. Found by the review of the pull request that filed this row, which drove
the row's own candidate against a case the row had not listed — the same
defect this row's parent was about, one level up.

It was not taken with the widening because that row was scoped to the three PEM
formats and this is a fourth defect in the same clause.

**One clean-corpus reading exists and it does not settle the row.** Both forms
above report 0 over `clean/` as it stands, and that zero is over material that
approaches them: `tls-runbook.md`'s "What the parts look like" section holds an
indented header *and* an indented base64 line, and neither candidate fires
because prose sits between them, which is the behaviour wanted. What the reading
cannot cover is the corpus this row goes on to change — the fixtures below are
new clean and planted files, and a count taken before they exist says nothing
about the half that has to hold afterwards. Take it again at the end.

A 200-byte window of
any printable bytes was measured there and refused: it fires on
`testdata/corpus/clean/tls-runbook.md`, which lays out a header, explains the
format in prose, and shows a body line inside 200 bytes. `[ \t]*` is much
narrower and has not been driven against the clean half at all. Add an indented
fixture to `testdata/corpus/planted/`, widen, and read the clean count.

The other half is what the *header* needs. `-----BEGIN` can sit anywhere on a
line today, so the header half of the indented case already matches; only the
body half fails. Check that admitting indented bodies does not make a quoted
header plus an indented base64 example reportable — the runbook's "What the
parts look like" section is exactly that shape and is the file to read the
count off.
