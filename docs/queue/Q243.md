# us-ssn pays a whole-buffer pass though a finding needs a label

`us-ssn` took the shipped set from 97.75 to 38.40 MB/s, 2.55x, over 312 MB of real text
on `efac304`. An independent re-take on a different sample read 82.88 to 35.51, 2.33x.
Every buffer pays that, yet a finding needs a label within 64 bytes before the value and
most buffers hold no label at all.

Unmeasured: how much of that a check for any label before running the regex would
recover. It re-opens a decision rather than extending one. `docs/design/README.md`
says `labels` is read after the match and "gates nothing", and the loader refuses
`keywords` on a `pii` rule so an author cannot ask for a literal gate there.

Two things a measurement has to answer before the design moves. The label gate would
have to find exactly what the validator finds, so its word-boundary rule and its case
folding must agree with `validate.NearLabel`, or a value crosses that does today. And
the rate that matters is the buffer the budget bites on, not the 2.55x: the worst case
tried is 32 MiB of grouped digits at 1.357s, well inside the 45-second budget, so this
is throughput a session does not feel on one file and may not feel at all.

If the answer is under a human's notice, delete this row rather than do the work.
