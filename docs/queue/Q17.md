# A tools module and a make doctor target

Blocked by [Q3](Q3.md). Both patterns want a module to hang off.

## The tools module is how the no-deps gate survives contact with real tooling

This is the half that is load-bearing rather than convenient. `Q3`'s `no-deps`
gate requires the runtime `go.mod` to carry no `require` block, and the project
still wants golangci-lint, govulncheck and actionlint pinned to versions rather
than to whatever a runner happens to install.

The answer is the standard Go tool-dependency pattern
(<https://go.dev/wiki/Modules#how-can-i-track-tool-dependencies-for-a-module>),
with `tools/` as its own module: a `tools.go` under a `//go:build tools`
constraint importing each tool, so `go mod tidy` keeps them in **that** module's
`go.sum` and out of every runtime one. Tools then run at their pinned version
with `(cd tools && go run <path> ...)`.

Without it the two requirements collide and one of them loses — usually the
gate, quietly, because pinning a linter is obviously reasonable and the
`require` block it adds is not obviously the thing the project promised not to
have.

## make doctor

A `doctor` target over a `scripts/check-tools.sh`: report which required CLI
tools are missing or installed-but-not-on-PATH, with per-OS install and
PATH-fix hints for each. It has to run **without** the pinned tool binaries
present, so it works on a fresh clone — that property is the point of it and is
the easy one to lose, since the natural implementation reaches for the tools it
is checking for.

It earns its place here more than in most repos: contributors will be on macOS,
Linux and Windows, and the release path adds cosign, goreleaser and the
platform package managers to the list of things that have to be present.

## What to decide while building it

Which tiers exist. A required tier (Go, git) and a release-only tier (cosign,
goreleaser) is probably the split; there is no e2e tier here. Tiers copied from
a larger project are how a doctor target starts reporting absences nobody needs
to fix.
