# The rule's ASIA and A3T arms have no planted proof

`aws-access-key-id` matches five prefixes: `A3T[A-Z0-9]`, `AKIA`, `ASIA`,
`ABIA` and `ACCA`. One of them is exercised end to end.

Measured 2026-08-27, by deleting arms from the regex in
[`rules/spill-guard.json`](../../rules/spill-guard.json) and running
`go test ./...` over the tree:

| Mutation | Suite |
|---|---|
| drop `ASIA` | green |
| drop all four non-`AKIA` arms | green |
| drop `AKIA` instead | red -- 1 failure in `cmd/spill-guard`, 4 in `internal/hook` |

The last row is the control: the suite can see an arm go missing, so the two
greens above it are a measurement rather than an inert instrument.

The cause is that `testdata/corpus/planted/` carries `aws-access-key-id.env`
and `aws-access-key-id-utf16le.env`, both `AKIA`, and
`TestEveryEnabledRuleHasAPlantedFile` is satisfied by either. Every other
`ASIA` string in the tree is something else: `prefilter_test.go` tests it as a
keyword, `capture_test.go` and `load_test.go` carry it inside a regex literal,
and the only `ASIA` value the pipeline ever sees is `ASIAIOSFODNN7EXAMPLE`,
which `aws-placeholder` is required to drop. The corpus's one ASIA reading is
a rule staying quiet; nothing measures one firing.

Plant an `ASIA` session key. For `A3T`, `ABIA` and `ACCA`, decide per arm
whether it is worth a fixture or worth cutting -- an arm no test can distinguish
from absent is surface with no evidence behind it, and this ruleset was
inherited rather than written, so the question of which prefixes AWS actually
issues has not been asked here. Each new file is `planted/`, so each value
needs the mark [`testdata/corpus/README.md`](../../testdata/corpus/README.md)
prescribes and each must produce exactly one finding.
