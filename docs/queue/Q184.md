# The rest of the zsh delta beyond globbing is unmeasured

`Q163` established that the tool shell is zsh unless something on the machine
names bash, and measured exactly three differences: `**` recurses, an unmatched
pattern is an error rather than a literal word, and an unquoted expansion is not
word-split. Only the first of those is a fail-open here, and the fix `Q163`
carries -- refuse to expand when the shell is not bash, narrowed by `Q194` under
zsh to the patterns the two shells expand differently -- covers the glob and
nothing else.

Everything else this hook resolves is still read as bash, on a shell that is
often not bash. Two members have since been driven -- one below, one in the list
itself -- and the rest is open rather than long:

- **Glob qualifiers, answered: refused under zsh since `Q194`.** The paragraph
  below held of `(.)`, which only narrows the match, and not of the class:
  driven 2026-09-26 on zsh 5.9, `*(D)` adds dotfiles, `*.txt(P:.env:)` prepends
  `.env` to every match and `*(e:reply=(.env):)` replaces them, so a qualifier
  can under-scan. `Q194` reads a `(` glued to a word off the raw text and defers
  a glob operand beside one. As measured before that: `cat *(.)`
  selects regular files in zsh with `BARE_GLOB_QUAL` on by default, where bash
  syntax-errors and reads nothing. [`internal/bash`](../../internal/bash/) cuts
  the word at `(` before any expansion sees it, so the operand is `*` and the
  call resolves. Driven by the independent review of `Q163` and reproduced here
  on a flat fixture holding a key in `secret.env`: `cat *(.)` denies naming that
  file, `cat secret.env(.)` denies too -- which one uncut word could not, since
  no such file exists -- and `cat zzz*(.)` and `cat (secret.env)` are silent
  allows. In a tree it defers instead, because `*` reaches a directory. So this
  member costs precision rather than coverage, and what remains for the
  measurement pass is whether the cut is right for the other qualifier spellings
  rather than what it does with this one.
- **`=cmd`, which is a measured fail-open rather than a candidate.** zsh's
  `EQUALS` expands `cat =ls` to `/bin/ls` where bash leaves it a literal, and
  `cat =ls` through the shipped binary exits 0 silent with no coverage file
  written at all -- driven twice, by the independent review of `Q163` and again
  here, against a control denying on `cat secret.env` in the same fixture. It
  carries no glob metacharacter, so `Q163`'s operand-level glob deferral does
  not reach it and shipping that fix leaves this open. The reachable set is
  `PATH` executables, which is a poor spill vector and is why it is a row rather
  than an emergency.
- **zsh glob syntax the segmenter splits as bash operators, a measured
  fail-open.** `cat (k1|zz).env` is alternation to zsh and a pipeline to
  `Segments`; `cat k<1-1>.env` is a numeric range to zsh and a redirect; `cat
  a.txt(P:k1.env:)` is a qualifier on a word with no glob metacharacter, so
  `Q194`'s check -- which fires only beside a glob operand -- never sees it.
  Driven 2026-09-26 over a directory holding a key in `k1.env`: zsh 5.9 prints
  the key for all three, against a `cat k1.env` control that denies, and both
  the `Q194` build and `v0.4.1` write no verdict and nothing to stderr. The
  review of #181 adds `cat a.txt(e:'reply=(.secret)':)`, a silent allow on
  `main` as well. The fix is the segmentation question below rather than a
  glob check.
- **Named directories.** `~foo` is a shell parameter in zsh and a user home in
  bash, and `resolve` reads the bash spelling.
- **The reserved words and the operator set.** `[[ ]]`, `((  ))`, `foreach`,
  and `;;` in a `case` arm -- the segmentation port is structurally bash's, and
  whether the shapes it splits on split the same way under zsh is unread.

## One member is already driven, and it is an over-block

Taken 2026-09-19 by the session working `Q175`, over `env -i <shell> -c '<word>
cat f'` on bash 5.3.15 and zsh 5.9, and repeated here for the abort reach.
"reads f" means the file's line printed.

| word | bash 5.3.15 | zsh 5.9 |
|---|---|---|
| `LC_ALL=C cat f` (control) | reads f | reads f |
| `LC_ALL+=C cat f` | reads f | reads f |
| `FOO[1]=x cat f` | reads f, warns `not a valid identifier` | reads f, silently |
| `FOO[2]=x cat f` | reads f | reads f |
| `FOO[0]=x cat f` | reads f | error, reads nothing |
| `FOO[0]+=x cat f` | reads f | error, reads nothing |
| `FOO[]=x cat f` | reads f | error, reads nothing |
| `FOO[a[0]]=x cat f` | reads f | error, reads nothing |
| `FOO[a]b]=x cat f` | `command not found`, reads nothing | `no matches found`, reads nothing |

Every index but 0 peels and reads in both, so the fix `Q175` carries is required
under zsh as well. Index 0 diverges because zsh arrays are 1-based and the
assignment is fatal there: the peel then models a read zsh never performs, which
is a false positive rather than a fail-open.

**What bash warns about, zsh refuses -- and how far the refusal reaches is one
command, not the string.** Driven here on the same shapes, because the class
matters more than the subscript does:

| string | bash 5.3.15 | zsh 5.9 |
|---|---|---|
| `FOO[0]=x cat f; cat g` | reads f, then g | reads g only |
| `FOO[0]=x cat f && cat g` | reads f, then g | reads nothing |
| `FOO[0]=x cat f \|\| cat g` | reads f | reads g |
| `cat g; FOO[0]=x cat f; cat g` | g, f, g | g, g |

So zsh drops the command the error is attached to and carries the non-zero
status through an and-or list, and a `;` after it still runs. A scanner reading
the whole string therefore reads a **superset** of what zsh opens, which is the
direction that costs precision rather than coverage. Every member of this class
found so far points the same way, and that is a finding about four shapes, not a
law: the first member that points the other way is what this row is for.

**The head peel is not one of these, and that was worth driving rather than
assuming.** A substituted word carrying an assignment prefix reads nothing under
either shell -- bash settles what an assignment prefix is before it expands, and
zsh does not split the value into words at all -- so both refuse
`V="LC_ALL=C cat"; $V f`, and both refuse `V=LC_ALL=C; $V cat f`. The order the
peel is decided in is the same question in both, which is what `Q167` is about.

What diverges sits one step earlier and is not the peel: `V="cat f"; $V` reads
f in bash and nothing in zsh, because the value becomes two words in one shell
and one in the other. Precision again. And `${=V}` is zsh's spelling for
splitting on demand -- `bad substitution` in bash -- which is a token shape
nothing here has seen.

**A scalar is subscripted by character in zsh.** `FOO=old; FOO[1]=x` gives
`xld` there and leaves `$FOO` at `old` in bash. `applyAssignmentGroup` drops the
name on any subscript, so it is already right in both shells -- for bash's
reason, with a doc comment that says so in bash's terms.

**What this owes is a measurement and a decision, not a port.** A zsh
segmentation layer is the shape to refuse on the same grounds the repo refuses a
hand-rolled one: two dialects maintained by inspection drift silently in both
directions. The likely answer is a wider version of `Q163`'s -- defer more, on a
shell this cannot model -- and the measurement is what says how much more, and
whether anything beyond the glob is a fail-open rather than a record.

Take it as a differential: the same command strings through this package and
through a real `zsh -c`, comparing the file set each would open. That needs an
interpreter at measurement time and not at test time, which is the constraint
the segmentation port already lives under.

**Do not size this from how often a session writes zsh-specific syntax.** The
population on hand is this machine, whose tool shell has been bash since
2026-08-24, so a model that learned what works here learned bash. The question
is what a *zsh* machine's sessions would write, and nothing here can see one.
