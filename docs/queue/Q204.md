# A failed operand skips the scan of the text that carries it

A prompt carrying an AWS access key blocks. The same prompt with an `@` token
the hook cannot resolve beside the key exits 0 with no verdict, and the key
crosses. The `Bash` command string does the same: `echo <key>` blocks, and
`echo <key>; cat $X` defers.

Driven 2026-10-01 through `hook.Run` in-process, with the fixture key the unit
tests use, four payloads:

| Payload | Exit | Verdict on stdout |
|---|---|---|
| prompt: key, then `@notes.txt`, no `cwd` | 0 | none |
| prompt: key alone | 0 | block |
| Bash: `echo <key>; cat $X` | 0 | none |
| Bash: `echo <key>` | 0 | block |

The mechanism is in the order of the walk. `promptTargets` and `bashTargets`
return the error from the first operand that fails, and `scanCall` gets no
buffers back at all, so the text they were carrying never reaches the match
loop. The comments at both sites say so: the walk "fails before the prompt
itself has been scanned". They give it as the reason a refusal cannot quote the
token, and nothing treats it as a coverage gap of its own.

The prompt arm is the one that matters. A `Bash` command string is model
output and has crossed once already. A prompt is what the person typed, and
`UserPromptSubmit` is the only place it can be stopped. The `@notes.txt` with
no `cwd` above is a synthetic trigger, because real payloads carry `cwd`.
Which organic `@` tokens fail to resolve is unmeasured: a fifo, a file this
process cannot read, and a home-relative token with no home are the arms
`prompt.go` refuses.

`TestACoverageRecordCarriesNoScannedValue` asserts the Bash arm defers on `cat
$HOME/<key>`, so the suite currently pins this behaviour.

The likely fix is to scan the text buffer before walking its operands, or
whatever the walk fails on, and to let a finding in it block. Coverage still
defers on the operand. Found while working Q200, whose record change does not
touch this.
