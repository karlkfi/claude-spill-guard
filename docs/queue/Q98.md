# `scripts/README.md` hand-keeps a count of its own files

Its **Modes** section opens by saying thirteen Python files there are this
repo's own and twelve of them are entry points. Measured on 2026-08-31 at
`793abbe`, before Q12 added another: `git ls-tree HEAD scripts/` names fifteen
`.py` files, fourteen at mode `755` and one library at `644`. The sentence was
two behind, and had been for however long — nothing re-reads it, so there is
no event that would have said.

The numbers are load-bearing in that paragraph rather than decorative: the
whole point of it is that the count of entry points and the count of `755`
files agree, and a reader checking that arithmetic against a stale pair
concludes something false about which files are meant to be executable.

Same class as [Q72](Q72.md) and not the same fix. There the number is one a
gate already prints, so the repair is to read it from the gate. Here nothing
prints it: it is a property of the directory, so the repair is either `make
status`'s shape — a generated block between markers, asserted by a `--check`
mode — or dropping the numbers and describing the split without counting it.
The second is cheaper and loses the arithmetic the paragraph is making.

One thing to settle first, because it reads the other way. The same section
says **No gate asserts any of this, on purpose**, and argues it: a mode that
drifts here breaks nothing, because no file is invoked by path. That argument
is about the modes. It is not about the count, and its presence is most of why
the count reads as deliberately ungated too.

## Both obvious ways to derive the number are wrong, in opposite directions

Measured 2026-09-01 while two branches were each adding a script, on a tree
whose true figure was nineteen own files and eighteen entry points:

| form | reports |
|---|---|
| `git ls-files 'scripts/*.py'` | 20 |
| the same, filtered `grep -v vendor` | 18 |
| the same, filtered `grep -v '^scripts/vendor/'` | 19 |

The unfiltered glob over-counts because a git pathspec's `*` does not stop at
`/`, so `scripts/*.py` reaches `scripts/vendor/claude-skills/queue.py` — the
one file the paragraph explicitly excludes. The substring filter then
under-counts, because `scripts/check-vendor.py` contains the word it is
matching on. Only the anchored form is right.

**The direction matters more than either error.** A reader who notices the
vendored file and reaches for the obvious repair lands on a *different* wrong
number and has more confidence in it than before, because they have just
fixed something. That is worse than the unfiltered count, which at least
nobody has audited.

This is an argument for the generated-block repair over the drop-the-numbers
one. Dropping them removes the arithmetic the paragraph is making; generating
them removes the step where somebody has to pick a filter, which is where both
errors above live. [Q116](Q116.md) covers the same counts from the merge side
and cites this row for the derivation.
