# The fence reader does not match a fence to its opener

`scripts/check-doc-links.py` tracks fenced code with a boolean it flips on any
line starting ` ``` ` or `~~~`, so the fence that closes a block need not be the
one that opened it. Three shapes leak, each of them a doc explaining markdown —
which is what this repo's gate docs are. Measured 2026-08-23 at 23bb6e1, all
three reporting the link inside as prose:

- a longer fence holding a shorter one, which is how a doc shows a fenced block
  as an example;
- a `~~~` block holding a ` ``` ` block;
- a ` ``` ` block holding a `~~~` block.

The first flip is right and the second is the defect: the inner fence closes
the outer block, the example's own content is read as prose, and a link in it
is reported. Same direction as Q32 — a false red, on a doc whose subject is the
gate itself.

A fourth is quieter and runs the other way. `FENCE` allows any indentation, so
a ` ``` ` four spaces in opens a fence rather than sitting inside the indented
code block it belongs to, and the checker then skips to the next fence line and
reads nothing between. That one stops reporting, which is the direction this
repo fails closed against everywhere else.

The fix is one pass: record the opening marker's character and length, and
close only on a line of the same character at least as long with nothing after
it, at an indent of three spaces or less. Q32 rebuilt the walk around blocks
and left the fence test alone; this is the piece it did not touch.

Both halves need a mutation control in `docs-mutation-control`, in the two
directions that job already runs: a link inside a nested fence must not fail
the gate, and a link after an indented ` ``` ` must still fail it.
