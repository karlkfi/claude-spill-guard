# An append assignment is read as a command name, so the file goes unread

`assignmentRE` is `^[A-Za-z_][A-Za-z0-9_]*=`, which does not match `FOO+=x`.
Bash makes that assignment, and exports it as a command prefix like any other,
so the prefix is peeled by the shell and not by this. `internal/readers` has no
row for `LC_ALL+=C`, so the segment contributes no operands and the file behind
the prefix is never opened.

## Measured

Driven 2026-09-09 on bash 5.3.15 and on a binary built from the Q92 head
`c6a1c48`, with `testdata/corpus/planted/aws-access-key-id.env` at `k.env`.

Bash, `bash -c "<word>; printf '[%s]' \"${FOO-UNSET}\""`:

```
FOO=x        [x]        assigns
FOO+=x       [x]        assigns
FOO+=x y     [UNSET]    a prefix, so it does not persist -- the control
```

And as a prefix, `FOO+=bar env` prints `FOO=bar`, so the child really does
inherit it.

The hook, on the same tree:

| command | bash reads | verdict |
|---|---|---|
| `cat k.env` -- control | `k.env` | deny, naming `aws-access-key-id` |
| `LC_ALL=C cat k.env` -- control | `k.env` | deny |
| `LC_ALL+=C cat k.env` | `k.env` | **no verdict object, exit 0** |

Two controls rather than one: the plain prefix is what says the peel works at
all, so the silence on the third row is the `+=` and not a broken probe.

## Where it came from, which is the part worth keeping

Found in review of the Q92 port, and it is a **miss in how that port was
taken** rather than a defect that port introduced. `assignmentRE` is untouched
by it and `main` fails the same way.

Upstream fixed this in `claude-bouncer` #113, merged 2026-09-08 as `05f69c0`.
That commit is an **ancestor of `6cc585b`**, the #110 merge Q92 ported --
`gh api .../compare/05f69c0...6cc585b` reports `behind_by: 0`. So the fix was
already sitting in the tree the port was read from, and porting a single PR's
diff rather than differencing against its base is what walked past it.

## Which way it gets built

Upstream's shape, and both halves are load-bearing. The regex becomes
`^[A-Za-z_][A-Za-z0-9_]*\+?=`, and the `=`-splitting sites need a splitter
rather than a `Cut` on `"="`:

- `internal/hook/override.go:50:name, value, _ := strings.Cut(assignment, "=")`
- `internal/hook/vars.go:549:name, raw, _ := strings.Cut(t, "=")`
- `internal/hook/vars.go:621:name, _, _ := strings.Cut(t, "=")`
- `internal/hook/bash.go:511:if strings.HasPrefix(assignment, name+"=")`

Widen the regex alone and `poisonVars` deletes the name `SP+` rather than `SP`,
and `assigns(…, "CDPATH")` misses `CDPATH+=`. That is a fail-open traded for a
fail-open.

It composes with the quote provenance at the regex: `m[1]` falls after the
`+=`, so quoting past it still assigns, which is what upstream measured when
the two changes met.

**The fix above is upstream's and is not measured here.** Whoever takes this
row should invert it after applying rather than before -- a widened regex passes
its new rows the moment it exists.
