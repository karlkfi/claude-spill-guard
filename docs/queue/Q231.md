# `<>` lexes as `<` then `>`, and its target becomes a command word

`<>f` opens `f` for reading and writing on stdin. `Segments` has no such
operator. It splits the run into `<` and `>`, records `>` as the input
target, and leaves `f` in the tokens. A probe on 2026-11-01 printed `toks=["cat"
"k.env"] redir=[">"] in=[">"]` for `cat <>k.env`, and `toks=["k.env"]` for a
bare `<>k.env`.

Driven the same day under `env -i PATH=/usr/bin:/bin`, with the planted AWS
key in `k.env`. bash is 5.3.15, zsh is 5.9 under `-f`, and the hook is a
built binary of the Q219 branch over `826fed2`.

| command | bash | zsh | hook, both shells |
|---|---|---|---|
| `cat <>k.env` | prints | prints | deny |
| `<>k.env` | nothing | prints | allow, silent |
| `echo $(<>k.env)` | nothing | prints | allow, silent |

The deny is an accident: `k.env` lands among `cat`'s operands. Under zsh the
bare form runs `$READNULLCMD` on the file, and the hook reads it as a
command called `k.env` with no reader row.

Upstream appears to share the lexing. In claude-bouncer at `00c94bc`, the
only `'<>'` literal in `plugins/workspace-guard/lib/bouncer_parse.py` is the
process-substitution check at line 1314. Nobody has driven upstream's lexer on
`<>f`. The fix is a lexer change, so it should land upstream and be ported
here, as the rule against hand-rolling shell parsing asks.

Found by the reviewer of the Q219 change.
