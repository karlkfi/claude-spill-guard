# The `<>` operator is this port's, and upstream still splits it

`<>f` opens `f` for reading and writing on stdin.
This row first reported that `Segments` split it into `<` and `>`, so the target became a command word and a bare `<>k.env` crossed silently under zsh.
The Q258 change closed that here by making `<>` a lexer operator, an input on fd 0 and a write to fd 1 where it is written `1<>`.

What is left is the other half of what the row asked for: the fix was to land upstream and be ported, and it landed here as a divergence instead.
`internal/bash/lex.go` says so beside the operator table.
Read by the reviewer of #301 in a clone of claude-bouncer at `7b4c472`: `REDIR` in `plugins/workspace-guard/lib/bouncer_parse.py` has no `<>`, its backlog mentions none, and no pull request there does.
Whether workspace-guard misjudges a `<>` path because of it is not measured.

## What is closed here

Driven on a binary built from `d0b776d`, with a planted key as the target, and checked by that reviewer against bash 5.3.15 and zsh 5.9 over fourteen spellings.
Every command a shell prints the file for is denied under that shell: `cat <>k.env`, `cat <> k.env`, `cat 0<>k.env`, `<>k.env cat`, and under zsh the bare `<>k.env`, `0<>k.env` and `echo $(<>k.env)`.
`cat 3<>k.env` prints in neither shell and gets no verdict.

Under bash the three quotings of `$(<>k.env)` are denied though bash prints nothing for them.
That is a false deny on a spelling nobody has been seen to write, and it is recorded here rather than given a row.

## What to do

Report the lexer gap to claude-bouncer with the three commands this row was filed on, so the next port of its segmentation layer does not silently drop the operator.
That report is a row in another repository, so it is started from a turn Karl begins.
