# gates.py reads the workflow's job list with a regex

[Q20](Q20.md) states the repo's position for this exact file: do the checking
over a real YAML parser rather than a regex, because `uses:` can appear inside
a comment or a `run:` block and neither is a mapping key. `scripts/gates.py`
reads job names out of `.github/workflows/tests.yml` with
`^  ([A-Za-z0-9_-]+):$` and a comment-stripping pass, which is the same class
of read against the same file.

Not a defect today. Every job name in the file is at that indent and nothing
else is: the job set the script derives matches the file exactly, which is what
`gate-drift` passing asserts. It is filed because the failure modes are
asymmetric and one of them is silent.

- A line at two-space indent ending in a colon inside a block scalar reads as a
  job. That direction is loud: a phantom job in no gate's name fails
  `gate-drift`, which is the right answer for the wrong reason.
- A job name the pattern does not match — quoted, or indented differently by
  someone reformatting the file — is simply not seen. `gate-drift` then reports
  agreement over a job list missing an entry, and a gate can drop out of CI
  while the check that exists to prevent exactly that stays green.

The second is the one worth closing.

## The obstacle is that there is no parser to reach for

The runners install Python with nothing on top, so `yaml` is not importable and
adding a pip install to every job is a real cost for this. Q20 has the same
problem for `uses:` pins and has to solve it first; whatever it lands —
a vendored pure-Python parser, a pinned tool from `tools/`, or a narrow
hand-written reader with its own tests — this should use the same thing.

**One fix closes both, so fold this into Q20 rather than working it alone.** It
is separate only because Q20 was filed before `gates.py` existed.

Until then the guard is that the parse refuses to read zero jobs: an empty
result exits with a message rather than passing over nothing, the same shape as
the `empty-store` lint class.
