# Without Git Bash, Windows runs the hook under PowerShell, and it fails

On a Windows machine with no Git for Windows, Claude Code runs every hook
command under PowerShell, not bash. spill-guard's command,
`"\"${CLAUDE_PLUGIN_ROOT}/hooks/run-spill-guard.cmd\" hook"`, is very likely a
PowerShell parse error, and a parse error exits non-zero but not 2. Only 2
blocks. If that holds, the launcher never starts, its deny-when-missing arm
never runs, and **no event is scanned on that machine**: not `Read`, not `Bash`
(which does not exist there), not `UserPromptSubmit`. On top of that, shell
commands there go through a tool named `PowerShell`, which `hooks.json` does
not match. The project ships a Windows install channel, so the plugin can be
installed there and do nothing.

## What is read from code, and what is not

Read out of the 2.1.290 CLI (`~/.local/share/claude/versions/2.1.290`) on
macOS, 2026-11-01. The first reading is by the session that filed this row,
and the hook-executor part is by the independent review of the PR that filed
it, re-read by the filing session. Nothing was run on Windows.

**Read from the binary:**

- The hook executor picks its shell as `Ct=e.shell??UW()`, and
  `function UW(){return rl()?"bash":"powershell"}`.
  `function rl(){if(O()!=="windows")return!0;return v5()!==null}` is false on
  Windows when Git Bash is not found. When the shell is `powershell` and the
  hook gives no `args`, it rewrites the command (`if(!Nt&&St){if(Zt=Zcr(Zt),…`)
  and spawns it with `-Command`. A hook can set `"shell"` explicitly, or use an
  exec form with `"args"`, which spawns with no shell. Ours sets neither.
- Shell commands on that machine go to a tool named `PowerShell`: `var
  Fe="Bash";var kt="PowerShell";`, with `qt({name:kt,…,searchHint:"execute
  Windows PowerShell commands",…})` running `ype(D,h.signal,"powershell",{…})`.
  Whether it is on is decided by `function ib()`. Off Windows it is on only
  when `CLAUDE_CODE_USE_POWERSHELL_TOOL` is true. On Windows the variable
  decides when set; unset, the tool is on if Git Bash is missing, and
  otherwise it follows the server flag `tengu_cobalt_ridge`, default `false`.
  The review found no alias that would widen a `Bash` matcher onto it.

**Not driven, and from knowledge of PowerShell rather than measurement:** that
`"<path>" hook` fails to parse (a quoted path needs the `&` call operator),
and the exit status it fails with.

## What a Windows drive has to establish

From the independent review, plus this row's own payload question:

- that the Windows build bundles the same JavaScript as the macOS one;
- that a hook process inherits the `SHELL` that startup sets, and in which form
  (`C:\…` or `/c/…`), which decides `filepath.IsAbs` and `shellNames` in
  `internal/hook/shell.go` (Q192);
- the real `PowerShell` tool payload's field names;
- the parse error, and its exit status, for our command under PowerShell;
- whether `tengu_cobalt_ridge` is on for any account.

A `windows-latest` runner has Git for Windows installed, so the drive has to
take Git Bash out of reach first, or set `"shell":"powershell"` on the hook to
reach the same branch.

## What to build

1. **Make the hook command run under both shells, or under neither.** The
   candidates are an exec form (`{"command": …, "args": ["hook"]}`, which needs
   no shell, though whether it can launch a `.cmd` on Windows is unmeasured), a
   PowerShell-safe spelling such as a leading `&`, or a second hook entry with
   `"shell":"powershell"`. Pick by driving all three, not by reading. Whatever
   is chosen must keep the launcher's deny-when-missing arm reachable, because
   that arm is what makes a broken install visible.
2. **Then add `PowerShell` to the matcher.** Scan its `command` string the way
   `scanCall` scans a `Bash` command. Its file operands (`Get-Content`, `gc`,
   `cat`, `type`, `Select-String`, `-Path`, `-LiteralPath`) need a reader
   table `internal/readers` does not have, and the bash port cannot segment
   PowerShell. Until a table exists, a `PowerShell` call naming a path is a
   coverage failure that gets recorded, not a silent allow.
   `internal/hook/manifest_test.go` asserts set equality between the matcher
   and the Go constants, so the tool goes in both.

**Done** is a `windows-latest` drive with Git Bash out of reach, through the
launcher, in which a `Read` of a planted key denies and a `PowerShell` payload
carrying one denies too. The `Read` arm is what catches the first step: a
machine with Git Bash would pass the second arm and still miss everything
above. Capture a real `PowerShell` payload first, as Q207 does for `Grep`.

Found by the Q192 scoping pass, which asked whether a `Bash` call can reach the
PowerShell provider. It cannot. A different tool does, and the hook runner uses
the same shell choice.
