# The `PowerShell` tool is not matched, so nothing scans it on Windows

On Windows, Claude Code runs shell commands through two tools: `Bash` on Git
Bash, and a separate tool named `PowerShell`. `hooks/hooks.json` matches
`Read|Bash|Grep`, so a `PowerShell` call fires no spill-guard hook. Its command
string goes unscanned, and so does any file it reads. On a Windows machine with
no Git for Windows, `PowerShell` is the only shell tool there is, so every
shell command crosses with no verdict and no record.

## The source, and what it is

Read out of the 2.1.290 CLI (`~/.local/share/claude/versions/2.1.290`) on
2026-11-01. This is a reading of shipped code. Nothing was run on Windows.

- The tool names are declared side by side: `var Fe="Bash";var
  kt="PowerShell";`. The `PowerShell` tool is `qt({name:kt,…,searchHint:
  "execute Windows PowerShell commands",…})` and is exported as
  `PowerShellTool`.
- `PowerShell` runs its command on the `powershell` provider:
  `ype(D,h.signal,"powershell",{…})`.
- Whether it is on is decided by `function ib()`. Off Windows it is on only
  when `CLAUDE_CODE_USE_POWERSHELL_TOOL` is true. On Windows the variable
  decides when it is set. When it is unset, the tool is on if Git Bash cannot
  be found, and otherwise it follows the server flag `tengu_cobalt_ridge`,
  default `false`.
- `Bash` is offered only when `function rl()` holds, which is always off
  Windows and only with Git Bash on it. Without Git Bash the startup log
  reads `Git Bash not found; BashTool will be unavailable`.

So the reach on Windows is every machine without Git for Windows, every
machine that sets the variable, and every machine the server flag turns on.
That flag is a third input nothing here can read.

## What to build

This is the class CLAUDE.md calls *the rest of the class*, so membership is
argued from what the call returns. That is Q207's shape, for a tool name the
manifest omits.

- Add `PowerShell` to the matcher. Scan its `command` string the way
  `scanCall` scans a `Bash` command, which needs no knowledge of PowerShell to
  catch a credential typed inline.
- Its file operands (`Get-Content`, `gc`, `cat`, `type`, `Select-String`,
  `-Path` and `-LiteralPath`) need a reader table that `internal/readers` does
  not have, and PowerShell is not a POSIX shell, so the bash port cannot
  segment it. Until a table exists, a `PowerShell` call that names a path is a
  coverage failure and gets recorded, rather than being allowed silently.
- `internal/hook/manifest_test.go` asserts set equality between the matcher
  and the Go constants. The new tool goes in both, or that test fails.

**Done** is a drive on a `windows-latest` runner, where a `PowerShell` tool
payload carrying a planted key denies, through the launcher. The payload
fields here are read from the binary and not from a captured call, so capture
one first, as Q207 does for `Grep`.

Found by the Q192 scoping pass, which asked whether a `Bash` call can reach
the PowerShell provider. It cannot. A different tool does.
