# `$(<file)` reads the file and nothing scans it

A command substitution whose whole body is an input redirect, such as
`$(<k.env)`, is bash's short form of `$(cat k.env)`. The file goes into the
command string's output. The hook returns no verdict on it and writes no
coverage record. Driven 2026-11-01 on the v0.6.0 binary with
`SHELL=/opt/homebrew/bin/bash`, over a scratch directory holding the planted
key from `testdata/corpus/planted/aws-access-key-id.env` as `k.env`. "prints"
means `env -i bash --norc -c` (5.3.15) wrote the key to stdout.

| command | bash | hook |
|---|---|---|
| `echo $(cat k.env)` (control) | prints | deny |
| `cat < k.env` (control) | prints | deny |
| `echo $(<k.env)` | prints | exit 0, silent |
| ``echo `<k.env` `` | prints | exit 0, silent |
| `x=$(< k.env); echo "$x"` | prints | exit 0, silent |
| `printf %s "$(<k.env)"` | prints | exit 0, silent |
| `<k.env` | nothing | exit 0, silent |

The last row is right for bash. In zsh, a redirect with no command at all runs
`$READNULLCMD` on the file. With `zsh -f`, `<k.env` and `< k.env | cat` both
print the key, and both pass the hook just as silently. So under zsh the
fail-open is not limited to a substitution. The same defect drives both, so it
goes in one row.

**The likely mechanism, from the docs rather than a read of the code.**
CLAUDE.md says `Segment.Inputs` puts a `<` target back among the operands of
a *known reader*. A segment with no command word has no reader, so its input
redirect reaches nothing. The fix is that a segment with no command word and
an input redirect reads the target. That holds inside a command substitution
under every shell, and anywhere under zsh. Confirm this against
`internal/hook/bash.go` before you write it.

**Traffic.** 15 of 235,379 model-issued `Bash` calls in this machine's
transcripts contain `$(<` followed by a file, counted 2026-11-01. The shape is
rare, and nothing records it, so the coverage log has never shown it.
