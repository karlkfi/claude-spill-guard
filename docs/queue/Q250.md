# An override prompt omits a finding beside a refusal

`hook.go` runs the scan under an override so that the prompt has something in it to confirm.
A refusal defeats that: `scanCall` discards the buffers whenever the walk returns one, so a
person approving a prompt about the refusal also sends a key the prompt never mentioned.

## Driven 2026-11-04

A built binary at `577f445`, by payload, where `key.txt` holds a key. The reviewer of #238
found it and Claude reproduced the rows:

| Command | Verdict | Prompt names the rule |
|---|---|---|
| `SPILL_GUARD_OVERRIDE=why cat key.txt` | ask | yes |
| `SPILL_GUARD_OVERRIDE=why cat key.txt .env` | ask | no |
| `SPILL_GUARD_OVERRIDE=why cat key.txt; env` | ask | no |
| `SPILL_GUARD_OVERRIDE=why cat key.txt; grep -r x sub` | ask | no |

Without the override, `cat key.txt .env` denies on the refusal and names no rule. That costs
nothing there, since the call is stopped and a retry without `.env` meets the finding.

## What is owed

A prompt that can be approved has to name what approving sends. One candidate is scanning
what the walk collected when the call is overridden, and it has not been built. The walk
returns at the refusal, so a key in a file after it needs the same answer, which is
unmeasured. The test is the table above, red on the three rows that omit the rule.
