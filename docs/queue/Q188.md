# A substituted value is not word-split, so a command it carries is unread

`V="cat key.env"; $V` reads the file and gets no verdict and no coverage
record — the silence of a call that sent nothing.

Driven 2026-09-19 against binaries built from `main` and from the Q167 branch,
identical on both, so it is live rather than a regression. bash 5.3.15 reads
the file: `env -i bash --norc --noprofile -c 'V="cat f"; $V'` prints f's
contents, because bash word-splits an unquoted expansion and the first word
becomes the command name.

| command | spill-guard | bash |
|---|---|---|
| `cat key.env` — control | deny, naming the rule | reads it |
| `d=. ; cat $d/key.env` — control | deny | reads it |
| `V="cat key.env"; $V` | **exit 0, no verdict, silent** | reads it |

The two controls are what make the silence legible: the resolver does track
`V`, and it does resolve a `$d` inside an operand. What it does not do is turn
one token holding `cat key.env` into two.

## Where it sits

`expand` in [`internal/hook/vars.go`](../../internal/hook/vars.go) maps token
to token — `out := make([]string, len(tokens))` — so a substituted value is one
token however many words bash would split it into. `readers.Files` then asks
for a reader row under the whole string `cat key.env`, finds none, and the
segment contributes no operands.

That length invariance is load-bearing elsewhere: Q167 decides the head peel on
the segment's own tokens and applies the count to the substituted copy by
index, which is only well-founded because the two lists are the same length.
So this cannot be fixed by making `expand` return more tokens than it was
given. The split has to happen after the peel, or in a second pass the peel
does not read.

## What to establish before fixing

**How much of bash's splitting to model.** The default IFS splits on space, tab
and newline; the result is then subject to pathname expansion, which is how
`V="cat *.env"; $V` differs again. `literalAssignmentValue` already refuses a
value carrying any of `impureValueChars`, which includes whitespace — so a
value with a space in it is *not* on the map at all today, and `$V` stays
unresolved. That is why the shape above allows rather than mis-resolving, and
it means the fix is not "split what is on the map" but "admit values this
currently refuses, and split them".

Admitting them is the part to measure. The refusal exists because an unquoted
`$V` holding `a b` reaches the command as two operands, and resolving it to one
path would name a file the command never opens — the fail-open this row is the
other half of. So the two directions have to move together: a value with
whitespace becomes usable only where every word it splits into is itself
scanned.

**Whether the traffic justifies it.** Nothing here has counted how often a real
`Bash` call builds a command from a variable. `CMD="..."; $CMD` is an ordinary
shape in scripts and may be rare in tool calls, which is the same question the
`env`-dump rule and the guarded-path class were each settled by. Take the sweep
over `~/.claude/projects/**/*.jsonl` before sizing the work.

**The shell is bash here and that is an assumption.** zsh does not word-split
an unquoted expansion at all, so `V="cat f"; $V` reads nothing there — driven
the same day on zsh 5.9. Q184 holds the dialect question; this row is written
against bash, which is what `internal/bash` models.
