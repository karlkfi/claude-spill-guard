# An awk or sed stage before the grep filter can write matches around it

`grep -rn foo . | awk '{print > "/dev/stderr"}' | spill-guard filter` exits 0
from the hook with no verdict, driven 2026-11-09 on a binary built from the
branch that closed Q233. awk writes every matched line to stderr, and the
`Bash` tool returns stderr to the model. sed's `w /dev/stderr` is the same
shape, and so is any interpreter stage (`perl`, `python3 -c`) whose program
opens a file.

`copiedAround` in `internal/hook/grep.go` reads where a stage's redirects, a
`tee` or `gtee`'s operands and a `dd`'s `of=` send a copy. It does not read a
stage's program, because deciding what an awk or sed script writes means
parsing it, and nothing here does that today. Nor does it know any other
command that takes an output path: `| cp /dev/stdin /dev/stderr |` gets no
verdict and puts the key on stderr, driven the same day. A per-command list of
writers has no end, which is the argument for the short list below.

The open question is the cost of the strict answer. Refusing any stage between
the grep and the filter that is not on a short list of commands with no
file-writing syntax (`head`, `tail`, `sort`, `uniq`, `cut`, `wc`, `tr`, `cat`)
would close the class, but `awk` and `sed` are common stages, and the rewrite
the reason offers appends the filter after whatever stages the call already had.
How often a refused recursive grep carries an awk or sed stage is unmeasured.

**Done** when the awk and sed shapes are refused with the plain reason, and a
count over the coverage log or the transcripts says what the chosen answer
costs.
