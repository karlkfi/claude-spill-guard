# A key beside a UTF-32 buffer crosses with no verdict

A call that names a file holding a key and a file behind a UTF-32 mark proceeds. The
key's finding is discarded and the only trace is a coverage record about the other
file. That breaks *A gap does not hide a finding beside it* in `CLAUDE.md`, which Q204
closed for an operand that will not resolve and not for this branch.

## Driven 2026-11-03

Built binary at `a99ed37`, payloads on stdin, `key.txt` a copy of
`testdata/corpus/planted/aws-access-key-id.env`, `notes.utf32` a UTF-32LE mark and text.

| Call | Result |
|---|---|
| `Bash` `cat key.txt` | denied, `aws-access-key-id` |
| `Bash` `cat key.txt notes.utf32` | exit 0, no stdout, one record naming `notes.utf32` |
| prompt `see @key.txt and @notes.utf32` | exit 0, no stdout, one record naming `notes.utf32` |

## Why

`internal/hook/hook.go:179:if len(blocking) > 0 {` returns through `abstain` ahead of
the findings check eight lines below it. The order was harmless when both
arms blocked. The change that made a coverage failure defer (9c93c4f, #117) turned the
first arm into `abstain`, so a blocking skip now hides the findings beside it. A
`SkippedUTF16Binary` buffer takes the same arm by reading `blocks()`; that one has not
been driven.

## What is owed

Test `findings` first, carrying `alsoUnread` for the skips as the `allowed` arm does,
with a test per surface that goes red when the order is put back. Check the sentence at
the end of `spill-guard coverage` afterwards: Q239 wrote it not to depend on this.
