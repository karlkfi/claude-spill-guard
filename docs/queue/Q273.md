# A GNU long option abbreviated to a unique prefix is not read

GNU's `getopt_long` accepts any unique prefix of a long option, so `--files0` is `--files0-from` and `--fil` is `--file`.
`splitArgs` in `internal/readers/readers.go` looks a long flag up in `fileFlags` and `consume` by exact name, so an abbreviated one reads as an unknown flag that takes no value.
Found by the reviewer of the Q263 pull request.

Driven 2026-11-27 under bash 5.3.15 against a binary built from `main` at `ba76d01`.
`key.txt` holds a planted key, `list0` names `key.txt` NUL-terminated, and `s.sed` and `p.awk` are one-line programs that print their input.

| Command | Hook | bash prints the key |
|---|---|---|
| `gsort --files0-from list0` | coverage record, no verdict | yes |
| `gsort --files0=list0` | no verdict, no record | yes |
| `sort --files0=list0` | no verdict, no record | yes, on macOS sort 2.3-Apple |
| `gsort --files0-f list0` | allowed with a binary notice, no record | yes |
| `gsort --files0-from=key.txt` | deny | yes, driven by the reviewer of #294 |
| `gsort --files0=key.txt` | no verdict, no record | yes |
| `gwc --files0=key.txt` | no verdict, no record | yes |
| `sed --file=s.sed key.txt` | deny | not driven |
| `sed --fil=s.sed key.txt` | no verdict, no record | not driven |
| `awk --file=p.awk key.txt` | deny | not driven |
| `awk --fil=p.awk key.txt` | no verdict, no record | not driven |

The `sed` and `awk` rows lose more than the flag: once `--fil` is unknown, nothing suppresses the program, so `key.txt` is taken for the script and read as nothing. macOS `sed` exits 1 on `--fil=`, macOS `awk` ignores `--fil=` and `--file=` alike and takes the next operand as program text, and `gsed` and `gawk` are not installed on this machine, so the bash column for those rows is not driven.
`grep` is not in the table because `internal/hook/grep.go` reads grep's long options by prefix already: `grep --fil=pats key.txt` denies.

The same exact-name lookup sits in `Indirect`, which is why `--files0` writes no record even where its list is read.
An abbreviated `consume` flag fails in the safe direction — its value is read as an operand — so it costs precision rather than a crossing.

`longOption` in `internal/readers/wrappers.go` already resolves a unique prefix for the wrapper rows.
Whether a row's tool takes prefixes is per tool: GNU tools and macOS `sort` do, macOS `sed` and `awk` do not, as above, and `jq` was not checked.

## Done

An abbreviation that GNU's `getopt_long` resolves to one of a row's `fileFlags`, `consume` or `indirect` flags is read as that flag, and every row of the table above denies or records as its unabbreviated spelling does.
An ambiguous prefix is not resolved.
The `sed` and `awk` rows are shared with the macOS tools, which do not take prefixes, so a resolved `--fil=` there can block a call that would have read nothing: `sed --fil=s.sed key.txt` exits 1 on macOS.
That over-scan is the accepted direction, as for `sed -i` in `spec.go`, unless a fix finds a way to tell the two tools apart that does not run either.
