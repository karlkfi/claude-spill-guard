# A commit message is immutable at squash, and nothing says so

[Q93](Q93.md) establishes that a squash here builds its message from the
branch's commits, so a pull request body never reaches `main`. The same field
settles the other direction and nothing in the repo draws it: **every commit
message on the branch lands in the trunk verbatim, correct or not.**

So branch commit prose is the opposite of a PR body. A body is a review surface
that stops existing; a commit message is published at merge and cannot be edited
afterwards. A wrong number in one is permanent.

## The instance

#170's branch carries an early commit reading `Of the 14 entry points ... which
is a 21% miss rate`, superseded twice on the same branch by commits that name
their revision. All three are in `c5c1158`'s message, in order, so a reader
going top to bottom meets the correction — the damage is bounded and the first
figure is still unqualified and false.

The author declined to reword it: an interactive rebase was blocked in that
environment, and resetting and replaying six commits to fix one word is more
risk than a superseded figure carries. That call was right.

**The trim was known, flagged twice, and still missed.** GitHub's squash dialog
lets the merging party edit the message, which is where this is fixed at
zero cost. Nothing carries the need for it to that moment: it lived in a chat
report and the merge happened elsewhere.

## What would actually hold it

A line in `CLAUDE.md` or `docs/queue/README.md` stating the rule — a false or
superseded figure in a commit message is permanent at merge, so either fix the
commit or trim the squash message — is rung 3, and rung 3 is what already
failed here. Worth deciding whether anything cheaper can fire at the right
moment.

The obvious mechanisms are weak. A gate over commit messages cannot tell a
superseded figure from a current one. `pr-sentinel` or a PR comment could carry
a reminder when a branch has more than one commit touching the same number, but
that is a heuristic over prose. This row's scope is the decision, not the
implementation, and "prose plus accept the miss rate" is a legitimate outcome.

## What this is not

Not an argument for squashing differently. `allow_merge_commit` is `false` and
`squash_merge_commit_message` is `COMMIT_MESSAGES`; both are deliberate, and Q93
depends on them too.
