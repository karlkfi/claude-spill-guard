# A grep path with a space in it is not crossed by private-key-block

`spill-guard filter` reads grep output, and `private-key-block` crosses
grep's per-line prefix (`path:N:`, `path-N-`) only where the path holds no
whitespace. So a key under a directory whose name contains a space reaches
the model through the filter.

Driven 2026-10-25 by the independent review of the change that added the
prefix arm, and reproduced on that branch's binary. Under `/usr/bin/grep -rn
-A30 'PRIVATE KEY' .` with the key at `./my keys/k.pem`, `filter` exits 0.
Under `-rnh`, which prints no path, it exits 3, and so does a raw read of the
file. `main` passes it under every prefix, so this is a recall gap the arm
left, not a regression.

**Do not fix it by letting whitespace into the prefix.** A prefix that may
contain spaces is a prose line, and prose between a header and a body is
what `testdata/corpus/clean/tls-runbook.md` and the `base64:` row in
`TestPrivateKeyBlockAcrossThePEMLayouts` hold the rule off.

The candidate worth pricing is narrower. Every line of one file's grep output
carries the same path, and the header line carries it too, so the filter
could take the path off the header line and strip that exact string from the
lines after it. That is a filter-side change, not a regex one, and it needs
a measurement of what it costs on the clean corpus as grep output
(`TestTheCorpusAsGrepOutput`) and on the module-cache differential
`rules/README.md` records for the arm.

**What is not measured:** whether paths with spaces carry any key traffic
here. Nothing in this repository or `~/go/pkg/mod` has been counted for it.
