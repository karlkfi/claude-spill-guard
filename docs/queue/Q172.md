# A citation the lint never reads looks exactly like one it read

`stale-citation` reports per row, so a row with one checked pointer and one
invisible pointer is reported as clean. Two shapes go unread, and both of them
are what `grep -n` emits:

**An extensionless path is not a citation at all.**
`scripts/vendor/claude-skills/queue.py:61:(?:go|py|sh|md|ya?ml|json|ts|js|rs|java)`
is the alternation the path has to end in, so a pointer at a `Makefile`, a
`Dockerfile`, a `go.mod` or a `.gitattributes` matches nothing — not the
fragment check, and not the resolves check either. The pointer can name a line
past the end of a file that does not exist and the lint says `item(s) OK`.

**A fragment opening with whitespace is dropped, and the row is still
reported OK.** The capture is `(?::(\S[^`\n]*)(?=`))?` — optional, and
requiring a non-space first character. Where it does not fire the citation
degrades silently to path-and-number, which is checked only for resolving. So
every indented source line is uncheckable as written: a Makefile recipe, a
Python function body, a YAML step. The regex's own comment gives the reason as
*which `grep -n` never emits either*, and that is the part that is wrong —
`grep -n` on a tab-indented recipe emits the tab.

There is a third gate on the same expression, already filed: [Q64](Q64.md)
covers the leading `\b`, which drops the dot from a dotfile path.

## Measured, and the number is small

Taken 2026-09-17 by running the shipped `CITATION_RE` over the 63 rows on
`origin/main` — the store without the change that found this. 30 pointers have
their fragment read. Four do not: two are deliberately bare, written as
`` `path.py:N` `` with no fragment at all, and two carry a fragment the leading-space
rule drops, one of them in a row an open pull request is completing. No row
there cites an extensionless path, so that class has no instance on the trunk
today; the one that found it was in this row's own sibling draft.

So this is not a store full of dead pointers. What it is, is a check whose
clean answer means less than it reads as meaning, in a store where the clean
answer is the only thing anyone looks at.

## How it surfaced

A row drafted on 2026-09-17 carried three pointers. The `CLAUDE.md` one was
checked — by luck, because the quoted sentence happened to be followed by a
backtick. The `Makefile` one was invisible, and was stale by one line at the
moment it was written, because an edit in the same session moved the recipe
down. The `check-release-notes.py` one was quoted from a fence with its
original indentation, so its fragment was dropped. `queue.py lint --strict
stale-citation --citation-window 0` returned `item(s) OK` over all three.

The author caught it by planting a wrong fragment into each pointer in turn and
watching which the lint named — a positive control, not a reading of the clean
run — and then rewrote that row's pointers into the checkable form, which is
why the draft described here is not what the store now holds.

## What would close it

Two candidates, and they are not the same size.

**Widen the expression** to accept a bare filename from a short list, and to
capture a fragment that opens with whitespace by stripping it before the
containment test — the test is already `fragment in text`, so a stripped
fragment still matches. Cheap, and it turns both silent classes into checked
ones.

**Or refuse what it cannot check.** A pointer shaped like `grep -n` output that
the expression does not match is currently indistinguishable from prose, so the
lint cannot warn about it without a second, looser pattern to notice the near
miss. That is the honest fix and it will have false positives on ordinary text
carrying a colon and a number — the probe that found this counted two
timestamps in [Q83](Q83.md) as candidates.

Either way the change is upstream in `claude-skills` rather than here: the file
is vendored, and `make vendor` pins its digest.
