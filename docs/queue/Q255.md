# A recursive grep with a detached `-f` and no operand is silent

A recursive `grep` with no file operand searches the working directory, and the
hook refuses it with the filtered form. Spell the pattern file as a separate `-f`
or as `--file=` and the refusal goes, where the glued form keeps it. Driven
2026-11-05 on `main` at `deff1dd` and on Q252's branch, with `key.txt` in the
directory holding a key beside the word `deploy`, under bash 5.3.15 and zsh 5.9:

| Command | Hook, both builds | The shell prints the key |
|---|---|---|
| `grep -r -f <(echo deploy)` | no verdict, no record | yes |
| `grep -r --file=<(echo deploy)` | no verdict, no record | yes |
| `grep -rf <(echo deploy)` | no verdict on `main`, refusal on the branch | yes |
| `grep -r -f plain.txt` | no verdict, no record | no: the pattern file matches nothing here |
| `grep -r --file=plain.txt` | no verdict, no record | no: same |
| `grep -rf plain.txt` | refusal | no: same |
| `grep -r -e deploy` | refusal | yes |
| `grep -r deploy` | refusal | yes |

So this is about the flag's spelling and not about a process substitution. Which
branch of `grepMode` or `grepFiles` loses it has not been read. Reach is unmeasured.

**Done** is `-r -f`, `-r --file=` and `-rf` all refused alike when no operand
follows, with `grep -r -f plain.txt d` and its neighbours still reading `d`.
