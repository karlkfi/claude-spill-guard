# The scanner refuses every read of the corpus README it ships

`testdata/corpus/README.md` holds three `aws-access-key-id` matches in its
prose, describing what the corpus contains. spill-guard has no path arm, so a
`Bash` read of that file is refused like any other — and a refused call runs
*nothing*, so a compound command that bundles that read with anything else
discards all of it.

The file is already on `self-scan`'s named allowlist with a stated reason, so
the scanner is behaving exactly as specified. The cost is a workaround every
session that wants to read it, and the workaround is not obvious the first time:
the refusal names the rule, not the fact that this particular file is
documentation about the rule.

**This is a judgement about the shipped product, not a measured defect.** Kept
in the framing the worker who hit it used. The design refuses a path exclusion
inside the scanner on the grounds that a file the model can point at is a
two-step bypass, and that argument is unaffected by this row.

What is open is whether anything cheaper than a per-session workaround exists —
a note in `testdata/corpus/README.md`'s own header saying to read it with the
Read tool rather than `cat`, a restructuring that moves the credential-shaped
prose into a fenced block the scanner still matches, or nothing at all. The last
is a legitimate answer: a security tool that will not let you `cat` its own
threat corpus is arguably working.
