# A reader pointed at a file by an input redirect is never scanned

`cat < deploy.env` reads the file and nothing here opens it. The same command
written `cat deploy.env` blocks. Driven 2026-09-04 over
`testdata/corpus/planted/aws-access-key-id.env`, payload carrying a `cwd`:

| the call | what the binary does |
|---|---|
| `cat testdata/corpus/planted/aws-access-key-id.env` | blocks, naming `aws-access-key-id` |
| `cat <testdata/corpus/planted/aws-access-key-id.env` | **exit 0, silent** |
| `head -n 20 <…`, `grep -c AKIA <…`, `wc -l <…` | **exit 0, silent** |
| `cat testdata/corpus/clean/tls-runbook.md` | exit 0, silent (negative control) |

**It defeats both answers this tool has, not only content matching.** The
path refusal Q126 added is bypassed the same way — driven 2026-09-04 on a
binary built from `c47d7bc`, with fixtures holding a password and an AWS
*secret* access key so that nothing a shipped rule matches could account for a
verdict, and an unguarded path in the same run as the negative control:

| the call | what the binary does |
|---|---|
| `cat .env` | blocks, the path refusal |
| `cat < .env`, `cat <.env` | **exit 0, silent** |
| `cat .aws/credentials` | blocks, the path refusal |
| `cat < .aws/credentials` | **exit 0, silent** |
| `cat notes.txt` | exit 0, silent (negative control) |

So a reader must not take this row for a content-only gap. Nothing about the
ruleset, the corpus or the guarded-path class closes it: the file is never a
buffer and its path is never an operand.

**It is not one reader's defect.** Four of them — `cat`, `head`, `grep`, `wc` —
allow the same file through the same way, which is what puts the fix at the
redirect operator rather than in any row of `internal/readers`.

**It is in the shipped v0.2.0 release.** Not by rebuilding the tag: `git diff
--stat v0.2.0..origin/main -- '*.go' rules/ go.mod go.sum` is empty, so the
whole shipped build graph is identical between `a81c87f` and the trunk and a
measurement on one is a measurement on the other by construction. The only
files that differ are `.claude/merge-posture.md`, `.gitignore`, `docs/plan/`,
three queue rows and `docs/queue/README.md`. That check is the cheap way to ask
whether any defect measured on `main` is shipped, and it cannot drift the way a
second build can.

**Give any probe for this a `cwd`, or it discriminates about the wrong thing.**
Without one, the operand arm blocks for an unresolvable relative path while the
redirect arm still allows — so the probe returns a clean deny/allow split that
looks like a working control and is answering neither question. A silent probe
would be easier to catch than this one.

## Why the surface has the information and does not use it

`bashTargets` builds its operand list from `readers.Files(tokens)`, which reads
a segment's *tokens*. `internal/bash` strips a redirect out of the tokens and
records it separately, in `Segment.Redirects`, and nothing in
[`internal/hook/bash.go`](../../internal/hook/bash.go) reads that field. So the
path is sitting in the parsed segment and the loop walks past it.

`shape.go`'s `lastInPipeline` already says why `Segment.Redirects` is awkward:
it records the target and not which descriptor was redirected, so `env
2>/dev/null` and `env > vars.txt` are the same entry. That argument is about
telling an *output* redirect from a filter, and it is the reason the shape rule
declines to read the field at all. It says nothing about an input redirect,
where the question is not which descriptor but whether the target is being
read — and a `<` is unambiguous about that if the parser records the operator.

**And it does not record the operator.** `Segment.Redirects` is a
`[]string` of targets — read 2026-09-04 at
[`internal/bash/bash.go`](../../internal/bash/bash.go), where the field's own
comment calls it "every redirect target written in this segment". So `< in.txt`
and `> out.txt` are the same entry, and the hook cannot tell them apart from
what it is given. The fix is upstream of `internal/hook`, in a package that is
a port kept structurally identical to its upstream so a fix there transfers by
inspection ([CLAUDE.md](../../CLAUDE.md), *Do not hand-roll shell parsing*).
Whether that means carrying the operator here or taking it from upstream is the
first decision this row makes.

## Size it before shipping it

Approximated over the same corpus the Q126 sweep used — 24,381 `Bash` calls in
238 transcript files, the seven days to 2026-09-04 — a regex for any of the
readers above in command position followed by an unquoted `<` matches 215
segments across 197 calls. The instrument is a regex over command strings and not the segmenter, so
that is a ceiling: `awk '$2<100 …'` and a `<path>` inside a quoted pattern both
match it. `wc -l < file` is the common real form and it sends a count.

That matters because the fix has a precision cost the operand path does not.
`wc -l < big.log` would block on any finding in `big.log` while sending one
number, and today it sends that number with nothing read. Take the count
through the segmenter first, split it by reader, and decide whether the answer
is every reader or only the ones that emit content.

## Provenance

Found while driving Q126's fixtures on 2026-09-04, as the control arm for a
path refusal: `cat < matches.env` was the arm that was supposed to behave the
same as `cat matches.env` and did not. Out of scope there — closing it means
recording the redirect operator in `internal/bash`, which is upstream of both
answers rather than a widening of either — so it is filed rather than folded in,
and Q126 was deliberately not widened to cover it.

The reader spread, the `v0.2.0` status and the `cwd` trap were added after the
row was filed, on a re-drive prompted by the orchestrator's own verification.
