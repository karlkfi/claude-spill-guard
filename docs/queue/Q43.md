# `actionlint` does not compile in `tools/`, and three docs say it runs

`cd tools && go build github.com/rhysd/actionlint/cmd/actionlint` exits 1 with
five errors, all of them one API disagreement about YAML. The last is the root
— `exhibit:parse.go:1567:26: undefined: yaml.ParserError` — and the other four
are downstream of it: `te.Errors[0].Error`, `e.Err`, `e.Line` and `e.Column`
each undefined because the value is a `string` where actionlint expects a
structured error.

The line numbers above are `exhibit:`-marked because they point into
actionlint's own source in the module cache, not into this tree, so no check
here can resolve them and none should try.

**Still live 2026-09-02 at `7163d08`**, after the five-item release batch:
`cd tools && go build github.com/rhysd/actionlint/cmd/actionlint` exits 1 with
the same five errors and the same line numbers, so nothing above has drifted
and the pin is untouched by that work.

**One of three, not the module.** Measured 2026-08-23 against `origin/main` at
`1a7e9f6`, independently in two checkouts: `govulncheck` builds (exit 0),
`golangci-lint` builds (exit 0), `actionlint` does not. So `tools/` is sound
and one pin has a conflict with a sibling's transitive choice. `tools/go.mod`
carries `go.yaml.in/yaml/v3 v3.0.5` and `gopkg.in/yaml.v3 v3.0.1` at once,
which is where to start; actionlint v1.7.12 wants a `yaml.ParserError` that
`gopkg.in/yaml.v3 v3.0.1` does not have.

It is not caused by Q20's one-line move of `go.yaml.in/yaml/v3` from the
indirect block to the direct one. That changed no version and left `go.sum`
untouched, and the failure reproduces on a `tools/` byte-identical to the
trunk.

## The half that makes it worth a row on its own

Nothing runs actionlint, so nothing reports this. [Q22](Q22.md) is where its
gate lands, and Q22 is ready rather than blocked now that the launcher has
shipped — so this pin is what stands between that row and a working third
gate. Meanwhile the repository asserts three times that it works,
and each claim is wrong in its own way:

- **`CLAUDE.md`**, zero-dependencies section: "Run one with `cd tools && go run
  <path>`."
- **`tools/tools.go`**, package comment: the single worked example in the file
  is `cd tools && go run github.com/rhysd/actionlint/cmd/actionlint
  ../.github/workflows/*.yml` — the one tool of the three that does not
  compile. Anyone following it gets five compiler errors and no reason to
  suspect the pin rather than their own machine.
- **`make doctor`'s own output**: "golangci-lint, govulncheck and actionlint
  are versioned in tools/go.mod and run with `cd tools && go run <path>`, so
  Go being present is what they need from you." Flatly false for actionlint.

Same shape as [Q39](Q39.md) and [Q42](Q42.md): an assertion in prose with
nothing executing it.

## `go run` is the wrong verb in all three, separately from the pin

`go run` does not propagate its child's exit status. It returns 1 for any
non-zero exit and writes the real one to stderr as `exit status 3`. Measured
2026-08-23 on a two-line probe: `go run .` returned 1 where `go build &&
./probe` returned 3.

That is harmless for a tool whose only codes are 0 and 1, and it destroys the
signal for anything richer. Q20 hit it in `scripts/check-vulns.py`, where
govulncheck's 3 (*a vulnerability was found*) arrived as 1 and was reported as
the tool failing — the one confusion that script exists to prevent. It builds
first now, and `CLAUDE.md` says why. The three docs above still teach `go run`,
so fixing them is part of this.

Fixing the pin is the first half; deciding what those three sentences should
say instead is the second, and they should not be three copies.
