# A count inside wrapped prose cannot be incremented without a reflow

[Q72](Q72.md) and [Q98](Q98.md) already say a number written by hand goes
stale, and both argue it from staleness: nothing re-reads the sentence, so
there is no event that would have said. This is a second cost, and under
parallel dispatch it is the one that shows up first.

**Both conflicts a four-branch batch produced on 2026-09-01 were hand-kept
counts, in two unrelated files** — and the two conflicted by different
mechanisms, which is the part worth writing down.

**The plain case, `.github/workflows/release.yml`.** The
`dry-run-mutation-control` header comment opened `Two mutations`. Two branches
each appended a step, at opposite ends of a hundred-line job, and each rewrote
that sentence — one to `Three`, one to `Four`. `git merge-tree --write-tree`
gives one path and `git merge-file` over the three staged blobs gives **one
hunk, six comment lines**. Both branches' actual step insertions auto-merged.
Nothing about proximity is involved: line-clearance arithmetic across the two
insertions predicted a clean merge and was right about the insertions.

**The case that is not obvious, `scripts/README.md`.** Q98's subject, opening
`Sixteen Python files here are this repo's own, and fifteen of them are entry
points`. Two branches each added a script, and **both wrote the identical
replacement** — `Seventeen ... sixteen`. That line merged. The conflict is nine
lines further down, in the *other* sentence carrying the count:

    <<<<<<< Q57
    **No gate asserts any of this, on purpose.** None of the seventeen is invoked by
    path: the sixteen entry points run as `$(PYTHON) scripts/x.py` from the
    =======
    **No gate asserts any of this, on purpose.** None of the seventeen is invoked
    by path: the sixteen entry points run as `$(PYTHON) scripts/x.py` from the
    >>>>>>> Q106

`sixteen` is one character longer than `fifteen`, so the paragraph has to
rewrap, and the two authors broke the line in different places. Same words,
same meaning, conflicting bytes.

**So the mechanism is not "a count is a shared line".** It is that a count
inside wrapped prose makes every increment a multi-line reflow, which no two
authors perform identically. That is why the second instance conflicted even
though both sides agreed on every word, and why it would still conflict if the
count were correct, gated, and reviewed.

The repairs Q72 and Q98 already name remove this as well as the staleness. The
workflow comment is a third instance wanting the third repair: enumerate what
each step covers and let the reader count, since the list is already there and
the number in front of it is the only part two authors have to agree on.

Half of that repair is in and it is the half that does not help. Read
2026-09-03, the comment enumerates all five steps and still opens `Five
mutations` — so the list is there, the number is in front of it, and the
count has gone `Two` to `Four` to `Five` in three days. Each increment is a
reflow two authors have to perform identically.

`scripts/README.md` line 22 says **No gate asserts any of this, on purpose.**
That stays right for the prose — it is an argument against a gate, not against
dropping a number no reader needs. The line quoted above is that same sentence,
which is what makes it the exhibit.

Found while resolving Q97's conflict with Q57. Filed rather than added to Q98
because a live batch was holding that file.

**[Q98](Q98.md) owns the derivation half and this row does not restate it.**
Resolving these conflicts means recomputing the count, and the two obvious
commands for that are both wrong in opposite directions — measured on the same
day, on the same file, and recorded there. The two rows are one subject seen
from two sides: this one is why the sentence conflicts, that one is why the
number you replace it with is likely to be wrong.
