# install.sh says the launcher finds a `--dir` it never looks in

`sh install.sh --dir <path>`, with `<path>` not on `PATH`, ends by printing:

```
install.sh: ./bin is not on your PATH. The hook launcher looks there
install.sh: anyway, so spill-guard will run as a hook; add it to PATH to
install.sh: use the command yourself:
```

The launcher does not look there. `hooks/run-spill-guard.cmd` resolves
`SPILL_GUARD_BIN`, then `command -v spill-guard`, then
`$HOME/.local/bin/spill-guard` on POSIX, and `%LOCALAPPDATA%\spill-guard\bin`
on Windows. A binary in any other directory off `PATH` is found by none of
them, so every hooked call gets `DENY_MISSING` and blocks with "the binary was
not found". It fails closed, so nothing crosses. But the message tells the
user the install worked when every call will block, and the fix it offers
(adding the directory to `PATH` "to use the command yourself") is what the
hook needs too, for a different reason than the one given.

Seen 2026-09-26 on the v0.5.0 publish check, `sh install.sh --dir ./bin` from
the published release. The message is at `install/install.sh:319` and is
unchanged since v0.3.0, so it is not a v0.5.0 regression.

The sentence is true only when `<path>` is the launcher's own default. So the
fix is either to print it only then, or to tell the user to set
`SPILL_GUARD_BIN` or add `<path>` to `PATH` before starting a session.
`install.ps1` needs the same reading. Check whether it prints a similar line
before assuming it does not.

see the block arrive. The reading above comes from the launcher's source.
