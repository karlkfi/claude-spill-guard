# The loader must reject validator settings that can never fire

`internal/rules` already fails a rule whose regex does not compile, rather than
skipping it, because skipping is the fail-open shape: a scanner missing a rule
reports the same clean result as one that checked everything. Two validator
settings have that property and neither involves a regex, so the compile check
does not reach them.

- **A context-proximity rule with no labels.** `NearLabel` returns false for
  every candidate, so the rule reports nothing at all. It cannot tell an empty
  list from a list that failed to match, and guessing the other way — treat
  "no labels" as "no gate" — turns one typo back into the 5,679-match ruleset.
  Pinned as returning false in `internal/validate/label_test.go`. A window of
  zero has the same outcome and is not reachable from a rule file: the schema
  carries no per-rule window, so a rule naming one is rejected as an unknown
  field.
- **An entropy floor above what the captured group can reach.** `Shannon` is
  bounded by `log2(len)` as well as by content, so no eight-byte capture
  exceeds 3 bits however random it is. A floor of 3.5 on a rule capturing eight
  bytes disables it, and nothing anywhere says so.

Each of these is a rule that loads, compiles, runs on every file, and reports
nothing. The failure is invisible from the outside: a quiet rule and a correct
rule produce identical output, which is the whole reason the loader fails
closed on the regex.

The entropy bound needs the rule's regex to answer properly — the shortest
string the captured group can match — which is why this sits with the loader
rather than in `internal/validate`. The other is readable straight off the
rule.
