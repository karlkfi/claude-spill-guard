# `gate-drift` cannot see a matrix leg in `tests.yml`

`job-drift` now declares the matrix legs of every workflow it reads, and narrowing `release.yml`'s `install-dry-run` to one OS turns it red.
It deliberately does not read `tests.yml`, which `gate-drift` reconciles against `GATES` in the Makefile, and `gate-drift`'s unit is the job key.
So the leg axis that row closed for the declared workflows is still open in the derived one.

Measured 2026-11-26 on the branch that added the leg declarations: narrowing `launcher`'s matrix from `[ubuntu-latest, macos-latest, windows-latest]` to `[ubuntu-latest]` leaves `make gate-drift` at exit 0 (`26 gates, and every consumer agrees`) and `make job-drift` at exit 0.
That deletes the only Windows exercise of the launcher's `cmd.exe` half, which is a shipped target and the half with a measured fail-open behind it.

Pull request #277 posted eight leg check runs from `tests.yml`: `launcher` (three), `launcher-mutation-control` (two) and `filter-rewrite` (three).

The legs cannot be derived from `GATES`, because which platforms a gate needs is a property of the gate rather than of the list, so the fix is a declaration beside the derivation — a leg list per gate that has a matrix, asserted both ways, in the shape `scripts/check-workflow-jobs.py` uses.
The parser already emits the legs, so this is Python only.

Found while completing the row that added legs to `job-drift`, and filed rather than folded in because `gate-drift` is a different gate with its own mutation control.
