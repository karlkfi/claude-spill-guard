# install.sh and install.ps1, exercised on all three OSes

Both scripts live in this repo so they are reviewable at a versioned URL. Each
detects OS and architecture, downloads the matching archive, verifies the
sha256 against `checksums.txt`, verifies the Sigstore signature when `cosign`
is present, and installs to `~/.local/bin` or `%LOCALAPPDATA%`.

**The documented form is two steps — download, read, run.** The one-liner that
pipes into a shell will work and is not what the README leads with. For a tool
whose pitch is that nothing leaves your machine, opening with "pipe this remote
script into your shell" undercuts the claim before a reader reaches the second
paragraph.

CI runs both scripts on all three operating systems every release. An install
script that broke is indistinguishable from a tool nobody installed, so this
needs a mutation control like the launcher's: break the checksum comparison and
require the job to go red.

## The open question this item carries

**Answered 2026-08-28: verify with whichever verifier is present, and refuse
only when neither is.** sha256 against `checksums.txt` always; then the cosign
keyless signature where `cosign` is installed, else `gh attestation verify`
against the build provenance. Both artifacts are already published — the
signature and `checksums.txt.pem` from the cosign step, and the attestation
from `actions/attest-build-provenance` — so this asks the release workflow for
nothing new.

**What the earlier framing got wrong, and it is why the question stood open.**
The row asked *refuse without cosign, or warn*, which reads as a trade between
fail-closed and reach. It is not: `cosign` is one of two verifiers for the same
property, and the other is `gh`, which anyone installing from GitHub is likelier
to have. The sha256 check is not the fallback it looks like either — a
`checksums.txt` fetched from the same place as the archive answers corruption
and not substitution, so authenticity genuinely needs a verifier and the only
question was which.

Refusing when neither is present costs the fail-closed rule nothing and costs
reach almost nothing: the two channels aimed at unequipped machines, the
Homebrew formula and the Scoop manifest, pin the sha256 themselves and ask the
user for no tool at all.

**Install-time only.** The shipped binary reaches neither verifier and cannot:
`scripts/check-supply-chain.py` forbids `os/exec` across the build graph, gated
in CI over 115 packages. Nothing about this decision can affect a scan.

The original question, for the record:

**Ask:** whether `install.sh` refuses without `cosign`. What turns on the
maintainer is a trade between two stated properties of the product, and the
repo's own rules point both ways: *fail closed* is the rule everywhere else
here, and most machines have no `cosign`, so the strict reading makes the
fallback channel unusable for exactly the people it exists for. No precedent
settles it — `CLAUDE.md` names this as the one open question left in
`distribution.md` rather than answering it.

Whether `install.sh` should refuse to proceed when `cosign` is absent. Failing
closed is the rule everywhere else in this project, and most machines do not
have cosign installed, so the strict reading makes the fallback channel
unusable for most of the people it exists for.
