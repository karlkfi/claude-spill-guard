# `job-drift` cannot see a matrix leg, and a leg is a check run

The gate reconciles the jobs in `release.yml` and `prompt-oracle.yml` against a
declaration. Its unit is the YAML job key, and a matrix leg is not one — so the
gate's own symptom reappears one level down.

Measured 2026-09-17 against the branch that added it. `release.yml` posts eight
check runs on a pull request and **five of them are legs**, whose rendered names
are not their keys:

```
install-dry-run (windows-latest)
install-dry-run-mutation-control (windows-latest, install/install.ps1)
```

Narrowing one line —

```
os: [ubuntu-latest, macos-latest, windows-latest]   ->   os: [ubuntu-latest]
```

— deletes the macOS and Windows exercise of `install.sh` and `install.ps1`, and
`python3 scripts/check-workflow-jobs.py` still reports rc=0 and `7 job(s) across
2 workflow(s), every one declared`. Two check runs stop existing and nothing
goes red, which is the sentence the gate's own docstring is written about.

Sharpest on `install-dry-run-mutation-control`, whose two `include:` legs are
the only Windows exercise of `install.ps1`'s digest check.

It is also the one place a declaration asserts something the gate cannot hold:
`install-dry-run`'s reason says *on Linux, macOS and Windows*, and nothing reads
the half that names three platforms.

## Why this is M and not S

`tools/cmd/workflow` models a job as `{Name, Runs}` and carries no matrix at
all, so this is a change to the Go parser before it is a change to the Python
that reads it. That model is the seam the whole check rests on — it exists so a
job name a regex misses cannot be silently unseen — so widening it is worth
doing deliberately rather than as a follow-on hunk.

Whether the declaration should then name legs, or name a leg *count*, or assert
only that a matrix exists where one is declared, is open. Naming legs by
rendered name pins `${{ matrix.os }}` interpolation into a declaration and makes
every matrix edit a two-file change; a count is weaker and cheap. Both readings
are available and this row does not take one.

## What this is not

Not the job-level check, which holds: a deleted, renamed or undeclared job is
caught in both directions, driven. This is the axis below it.

Not a defect the gate introduced. Before it, nothing read `release.yml`'s job
list at all, so the leg axis was uncovered along with everything else. The gate
narrowed the gap and this names what is left.

Found by an independent review of the pull request that added `job-drift`,
which is also where the two smaller halves of that review were fixed: an empty
declared reason, and a success line that credited a derived workflow that was no
longer there.
