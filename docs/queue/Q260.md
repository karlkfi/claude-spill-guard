# A case behind coproc is read as code that ran

bash runs the word after `coproc` as the coprocess's command, and that command
runs in a subshell, so nothing an arm assigns reaches the reader after it. The
segmenter does not read `coproc` as a word that leaves the next one in command
position: it is not in `leadingWords`. So the `case` behind it is no keyword,
the arm's assignment is taken as one that ran, and the reader after it is
resolved to the arm's path while bash opens the original.

Driven with a key in `./f` and clean text in `w/f`, bash 5.3.15 under `env -i
bash --norc --noprofile -c`, against binaries built at `08b0fb0`, at `649ef49`
and at Q223's fix:

| Command | bash | Hook, all three binaries |
|---|---|---|
| `SP=.; coproc case x in y) SP=w;; esac; cat $SP/f` | prints the key | exit 0, no verdict, no record |
| `SP=.; coproc case x in x) SP=w;; esac; wait; cat $SP/f` | prints the key | exit 0, no verdict, no record |
| `coproc { cd w; }; wait; cat f` | prints the key | deny, `aws-access-key-id` |

The second row matches its arm and still reads `./f`, which is the subshell.
The third is the control: a brace group behind `coproc` already gets its
verdict. Found by Q217's reviewer, and kept out of Q223, which fixed the
same crossing behind `time -p`.

Q220, merged as `649ef49`, peels `coproc` off a reader's head so the reader
behind it is looked up. That is the simple-command half and does not touch the
compound tracker, which is why `649ef49` reads like the other two.
