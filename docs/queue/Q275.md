# A brace group after env copies the dump around the filter

`env | tee /dev/stderr | cut -d= -f1` is refused on the branch that closed Q258.
Written as a group, the same stage is not: `env | { tee /dev/stderr; } | cut -d= -f1` and `env | { cat >&2; } | cut -d= -f1` get no verdict.
Driven 2026-11-27 through `hook.Run` with `bashCall`, on that branch's local tree.
Reviewer C found the shape in review of that PR. This row is what Claude drove from it.

The grep filter does not share the hole, and that is the control.
`grep -rn x . | { tee /dev/stderr; } | spill-guard filter` and the `{ cat >&2; }` spelling are refused in the same run, while `grep -rn x . | spill-guard filter` is allowed.
Why the grep path refuses was not read, so it may be refusing for a reason other than the copy.

The mechanism is unverified.
`copiedAround` skips a segment whose `Pipe` differs from the dump's, and a command inside a `{ …; }` piped as a whole may not carry the dump's pipe number.
`downstream`, which Q257 added, reads a group's segments by `Shells` depth for the grep path, which may be what `lastInPipeline` needs too.

**Done** when both group spellings after `env`, and the same after a guarded read, are refused, and `env | { cut -d= -f1; }` is still allowed.
