# A key in a command string holding a NUL crosses

A `Bash` or `PowerShell` command string with a NUL in its first 8 KiB takes the binary
skip like a file does, so no rule runs over it. A key typed beside that NUL crosses. The
prompt surface does not have this gap, because it runs the match loop over raw bytes.

## Driven 2026-11-03

Built binaries at `a99ed37` and at Q244's head, identical on both. The reviewer of #236
found the `$X` arm; Claude reproduced it and took the rest.

| Payload | Result |
|---|---|
| `Bash` `cat "$X" <key>` | denied |
| `Bash` `cat "$X" <key> <NUL>` | exit 0, no verdict, one record: `Nothing in this call was decoded` |
| `Bash` `echo <key> <NUL>` | exit 0, a notice naming `<command>` as undecoded, no block |
| `PowerShell` `echo <key> <NUL>` | exit 0, no verdict, one record |
| prompt `<key> <NUL>` | blocked |

Whether a NUL reaches a command string in real traffic is unmeasured, and the harness may
not deliver one to the shell intact. So how often this happens is open, as is whether the
call would run at all.

## What is owed

Decide with those two readings in hand. `scanCall`'s reason for keeping `Read` and `Bash`
on `scan.Buffer` is the cost of a 306 MiB binary operand, which is an argument about
files and says nothing about a command string, so one candidate is
`scan.BufferIncludingBinary` for `commandLabel` alone. That has not been built. A fix has
to go red when put back, on each row above that crosses.
