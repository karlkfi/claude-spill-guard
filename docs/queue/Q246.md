# A command string holding a NUL goes unscanned, if one ever arrives

**Event:** a `must_refuse_nul` arm in `scripts/check-hook-harness.py` goes red at a
`CLAUDE_VERSION` bump, because that version lets a `Bash` or `PowerShell` command holding a
NUL reach `PreToolUse`. Then this row is the work. A red arm can also be a reworded refusal,
so read the result first.

A command string with a NUL in its first 8 KiB takes the binary skip like a file does, so
no rule runs over it. The prompt surface does not have this gap, because it runs the match
loop over raw bytes. So the hook has the gap, and on every version driven Claude Code
refuses the call first.

## The hook, handed the payload directly

Driven 2026-11-03 on built binaries at `a99ed37` and at Q244's head, identical on both. The
reviewer of #236 found the `$X` arm; Claude reproduced it and took the rest.

| Payload | Result |
|---|---|
| `Bash` `cat "$X" <key>` | denied |
| `Bash` `cat "$X" <key> <NUL>` | exit 0, no verdict, one record: `Nothing in this call was decoded` |
| `Bash` `echo <key> <NUL>` | exit 0, a notice naming `<command>` as undecoded, no block |
| `PowerShell` `echo <key> <NUL>` | exit 0, no verdict, one record |
| prompt `<key> <NUL>` | blocked |

## Claude Code, making the call

Driven 2026-11-04 through a real `claude` and the loopback fake from
`scripts/check-hook-harness.py`, with a plugin whose only hook appends its stdin to a file.
spill-guard itself cannot answer this, because it writes nothing on `echo <key> <NUL>`.
macOS.

| Call | Hook fired | Result |
|---|---|---|
| `Bash` clean, on 2.1.282, 2.1.289 and 2.1.290 | once each | the command's output |
| `Bash` `echo <key> <NUL>`, on the same three | 0 | `InputValidationError`, no output, no key |
| the same under `--dangerously-skip-permissions`, 2.1.290 | 0 | the same |
| the same with `run_in_background`, 2.1.290 | 0 | the same |
| `PowerShell` clean, `pwsh` a stub, 2.1.290 | once | a classifier error |
| `PowerShell` `Write-Output <key> <NUL>`, the same stub | 0 | `InputValidationError` |
| `Grep` clean, `--tools Grep`, 2.1.290 | once | `No files found` |
| `Grep` pattern `<key><NUL>`, the same | 0 | `Grep pattern cannot contain null bytes` |

The refusal reads `command contains control characters that would be hidden in the
approval dialog`. It also takes U+0001, U+0007, U+001B and U+007F. It does not take a tab,
U+202E or U+FEFF, and the hook fired on all three. No command runs and the result holds no
key. The next request repeats the refused `tool_use` with the key in it, on 2.1.282, 2.1.290
and 2.1.309, as it does when the hook denies the same call without the NUL. The model wrote
that input, so refusing it unsends nothing.

The `must_refuse_nul` arms run this on every pull request at the pinned `CLAUDE_VERSION`:
`Bash` on `ubuntu-latest`, and whichever shell the harness offers on `windows-latest`. They
pass on 2.1.309 too, the build Claude Desktop ships here, driven locally. Nothing moves the
pin when Claude Code ships, so a release that delivers such a call goes unseen here until
somebody bumps it.

A different check refuses a NUL in `Read` `file_path` and in `Grep` `pattern`, `path`, `glob`
and `type`, reading `cannot contain null bytes`. The hook fired 0 times on each of the five
on 2.1.290 and 2.1.309, against controls that fired once, the reviewer of #239 and Claude
driving it separately. No CI arm covers this one.

## Real traffic

0 of 243,065 `Bash` commands hold a NUL, over every transcript under `~/.claude/projects`
on one machine: 2,924 files, 2,098,328 lines, none undecodable, 2026-07-26 to 2026-11-04,
deduped on `tool_use` id. The walker found the NUL in 5 of 5 NUL-bearing harness
transcripts and in 0 of 2 clean ones, so a call the harness refuses still gets recorded and
that zero can be read. 53 of 328,232 tool results in the same files hold one.

Two of those commands hold another C0 control character, U+0007 on 2.1.237 and U+0001 on
2.1.260. Both were refused with the same error, and those are the only two.

## What this does not cover

- 0 `PowerShell` calls in that corpus, so the sweep says nothing about that tool.
- One machine and one user, with nothing from before 2026-07-26 and no cloud sessions.
- A NUL on anything below 2.1.282. The lowest driven binary is that one, and the U+0007
  refusal on 2.1.237 is the only reading further back.

## What is owed if the event fires

`scanCall`'s reason for keeping `Read` and `Bash` on `scan.Buffer` is the cost of a 306 MiB
binary operand, which is an argument about files and says nothing about a command string,
so one candidate is `scan.BufferIncludingBinary` for `commandLabel` alone. That has not
been built. A fix has to go red when put back, on each row of the first table that crosses.
