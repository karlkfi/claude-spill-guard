# The vendored `queue.py` predates the label metrics the groom reads

[`scripts/README.md`](../../scripts/README.md) pins
`scripts/vendor/claude-skills/queue.py` at `c0a239b`, 2026-08-22. Upstream has
added `metrics --labels` since, and this copy does not have it:

```
$ python3 scripts/vendor/claude-skills/queue.py metrics --labels
queue.py: error: unrecognized arguments: --labels
```

Two lint classes are missing with it, both measured the same way on 2026-09-01.
`--strict question-route` is rejected as an invalid choice, so nothing here can
name a marked row that carries no route — the check the groom's routing step is
supposed to run. `wikilink-ref` is absent too, which is the class that is wrong
on the rendered page and silent in the store, so its absence is the one that
cannot be noticed by reading.

`render --label` works here and answers a different question. It reports the
**stock** — four rows carry `open-question`, out of sixty-three, measured
2026-09-01 after that day's groom routed two more. What the groom
needs is the **flow**, because two moves change the stock with no question
settled: a row filed already carrying the label, and a row that ships still
carrying it. A stock holding steady is equally consistent with a class settling
questions as fast as it meets them and with one that has never settled any, and
this store cannot currently tell those apart.

That reading is not decoration on the label. It is the only signal that the
class is being settled rather than marked, and the label was introduced here
because a selection pass skips every row carrying it.

**Run from an up-to-date copy, the answer is good — which is worth recording
and does not retire this row.** Taken 2026-09-02 at `7163d08` against the
installed `session-backlog` script rather than the vendored one:

```
label          filed-with  gained  settled  closed-carrying  now
open-question           7       6      10               0    3
```

Ten settled against nothing shipped still wearing the label, so the class is
draining rather than accumulating. The stock in the paragraph above has moved
too — three rows now, not four.

What this settles is the worry, not the gap. The reading had to be taken from
outside the repository, so no gate here can take it, `make queue` still cannot,
and the next groom is back to the stock unless somebody remembers to reach for
another copy. Re-vendoring is what makes the answer available to the check that
is supposed to produce it.

## What the re-vendor costs, measured

The diff against upstream is four hunks and purely additive — 120 lines added,
2 changed, both of them the help text and the `--events` argparse line that
`--labels` joins. Nothing before line 709 moves.

Two consequences worth having before the work starts. `CITATION_WINDOW` does
not move, so [Q30](Q30.md)'s live pointer at it survives the refresh and the
`queue` gate's threshold is unchanged. And `lint` is untouched, so no gate
changes verdict — this is a feature arriving, not a behaviour bump.

That is what makes it S. A re-vendor that moved `lint` would need the whole
store re-linted against the new copy before the digest row could be trusted.

## The work

Follow the procedure `scripts/README.md` already states: overwrite the file
from upstream rather than editing in place, move the commit and `sha256` in the
vendored table to the new revision so the digest change lands in the same diff,
then `make vendor` and `make queue`.

Re-derive the diff at the revision actually taken rather than trusting the
measurement above — it was read on 2026-08-26 against the working checkout of
`karlkfi/claude-skills`, which is not a revision anybody else can resolve.
