# Drive a real Grep tool payload through the hook

`hooks.json` now matches `Grep`, and `grepToolTargets` reads `pattern`, `path`
and `output_mode`. Those names come from 161 `Grep` `tool_use` blocks in this
machine's transcripts, 2026-08-02 to 2026-10-01 — and every one of them came
back `No such tool available: Grep`. So they are the model's guesses at a tool
the harness did not offer, not a payload anything received, and nothing here
shows the tool exists in any build. The PR #191 review found it.

So four things are assumed rather than read:

- that a `Grep` tool exists in some Claude Code build at all;
- that the payload's `tool_input` carries those keys as the model wrote them;
- what an absent `output_mode` means to the tool — read as `content` here, so
  a wrong guess over-refuses rather than letting lines cross;
- that a deny reason reaches the model on this tool as it does on `Bash`.

Drive it the way the other surfaces were driven: a session with the tool,
a matcher of `Grep` and a stdin log, then one `content` search over a
directory and one `files_with_matches` search, reading what the hook received
and what reached the transcript.
