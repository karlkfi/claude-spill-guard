# Attach the provenance bundle, so a scanner can see it

A release carries a cosign signature over `checksums.txt` as
`checksums.txt.sig`, and build provenance minted by
`actions/attest-build-provenance`. The signature is a release asset; the
provenance is not — it lives in GitHub's attestations API, which is what `gh
attestation verify` reads and what nothing scanning the release page can.

OpenSSF Scorecard's Signed-Releases check reads the last five releases and
scores their **asset names**: a `*.sig`, `*.asc`, `*.sign`, `*.minisig`,
`*.sigstore` or `*.sigstore.json` scores 8, and a SLSA provenance file
(`*.intoto.jsonl`) scores 10. So this release scores 8 while carrying the
evidence for 10, and the gap is a packaging decision rather than a difference in
what was signed.

`actions/attest-build-provenance` has a `bundle-path` output. Uploading that
file to the release as `<something>.intoto.jsonl` closes it, and the release job
already holds `contents: write`.

Worth settling at the same time: whether the verification step should also
verify the attached bundle offline, rather than only through `gh attestation
verify`, which reads the API. A consumer with no network path to GitHub's
attestations endpoint has the bundle and nothing that uses it.
