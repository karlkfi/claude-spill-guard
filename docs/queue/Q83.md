# Nothing reports a branch carrying reviewed work that has no PR

When this row was committed, at 2026-08-28T15:14:11Z, `git ls-remote --heads
origin` returned two refs. One of them, `claude/cranky-bardeen-9ea62b-notes` at
`2b54a6f`, had never had a pull request and carried a commit `main` cannot
reach. It had been there for two days when a sweep for something else found it.

That count is pinned to its reading on purpose, because the decay is this row's
subject rather than an aside. Twenty-five minutes later the same command
returned six — this pull request's own branch and three siblings — with a
reviewer reading five in between, bracketed by #53 opening at
2026-08-28T15:33:40Z. A ref listing is where a live branch and a spent one stop
being distinguishable, and it fills faster than anyone reads it.

## What happened, from the API rather than from the branch name

Pull request #32 merged `claude/cranky-bardeen-9ea62b` at 2026-08-27T00:35:00Z,
as a squash — three commits under the PR head, one on `main`, which is what
establishes it rather than the two readings below that do not. `2b54a6f` is one
commit past that head, `2fc8405`, committed
2026-08-26T16:38:02Z — 7h57m *before* the merge — and pushed only to the
`-notes` branch, which no pull request ever carried. The squash took the three
commits under the PR head and left the fourth where it was.

That is the mechanism the
[2026-08-27 postmortem](../postmortems/2026-08-27-refusal-echoed-an-unscanned-field.md)
records under *The squash boundary is invisible from a pull request view*, and
it says the mechanism will recur. It already had: this instance predates the
postmortemed one by about fourteen hours.

**The two differ only in whether a person was holding the commit.** In the
postmortem the author refused an instruction to downgrade the fix, re-measured,
and pushed it into an open PR — the write-up calls that "a good outcome reached
by an unreliable route". Here nobody was holding anything, the route was not
taken, and the work sat.

## Why ancestry cannot be the test

The obvious sweep is `git merge-base --is-ancestor <ref> origin/main`, and it
answers nothing here. This repository squashes in practice, so the merge
rewrites the tip and **every** merged branch stays diverged forever — `2fc8405`,
whose whole content is on `main`, fails that test exactly as `2b54a6f` does.

**Arity is what establishes the squash**, and that is worth writing down because
the weaker argument is the one that comes to hand. A single-parent merge commit
and a non-ancestor head are each produced by a rebase merge too, so neither tells
the two strategies apart — and `rebaseMergeAllowed` is `true` here, so that is
live rather than academic. Arity does tell them apart, and exhaustively:
`mergeCommitAllowed` is `false`, so squash and rebase are the only two available,
and they differ in how many commits a multi-commit pull request leaves on `main`.
#32 left three commits' worth of work as one, `bda2739`, the only commit citing
`(#32)`. (A single-commit pull request is not a discriminating case under either
strategy, which is why the argument has to name #32 rather than rest on the last
40 commits each carrying a distinct `(#N)`.) The conclusion holds either way,
since ancestry fails under a rebase merge too.

Separating the two *branches* is a different question from separating the two
merge strategies, and the reading that did it was content: `git diff origin/main
<ref> -- <paths>`, which is empty for the merged commits and 24 insertions for
the orphaned one, plus `gh pr list --head <ref> --state all`, which returns
`#32` for one branch and `[]` for the other. Neither read closes it alone.

## Where a check could live, and where it cannot

Not in CI on a pull request. Every gate this repository runs reads the tree, and
this is a property of the remote's ref set — no tree contains the evidence, so
no `make` target can be pointed at it. That leaves a scheduled job or a step in
whatever grooms the backlog, reporting each non-`main` ref with the commits
`main` cannot reach and whether a pull request ever carried it.

The same output answers the question nothing answers today either: which of
these refs is safe to delete. A branch that is spent and a branch holding
unmerged work are indistinguishable from the listing, which is why the listing
is where they accumulate.
