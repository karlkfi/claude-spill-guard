# A function body is read where it is defined, not where it is called

`f() { cat x; }; cd w; f` reads `w/x` in bash, because the body runs in the
caller's directory at the call. The hook reads `./x`, at the definition. With
the key in `w/x` and clean text in `./x` it exits 0 with no verdict and
nothing on stderr. Driven 2026-11-01 on bash 5.3.15 under `env -i bash
--norc --noprofile -c`, and through `hook.Run` on the Q212 branch by a
throwaway test.

Q212 scoped a function body, so a `cd` inside one no longer moves what
follows the definition, and a call to a body that moves loses the directory.
What it did not change is where the body's own operands resolve: the walk
reads the body's segments in place, with the directory in force at the
definition, and a body never called is read anyway. Upstream does the same,
where the cost is a prompt rather than which file gets opened.

Two readings to weigh, neither measured: resolve a body's relative operands
against every directory a call reaches (the set the command sends), or treat
a relative operand in a body as unresolved whenever the directory at a call
differs from the one at the definition. A body defined and never called is
the over-read half and costs precision, not recall.
