# Resolve a literal assignment made earlier in the same command string

`F=probe.txt; grep -n hello $F` blocks with *a file operand expands at run time,
so what this command would read cannot be known before it runs* — driven on the
0.2.0 binary, alongside `grep -n hello $F` with no assignment, which produces
the byte-identical reason.

The two are not the same situation. In the second, `F` was set by some earlier
Bash call and the value genuinely is unknowable at `PreToolUse`. In the first it
is written in the string being scanned, three tokens earlier, and the refusal
throws away an answer it is holding. `workspace-guard` resolves this case — a
variable assigned a plain literal path earlier in the same command string is
tracked and does not prompt — so the two guards diverge on a shape sessions
write constantly.

## Why it is not simply a lookup

The value has to be a *literal*, and deciding that is the whole of the work:

- **Only a plain literal.** `F=$HOME/x`, `F=$(pwd)/x`, `F="$D/x"` all have to
  keep refusing. Resolving one substitution invites the next, and the stopping
  point is the same closed set `workspace-guard` settled on.
- **Last assignment before the use wins**, and only on a path the shell would
  actually take. `F=a; F=b; cat $F` is `b`; `false && F=b; cat $F` is not, and
  neither is an assignment inside a `$(…)` body or one branch of an `if`.
  Reaching for control flow here is how a shell parser starts being written,
  which this repo refuses by name.
- **`export`, `local`, `declare` and `readonly` prefixes** are assignments too,
  and each has its own argument shape.
- **`${F}`, `${F:-default}`, `$F.bak`** are uses that a naive `$NAME` match
  either misses or mis-splices.

The fail-closed direction is available at every one of these: anything not
settled keeps the refusal it has now. What must not happen is resolving to a
path the command would not have read, which turns a block into a scan of the
wrong file and reports clean for the right one.

## The precedent to port rather than re-derive

`claude-workspace-guard` already carries this, and
[`internal/bash`](../../internal/bash/) is a port of its segmentation layer kept
structurally identical so a fix there transfers by inspection. So the shape to
take is upstream's tracker, not a fresh one — and [Q63](Q63.md), which is about
nothing re-checking that port against its upstream, is the row this should be
sequenced with.

## Read with Q92 before starting

[Q92](Q92.md) is the same lexer boundary pointed the other way: the tokens
`bash.StripEnvPrefix` drops have already had their quotes stripped, so the hook
sees an assignment where bash sees a command name. Anything reading assignments
to *resolve* them inherits that defect, and would widen it from arming the
override to choosing which file gets scanned. Q92 is blocked on the shared-lexer
fix landing upstream; this row should not route around it.

## Where it came from

A friction report on 0.2.0, from a session in `~/workspace/claude-bouncer` on
2026-09-04. That report recorded the previous-call case as correct-by-design and
flagged the same-string case as a possible cheap alignment; driving both showed
the hook does not tell them apart.
