# The citation window hides the drift a pull request causes itself

`stale-citation` compares a citation's line number against the tree with a
tolerance, and the tolerance is
`scripts/vendor/claude-skills/queue.py:75:CITATION_WINDOW = 10`. That window is
right for the case [Q30](Q30.md) measured and settled — a branch that moves a
line some other row cites should not go red for work it did not do, which is the
`dangling-link` shape. This row is the other case, and the window does not
distinguish them.

A branch that moves a cited line **by ten or fewer** ships a citation that is
now wrong, and no gate anywhere reports it. `make queue MERGED=true` is green,
the `queue` job on `main` is green, and the store carries a pointer that sends a
reader to the wrong line.

## Measured on this repository, 2026-08-31

The pull request completing Q85 added nine lines of comment to `blocks()` in
`internal/hook/hook.go`. `Q10` cited that file by line and fragment — the row
has been completed since, so its text is in git history rather than the store,
and the exhibit outlives it:

| | |
|---|---|
| Q10 cites | `exhibit:internal/hook/hook.go:237:case UserPromptSubmit:` |
| where the fragment was on `main` | 237 — correct when written |
| where it was on the branch | 246 |
| drift | 9 |
| `make queue MERGED=true` | **exit 0, silent** |

**The boundary, bisected on this tree rather than read off the constant.**
Reverting Q10's pointer to each value and running `make queue MERGED=true`:

| cited line | drift | exit |
|---|---|---|
| 247 | 0 | 0 |
| 238 | 9 | 0 |
| 237 | 10 | **0** — the broken pointer, green |
| 236 | 11 | 2 — `stale-citation` fires |
| 235 | 12 | 2 |

So **drift of 10 or less passes and 11 or more fails**. Take that rather than the
comment above the constant, which illustrates the gap with a fragment that
`scripts/vendor/claude-skills/queue.py:73:moved nine lines` — true, and it reads
as a tolerance of 9, so an implementer working from the prose rather than the
value would be off by one on the number this row is about.

The citation in that first cell is marked `exhibit:` because it is a record of
where Q10 pointed on `main`, not a pointer this row depends on. Unmarked it would
drift with every edit to `blocks()`, and on the branch that filed this row it sat
at a drift of exactly 10 — the last passing value, the row's own subject closing
over the row's own evidence.

It was found by hand, while checking a different citation, and it would have
merged. Had it merged, the next branch to move that line would have pushed the
drift past 10 and gone red — so the branch that *reports* the defect would not
have been the branch that caused it. That is the same misattribution Q30 rejects,
displaced by one pull request: the window does not prevent it, it defers it.

## The two-branch case is worse, and no branch can see it

The measurement above is one branch moving a cited line. Two branches doing it
is a different defect, and the fix proposed below does not reach it: **each
side's citation is correct on its own branch, and the merged value is one
neither branch holds.**

Measured on `docs/queue/Q108.md`, which cites `CLAUDE.md` by line and fragment,
while #64 and two sibling PRs each added prose above that fragment. Every value
below was read from the line rather than derived, and each is correct in the
tree it was written in:

| | main | the PR | merged |
|---|---|---|---|
| after #66 | 220 | 224 | **247** |
| after #61 | 228 | 247 | **255** |

Twice, the same citation, within a day. Both sides repointed honestly against
what they could see, both were right, and both were wrong about the trunk. The
right answer existed in no branch at the moment either was written — it is a
property of a tree that does not exist until the merge, so *reading the line*,
which is the instrument the single-branch case needs, is not available either.

**That is strictly worse than the case above.** A single branch that moves a
cited line at least has the defect present in its own tree, where a windowless
check would find it. Here the defect is in neither tree. It appears on the
trunk, after both merge, attributable to neither author.

## A green store lint was consistent with both, for two different reasons

Worth stating because it is what made this expensive to find. Over one tree
carrying both a dangling link and a stale citation, `make queue` was green:

- `dangling-link` is promoted only on a push — the workflow passes
  `MERGED=${{ github.event_name == 'push' }}` — so it is a note on every pull
  request by design.
- `stale-citation` was promoted, and could not fire: the drift was 8, inside
  `CITATION_WINDOW`. Promotion changes what a note *costs*, never what counts as
  one, so no `--strict` flag reaches inside the window.

So a green `queue` check is evidence about neither class, for reasons that do
not overlap and neither of which is visible in the output. The reading that does
settle it is `--citation-window 0` with both classes promoted, and nothing in
CI runs it.

**There is one on the trunk as this row is filed.** `docs/queue/Q108.md` cites
`docs/design/README.md:101`, and the fragment is at 104 — drift 3, inside the
window, so `make queue MERGED=true` is green over it on `main` and has been
since Q108 landed. It is visible only to the reading above:

`exhibit:docs/design/README.md:101:Neither catches a command that synthesizes a secret at runtime`
is the pointer, marked because this row quotes it as evidence rather than
relying on it — the case `docs/queue/README.md` names as the one where reporting
drift is worse than missing it. Only this reading finds it:

```
queue.py lint --strict stale-citation --strict dangling-link --citation-window 0
```

This row does not fix it. #64 already repoints that line, and a second branch
editing it would create exactly the two-branch collision described above — which
would be an unusually literal way to make the point.

## What would close it

The check the window cannot make: for each citation, was the cited file changed
**by this branch**, and did the fragment move? A branch's own diff is what
separates the two cases, and it is available — `git diff --name-only
origin/main...HEAD` names the files this branch touched, and any citation into
one of those has no claim on the tolerance. Everything else keeps the window.

That is a repo-side check rather than a change to the vendored linter, which
matters twice: `make vendor` pins `queue.py` by digest so patching it is a fork,
and the window has to stay for every citation the branch did not disturb.

Not decided here: whether it lives in `scripts/check-queue-index.py`, in a new
gate script, or as an argument upstream in `claude-skills`. Q30's flag work is
independent — pinning the window at the call site does not close this, because
the window is not the defect.
