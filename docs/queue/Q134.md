# spill-guard blocks three operand shapes workspace-guard resolves

`resolve` refuses an operand it cannot settle, and three of those refusals land
on command shapes the machine's global working agreement tells every session to
write -- because they are the shapes *workspace-guard* resolves rather than
prompts on. Two sibling guards in one fleet therefore pull opposite ways on
identical command text, and following the documented advice for one reliably
trips the other.

**Measured 2026-09-04** in a `claude-bouncer` worker session, three hard blocks
in one session -- the whole `Bash` invocation ran nothing each time -- plus a
fourth in the session that filed this row. Each refusal opens
`spill-guard: blocked. Nothing scanned this call for secrets, because the scan
could not be completed:`, and the reasons were:

1. `for f in docs/queue/Q135.md docs/queue/Q145.md docs/queue/Q146.md; do echo "== $f =="; cat "$f"; done`
   -> `in the "cat" here, a file operand expands at run time, so what this command would read cannot be known before it runs`
2. `cd /Users/karl/workspace/claude-bouncer/.claude/worktrees/upbeat-sanderson-f2212d && wc -l plugins/branch-guard/hooks/branch-guard.py`
   -> `in the "wc" here, a file operand is relative and the command changes directory first, so which file it names is not settled here`
3. `SP=/private/tmp/claude-501/<...>/scratchpad; ...; tail -20 "$SP/fixA.log"`
   -> `in the "tail" here, a file operand expands at run time, so what this command would read cannot be known before it runs`
4. `grep -rli 'operand' docs/queue/ | sort`
   -> `in the "grep" here, a file operand names a directory, and this reads files rather than walking them, so what that operand would send was not read -- name the files instead`

The fourth is the directory refusal, which is settled and stays settled --
`docs/design/README.md`, *A directory operand is refused rather than walked*. It
is recorded here only because it is what the reporting session hit next, and
because it puts the friction's real rate above the three below. The first three
are the class this row is about, and all three are resolvable by static
analysis: a `for f in <literal list>` loop, a variable assigned a plain literal
path earlier in the same command string, and a `cd` to a literal target. The
global agreement names those three by name as the ones workspace-guard resolves,
and case 2 is the sharpest -- `cd <literal> && <relative operand>` is exactly
what its `cd` tracker is built for.

The code says why, and says it as a deliberate omission rather than an
oversight: `internal/hook/bash.go:93:this port does not carry the tracker`, so
any `cd` in a segment marks every later relative operand unsettled, whatever the
target. The `$` and backtick arm is a substring test --
`internal/hook/bash.go:274:a file operand expands at run time` -- so a variable
this process could have resolved reads the same as one it could not. The
relative-after-`cd` arm is
`internal/hook/bash.go:298:a file operand is relative and the command`.

**Two questions, and the row does not answer either.**

Whether spill-guard should adopt the three resolutions workspace-guard already
implements, and if so whether that logic belongs in a module both repos share
rather than being written twice. `claude-bouncer` has the precedent --
`lib/bouncer_parse.py` is vendored into all five guards by `scripts/sync-lib.py`
and its `CLAUDE.md` says what belongs in the shared parser -- but spill-guard is
a separate repo in a different language, so sharing is a real design question
rather than an obvious yes. It also bears on the standing rule that
`internal/bash` is held structurally identical to its upstream: a resolver is
the layer above segmentation, and nothing today says whether parity is expected
there too.

And whether an operand this cannot settle should block or should scan what it
can. The repo's fail-closed law answers that in one direction and the reason
text states it -- a scanner that skips an operand reports a clean result for a
file nothing opened -- so the question is not whether to weaken it. It is
whether a shape that *is* statically resolvable was ever in the fail-closed
class, given the cost of the block is the whole call rather than the operand.

**Ask:** whether to port the three resolutions, and whether a resolver is shared
across two repos he maintains -- a cross-repo ownership call, not a design
nobody here can settle.
