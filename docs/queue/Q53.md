# Benchmark the prefilter as implemented, and retire the inherited 280x

`docs/design/language-choice.md` section 2 puts the prefilter at 255–307 MiB/s
against 1.0 MiB/s for the regex pass — roughly 280x — and that figure was taken
on a `strings.Contains` prefilter. The same subsection then says that
implementation has to be replaced, because naive matching finds `sk-` inside
`disk-containerd-…`. So the number describes the shape the design corrects, and
it was never a measurement of the boundary-aware code that shipped.

The doc comment on `hasKeyword` quoted it as though it were, until a review
caught it.

## What is measured, and what the number depends on

Two runs on 2026-08-24 agreed that the walk cost about what the regex pass it
exists to skip costs — roughly 250x off the design's figure — and disagreed by
an order of magnitude about how much better `bytes.Index` is: 2.9x against
52–96x. That gap has a cause, and it is neither the corpora nor the load on the
machine.

**It is the first byte of the keywords.** The walk is O(buffer) and
content-independent. `bytes.Index` costs O(occurrences of the byte it anchors
on), because `IndexByte` skips at SIMD speed and pays only at candidate
positions. So the speedup is set by how common that letter is in the text.

Measured over 0.53 MiB of this repo's real files, thirteen keywords of
identical length, none of them matching, min-of-7, only the first byte varying:

| keyword | anchor-byte hits | per KiB | `bytes.Index` | walk | speedup |
|---|---|---|---|---|---|
| `Zqxj` | 1,607 | 3.0 | 32.3 µs | 1.508 ms | 46.6x |
| `Kqxj` | 4,621 | 8.6 | 77.8 µs | 1.490 ms | 19.2x |
| `Cqxj` | 13,443 | 25.0 | 244 µs | 1.565 ms | 6.4x |
| `Sqxj` | 23,166 | 43.0 | 345 µs | 1.548 ms | 4.5x |
| `Aqxj` | 25,184 | 46.8 | 387 µs | 1.523 ms | 3.9x |
| `Eqxj` | 39,856 | 74.0 | 506 µs | 1.558 ms | 3.1x |

The walk is flat across all thirteen, 1.49–1.56 ms. The indexed arm is linear
in anchor-byte frequency: 15.7x the hits, 15.6x the time. A 15x spread in the
speedup, from one letter.

Reproduced side by side, same head and same corpus in one process: realistic
credential prefixes (`A`, `g`, `x`, `s`, `S`, `e`, `p`, `k`, `d` — AWS, GitHub,
Slack, Stripe, SendGrid shapes) give 6.3–11.8x, and a `Z`-led keyword gives
55.4–56.7x. **The 52–96x reading came from synthetic `ZQ..` keywords, which is
the rarest leading byte in the table and a set no real ruleset has.** The
realistic regime is the honest one.

## The fifth rule, which is why this row is not just a benchmark

`docs/design/language-choice.md` §2 already pays for four benchmarking rules,
and §2.2's is that a repeated chunk lets the fixture choose the answer. This is
the same class through a door nobody had marked: **a synthetic keyword list
silently picks its own speedup.** The benchmark this row produces has to run
the *shipped* keyword list, and say so.

The method note beside it: a differential proves a rewrite preserved behaviour
only when it runs against the implementation being replaced. A 200,000-case
differential run against a variant of the new code passed clean while that code
carried two defects, because it was comparing the new implementation with
itself. Both defects were found by mutation instead.

## What this row has to produce

A benchmark in the tree rather than in a scratch directory, following the four
rules the design already paid for: real heterogeneous files, never a repeated
chunk, match counts asserted identical before any two timings are compared, and
fixed startup cost measured separately from throughput — below about 8 KB it
dominates, and a per-invocation hook lives there.

Then rewrite section 2's figure, or annotate it, so the repo stops carrying a
throughput claim about code it does not have. A number nobody can reproduce is
worse than no number, because it reads as evidence.

One lever to measure while the harness exists: anchoring on the keyword's
**rarest** byte rather than its first is correctness-neutral — the candidate
start is `i-k` and the boundary test is unchanged — and measured 155.8 µs to
25.4 µs on `AKIA`, 316.3 µs to 6.7 µs on `A3T`, and 332.2 µs to 307.4 µs on
`ASIA`, for 2.3x over the whole AWS list. Uneven, and it needs a byte-frequency
table or a sampling pass to choose the anchor without knowing the corpus, which
is real complexity for an uneven win. Measure before implementing.

The corpus this wants is `testdata/corpus/`, which [Q7](Q7.md) brings. Taking
the measurement before then is possible and gives an answer about whatever
files happened to be lying around, which is how both readings above were
taken.
