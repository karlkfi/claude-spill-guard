# A recursive grep's filter is judged without knowing where stdout goes

`filteredLater` in `internal/hook/grep.go` allows a recursive grep when a
`spill-guard filter` stage follows it in its own pipeline. It cannot ask
whether grep's stdout reaches that stage, and it cannot see a pipeline that
continues across a `}` or into a `(`. Both answers live in the segmenter, not
in `grep.go`. Driven 2026-11-01 through `spill-guard hook` on binaries built
from `9461a14` and again after Q212 merged, with the same verdicts, against a
directory holding one matching file:

| Command | Verdict | Should be |
|---|---|---|
| `grep -r x d >&2 \| spill-guard filter` | allowed, silent | refused |
| `grep -r x d 1>&2 \| spill-guard filter` | allowed, silent | refused |
| `grep -r x d 2>&1 \| spill-guard filter` | allowed | allowed |
| `{ grep -r x d; } \| spill-guard filter` | refused | allowed |
| `grep -r x d \| (spill-guard filter)` | refused | allowed |

**The silent allow.** `>&2` sends grep's matched lines to stderr, which the
tool result carries, and the filter reads nothing. A descriptor duplication is
never recorded in a `Segment`: the dup branch of `segments` skips a target that
is a bare descriptor number or `-`, so `>&2`, `1>&2` and `2>&1` all leave
`Redirects` empty and cannot be told apart. The fix is a field set at that
branch saying fd 1 was retargeted, which `Inputs` is the precedent for, and
`filteredLater` refusing to count a filter when it is set. There is nothing to
port: workspace-guard 1.14.0 reads a `>&` target in `lib/bouncer_parse.py`
(`` # A `>&` target that duplicates or closes a descriptor rather than naming a
file. ``) only to decide it is not a path, because no question upstream turns on
where stdout goes.

One residual the field cannot close: the lexer splits `2>&1` into `2`, `>&`,
`1` before segmentation, so a descriptor prefix and an operand literally named
`2` written before a spaced `>&2` read the same way. Upstream documents the
same ambiguity at the same site.

**The over-refusal.** A throwaway test printing `Segments` shows grep in pipe 0
and the filter in pipe 1 for both shapes: the `;` before `}` closes pipe 0, so
`}` and the filter open pipe 1, and a `(` before the filter opens a new number
too. Q212's rework of how a piped group is segmented did not change either
verdict. The PR 191 review also reported
`grep -r x d |& spill-guard filter` as refused; it is allowed, which is
correct, since `|&` pipes stderr as well.

The rest of this row's original scope shipped in the pull request that
narrowed it: `--context` read both ways, a digit option read as recursion
because ugrep recurses on it, and the reader table's grep row brought into
step with how grep takes long options. Two halves were answered as won't-fix there. An
unknown option stays refused, because ugrep walks the tree on options the
table does not list. A quiet flag after an operand stays honoured despite
`POSIXLY_CORRECT`, because refusing it changed 86 recorded commands from
allowed to refused, all harmless; `docs/design/README.md` has the count.
