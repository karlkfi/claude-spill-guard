# The recursive-grep refusal still misreads some grep commands

`filteredLater` asks whether a `spill-guard filter` stage follows the grep in
its pipeline. It does not ask whether grep's stdout reaches that stage, and
three shapes from the PR #191 review show the gap in both directions. Two more
from the re-review are in `grepMode`, which reads the flags, and are at the end.

**Allowed when it should not be.** `grep -r x d >&2 | spill-guard filter`
sends grep's output to stderr, which the tool result carries, and the filter
reads nothing. The hook allows it silently. The reason is upstream of here:
`internal/bash` records a redirect's target and not its descriptor, and a
descriptor duplication is not recorded at all — probed 2026-10-02, `>&2`,
`1>&2` and `2>&1` all leave `Segment.Redirects` empty, while `2>/dev/null`
and `>out` record their targets. So `>&2` (the bypass) and `2>&1` (harmless,
and common) cannot be told apart from a segment. Fixing it means the segmenter
carries the operator and descriptor, which is a change to ported code and
belongs upstream first, per CLAUDE.md's rule on shell parsing.

**Refused when it should not be**, reported by the reviewer and not re-driven
here: `{ grep -r x d; } | spill-guard filter`, `grep -r x d | (spill-guard
filter)` and `grep -r x d |& spill-guard filter`. Over-refusal costs a turn
and is the safe direction, so this half ranks below the first.

**Unmeasured: `POSIXLY_CORRECT`.** With it set, GNU grep stops reading options
at the first operand, so in `grep -r x d -l` the `-l` is a file and grep
prints matched lines — while `grepMode` reads it as quiet and allows the call.
`grepMode` assumes both greps permute, which was driven only for BSD grep 2.6.0
(no GNU grep on the machine that wrote it). The hook cannot read the tool
process's environment, so the fix is probably to stop honouring a quiet flag
that appears after the first operand; drive GNU grep first.

**Allowed when it should not be: a consumed value that is really `-r`.**
`grepLong` marks `--context` as taking the next token, so in `grep --context -r
x` the hook reads `-r` as the value, finds no recursion and, with no operand,
nothing to open. BSD grep takes `--context`'s value only after `=`, so `-r` is a
flag there and grep walks `.`. Driven 2026-10-03 on a binary built from
`720ff7d`: BSD grep 2.6.0 printed `./sub/f:xmark` at exit 0 and the hook exited
0 with no output and no coverage record. The comment on `grepLong` says a
consumed token never works the other way, and this is that way. Where GNU and
BSD disagree on whether an option consumes, the token after it should be read
both ways and the call refused if either reading recurses — the same rule
`unsure` already applies to an unknown option. It is a silent allow, so it
ranks with the `>&2` half.

**Refused when it should not be: an unknown long option on stdin.** An unknown
or ambiguous long option sets `unsure`, which reads the call as recursive, and
a recursive grep with no operand is given `.`. So `echo hi | grep --frobnicate
hi` is denied with the directory reason, driven on the same binary, though grep
reads stdin there and would reject the option at exit 2 anyway. Over-refusal,
and the reason names a walk that does not happen. Reported by the reviewer as
N5 and N6 in the
[re-review](https://github.com/karlkfi/claude-spill-guard/pull/191#issuecomment-5971030310).
